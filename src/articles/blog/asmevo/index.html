AsmEvo

Agentic Assembly-Level Optimization of AMD GPU Kernels with Functional Equivalence Verification

已经编译完的 GPU kernel 还能再快多少？AsmEvo 把优化的入口放到编译产物之后：输入一个 AMDGPU code object，输出另一个更快的 code object，中间不碰任何源码，正确性的唯一裁判就是原来那个二进制自己。

KernelBench 30 个 29 改进，几何均值 1.35× 最大 3.88× 生产 kernel 8/8 改进 arXiv 2608.20711

前置一：源码级优化管不到的那一层

现在做 GPU kernel 优化的 LLM 系统几乎都长一个样：给模型一份 CUDA / Triton / HIP / tensor-program 源码，让它改写，然后拿一份参考实现比对输出，快了就留下。KernelBench、Kevin、CUDA-L1、GEAK、CudaForge、KernelEvolve 都在这条线上。

这条线有一个共同的隐含前提：还剩下的性能，都能通过改源码拿到。AsmEvo 这篇论文的出发点就是质疑这个前提。它指出 kernel 的最终性能不只由 high-level schedule 决定，还由 lowering 之后才落定的一批低层决策决定，原文列的是五类：

  • wait-counter placement——AMDGCN 的内存等待是显式的，等在哪一条指令前面直接决定 stall 长度；
  • instruction selection——同一个语义有多个变体（不同的 cache hint、不同宽度的 load）；
  • register allocation——VGPR/SGPR 用多少反过来钳住 occupancy；
  • kernel descriptors——描述这个 kernel 需要多少资源的那张表；
  • ABI-visible metadata——host 侧 launcher 看得见的那部分接口信息。

论文的原话是，一旦 kernel 变成了 AMDGPU code object，剩下的优化机会「may no longer be exposed through the source program」——不是源码里改不动，而是源码里看不见。你在 HIP 层面写不出「把这条 s_waitcnt 往后挪三条指令」。

更现实的一层是：很多部署场景根本没有源码可改。论文点了三种形态——serving stack 只暴露一个编译好的 HSACO；一个 JIT cache artifact；或者干脆是 vendor binary，比如 AMD 自家的 AITer code object，以及嵌在 vLLM / SGLang 里由 Triton 生成的 kernel。

注意一个容易混淆的点。这里说的「没有源码」不等于「反编译不出来」。Triton kernel 当然有 Python 源码，但你拿到的是 JIT 编译缓存里的那个 HSACO，它是实际被 dispatch 的东西；重新编译一次未必得到同一个二进制，而生产环境要替换的正是这个二进制。所以「source-free」的准确含义是：可优化对象与可验证对象都只有这个二进制。

前置二：一个 AMDGPU code object 里到底有什么

要理解 AsmEvo 的第一个创新点，得先知道它面对的对象长什么样。一个 .co / .hsaco 是个 ELF 容器，里面大致分三类东西：

  • 指令体：AMDGCN 机器码。这是反汇编器唯一能可靠还给你的部分。
  • kernel descriptor：一张定长的资源表，告诉运行时这个 kernel 要多少 VGPR、多少 SGPR、多少 LDS、多少 scratch。运行时靠它决定一个 CU 上能并发放几个 workgroup（也就是 occupancy）。
  • AMDGPU metadata 与符号表：kernarg 的布局与总大小、每个参数的类型与偏移、kernel 的符号名。host 侧的 launcher 靠这些把参数打包进 kernarg buffer 再 dispatch。

关键在于：资源信息在两个地方各存了一份——kernel descriptor 里有，AMDGPU metadata 里也有。这两份必须一致，否则运行时的行为就没有定义了。论文把这种情况叫 desynchronize metadata，并把它列为汇编级编辑四大风险之一（另三个是破坏内存、违反 kernarg ABI、以及「只是改了语义所以看起来变快」）。

问题设定：二进制既是部署产物，也是唯一 oracle

这是全篇最值得慢慢读的一段，因为它决定了后面所有机制的形状。

设待优化的 code object 是 $K_0$。AsmEvo 把「正确」定义为「和 $K_0$ 跑出来一样」，也就是

$$O(x) = \mathrm{run}(K_0,\, x)$$ $x$ 是一组输入与 launch 配置，$O$ 是 oracle。这个式子朴素到有点反常——oracle 不是数学定义、不是参考实现、不是 PyTorch 算子，就是把原二进制跑一遍。

论文的原句是「the original binary is both the deployed artifact and the only behavioral oracle」。这带来一个很好的性质，作者称之为 non-hackable：

「the optimization signal is non-hackable: fast but incorrect candidates are rejected before timing.」
对比一下源码级 LLM kernel 优化的经典失败模式：模型发现只要输出形状对、数值大致对，评测脚本就给分，于是它开始偷工减料——少算一个分支、把 tolerance 内的近似当成等价、甚至缓存住测试输入的答案。这类 reward hacking 之所以可能，是因为参考实现和被测实现是两个不同的东西，二者之间有解释空间。而当 oracle 就是 $K_0$ 自己时，解释空间被压缩到只剩「输出是否一致」这一条。

代价也很直接：你失去了「什么叫正确」的独立定义。如果 $K_0$ 本身有 bug，AsmEvo 会忠实地把这个 bug 保留下来。论文对此的态度是明确的——它要的不是「正确的 kernel」，而是「和已部署的那个 kernel 行为一致但更快的 drop-in 替换件」。这两个目标在生产环境里往往后者更实用。

再看它和已有工作的边界。论文的判据是「已有工作都 operate before or during compilation and assume editable source or IR together with a high-level correctness reference」。也就是两个维度同时不同：

优化对象正确性参照能否 drop-in 替换

论文对自身定位的原句：「To our knowledge, AsmEvo is the first system to combine agentic search, ABI- and metadata-preserving AMDGPU code-object rebuilding, and differential verification against the original deployed binary.」注意这是一个三者组合的首创声明，不是单项首创——binary 层做 instrumentation 早有 Luthier，汇编层做超优化搜索早有 STOKE / AlphaDev / CuAsmRL。

一个顺带的方法论论点。论文引用 EquiBench 说明「程序等价性推理对强模型仍然很难」，据此论证不能让模型自己判断改动是否等价，必须用 execution-based verification。这条论证贯穿全篇——后面你会看到，凡是「宣告」性质的判断（能不能编译、ABI 是否一致、是否等价、是否更快、是否 commit）全部由确定性代码持有，模型一条都不碰。

创新一：恢复一份「可重汇编」的表示，并用逐字节 round-trip 证明它可信

直接把 K_0 反汇编一遍，然后改指令、再汇编回去——这条路走不通。论文一句话点出原因：

「raw disassembly omits the declaration layer.」
反汇编器给你的是「这些字节是什么指令」，但汇编器需要的是一份完整的源文件：段怎么分、符号怎么声明、kernel descriptor 的每个字段取什么值、metadata 里写了什么。这些信息在反汇编输出里全都是注释或者干脆没有。

所以 AsmEvo 的第一步（论文的内部工具名叫 co2s）不是反汇编，而是重建一份等价的汇编源文件 $s(K_0)$。论文列出它恢复的六类东西：sections、symbols、notes、kernel descriptors、AMDGPU metadata、AMDGCN instruction body。其中 kernel descriptor 是以 .amdhsa_kernel 声明的形式重建的。

为什么必须 re-symbolize PC-relative 控制流

这一步是整篇论文里最容易被跳过、但技术上最关键的一处。原文：

「re-symbolize PC-relative control flow so that branches remain valid after instruction insertion, deletion, or reordering.」

AMDGCN 的分支是相对偏移的：s_branch 里存的是「往前/往后跳多少个指令字」。如果你保留这个数字不动，那么一旦在分支和目标之间插入或删除任何一条指令，这个偏移就错了——控制流会跳到指令中间，行为完全不可预测。

把偏移换回符号标签之后，偏移的计算权就交回给汇编器：每次重新汇编时，汇编器按当时的实际布局重新算所有偏移。这一个动作把可做的编辑从「等长替换」放宽到「任意插入、删除、重排」——而后者才是调度类优化（把 load 提前、把 wait 后移、交错两条依赖链）的必要条件。

反过来看就理解了 fallback 的定位。后面会讲到的 in-place byte patch 之所以被限制为 size-non-increasing，恰恰是因为它没有经过 re-symbolize——指令地址不能变，所有 PC 相对偏移才继续有效。这两条路径的能力差异完全由「偏移是数字还是符号」这一点决定。

round-trip gate：一次性的逐字节自证

恢复出来的 $s(K_0)$ 到底忠实不忠实？AsmEvo 不假设，而是验证：把 $s(K_0)$ 重新汇编并重新链接，然后拿结果和 $K_0$ 比三样东西——

  1. regenerated instruction body；
  2. kernel descriptors；
  3. metadata。

比对时只 mask 掉「由链接决定的字段」（原文 masking only fields determined by linking，比如加载地址一类每次链接都会变的东西）。过了这个 gate，就证明后续所有编辑作用在一份 faithful, rebuildable representation 上。Algorithm 2 的第一行是硬断言 assert RoundTrip(s(K₀), K₀)——过不了，这个 kernel 就直接不进入优化流程。

论文还提了一句：偶尔需要对 recovery 做修补（rare recovery repairs），修补后的表示必须重新通过同一个 byte-level round-trip check 才被接受。也就是说这道 gate 不是一次性摆设，而是 recovery 层唯一的信任来源。

这个设计的漂亮之处在于它把「反汇编正确性」这个通常无法验证的问题，转化成了一个可判定的等式。你不需要论证 co2s 的实现没有 bug；你只需要检查这一次的输出重新编译后与输入逐字节相同。不同就拒绝，不冒险。

创新二：metadata 感知重建——哪些字段必须重算，哪些必须冻结

假设 agent 改了几条指令。现在要把 $s'$ 变回一个能被运行时加载、且能被原来那个 host launcher 不改一行代码就调用的 code object。这里有一组精确的「重算 / 冻结」划分，是这一步的全部内容。

必须重算的：资源字段

原文：rebuild 时会 rescan 汇编，统计 VGPR / SGPR / AGPR、LDS、scratch 的用量，然后在 kernel descriptor 和 AMDGPU metadata 两处同时重算资源字段，最后重新链接。

为什么必须重算？因为指令一改，资源用量就可能变。举个方向性的例子：agent 为了打散一条依赖链多用了两个 VGPR，声明里却还写着原来的数字——运行时按旧数字分配寄存器，实际执行时越界访问其他 wave 的寄存器，行为不可预测；反过来如果多声明了，occupancy 白掉一档，性能反而变差。而「两处都要改」是因为前置二里说的那件事：资源信息在 descriptor 和 metadata 里各存了一份，只改一处就是论文所说的 desynchronize metadata。

必须冻结的：接口

原文列的是四样：kernarg layout、kernarg segment size、symbol interface、launch semantics，目的是 preserving compatibility with the original launcher。论文把这条整理成需求 R1：$K'$ 保持 symbols、kernarg layout、launch semantics 与 externally visible metadata。

这条冻结要求正是「drop-in」的技术定义。host 侧代码是这样调用 kernel 的：按 metadata 描述的偏移把每个参数写进 kernarg buffer，按符号名查到 kernel，按自己的 grid/block 配置 dispatch。这三件事任何一件对不上，替换就失败——不是慢一点，是根本调不起来。所以 AsmEvo 允许改的只有「怎么算」，一律不许改「怎么被调用」。

agent 是怎么被阻止破坏这些的

这里体现了论文的核心工程主张：不靠提示词约束，靠机制。三层：

  1. metadata 重算不是 agent 做的。它由确定性 controller 执行。原文的职责划分是「Deterministic gates own build validation, resource checks, equivalence, timing, commit thresholds, and lineage management」——agent 连碰这些的接口都没有。
  2. 每个候选先过静态一致性检查。Algorithm 1 的第 3 步：if ¬StaticConsistent(c) then return ⟨abi_invalid⟩。这对应架构图里的 gate G1（static ABI / resource），在任何计时之前。
  3. agent 的先验知识里就写了 ABI 规则。架构图的 "Built-in Knowledge" 一栏是「AMDGCN ISA, hazards, ABI rules, tolerance policy」。这只是降低无效尝试率，不承担安全性。
要澄清一处，避免读者被我误导：论文只点名了 VGPR / SGPR / AGPR、LDS、scratch、kernarg segment size 这一组字段。像 .amdhsa_accum_offset、.amdhsa_wavefront_size32、kernarg_segment_align 这些具体字段名在全文中一次都没出现。如果你在别处看到把它们写成「AsmEvo 保持的字段」，那是补充的工具链背景知识，不是论文内容。

兜底路径：保守的 in-place byte patch

如果一个 object 含有 unsupported or incompletely recovered constructs，正常重建就会失败。这时 AsmEvo 可以退到「直接改原二进制的字节」这条路，但被加了两道限制：

  • resource-neutral——不改变资源用量；
  • size-non-increasing——改动后不变长；
  • 并且保留原有的 descriptors 与 metadata。

三条限制各自封住一类风险，对应关系很干净：保留原 descriptor / metadata ⇒ 不可能出现两处 desync；resource-neutral ⇒ 不动资源声明 ⇒ occupancy 不变；size-non-increasing ⇒ 后续指令地址不变 ⇒ 所有 PC 相对偏移继续有效（这正是创新一里 re-symbolize 解决的问题，在这条路径上是用「不许变长」硬绕过去的）。

论文特别强调一句：patched candidate 仍然要过全部 gate（静态一致性、差分等价、性能），「the fallback therefore changes only the rebuild mechanism, not the acceptance criterion」。

论文未说明：是否用 s_nop 之类填充空出来的字节、patch 的粒度，以及实际有多少 kernel 走了这条 fallback（没有任何统计）。

创新三：两层差分 oracle——没有源码，怎么知道该喂什么输入

「拿 $K_0$ 跑一遍当参考」听起来简单，实际有个先决问题：你都不知道这个 kernel 收哪些参数。没有函数签名，只有一个 kernarg buffer 的总大小和一堆偏移。AsmEvo 分两层解决。

Tier 1：synthetic inference（从 descriptor 与 metadata 推参数）

当 launch structure 能从 descriptors 和 metadata 里恢复时，AsmEvo 推断这五样：argument offsets、scalar types、pointer roles、buffer sizes、launch dimensions。然后生成确定性输入，覆盖 representative shapes, strides, dtypes, boundary values, and random seeds。

这里有一个很值得学的小设计：

allocation 带 guard region，并用 canary 初始化。
也就是在每块 buffer 的前后留一段哨兵区、填上已知的魔数。这样等价检查除了「输出对不对」之外，还顺手多检出一类错误：越界写。这类 bug 在只比对输出的方案里是完全隐形的——它可能这次没踩到别人的数据，下次就踩到了。用 canary 把它变成一个确定性可观测的信号，成本几乎为零。

Tier 2：real-dispatch capture（拦一次真实调用录下来）

Tier 1 有明确的失效边界。论文列了五种情况推不出来：mixed dtypes、non-contiguous tensors、block tables、nested pointer structures、application-defined workspace layouts。想想 vLLM 的 paged attention——kernarg 里有个指向 block table 的指针，block table 里又是一堆指向物理块的指针，这种结构不可能从偏移和大小反推出来。

所以 Tier 2 换了个思路：拦截一次真实的 application dispatch，把现场整个录下来（架构图里这个工具叫 kerncap）。录四样：

  • kernarg buffer 的内容；
  • grid 与 workgroup dimensions；
  • 被引用到的 device-memory regions；
  • pre-dispatch memory state（执行前的内存快照）。

然后用原 object 跑一次，得到 reference post-state（执行后的内存快照）。候选就在完全相同的 launch 参数与内存内容下回放，比对 post-state。

这里有一句技术细节我认为是全篇最巧的一手：

「When captured arguments contain absolute device pointers, memory regions are restored at their original virtual addresses so that nested pointers remain valid without reconstructing application-level data structures.」
录下来的 kernarg 里存的是绝对设备虚拟地址。如果回放时把内存分配到别的地址，指针就全废了，而且嵌套指针（指针指向的内存里还有指针）没法简单地做地址重定向——你得先理解应用层的数据结构才能改写内部指针，而那正是 source-free 场景下办不到的事。AsmEvo 的解法是绕开这个问题：不改指针，改地址——把内存恢复到原来那个虚拟地址上。这样任意深度的嵌套指针自动全部有效，无需理解任何应用语义。

等价判据

两层 oracle 拿到输入集 $\mathcal{X}$ 之后，等价性的定义是（论文 Eq. 1）：

$$\mathrm{eq}(K',x)\;\equiv\; c_x \ge \theta \;\wedge\; \|\Delta_x\|_\infty \le \tau \;\wedge\; \iota(K',x)$$ $$c_x=\cos\big(K'(x),\,O(x)\big),\qquad \Delta_x = K'(x)-O(x)$$ $c_x$ 是余弦相似度（管方向/整体形状），$\|\Delta_x\|_\infty$ 是最大绝对误差（管单点离群），$\iota$ 是一个布尔谓词，要求整数 buffer 逐位相同且越界哨兵完好。实验取值：$\theta = 0.9999$、$\tau = 10^{-3}$，每个候选重复 3 次。

三个条件的分工很清楚。只用余弦相似度会漏掉「一个元素错得很惨但其余全对」的情况；只用 $L_\infty$ 会对大数值的正常浮点抖动过于敏感；而 $\iota$ 处理的是浮点容差不该适用的那部分——索引、掩码、计数这些整数结果没有「差不多对」，必须逐位相同。Tier 2 里对 integer buffer、opaque state 和 guard region 同样是逐字节比较。

创新四：GatedEval——正确性严格先于计时，以及一个方差感知的接受阈值

论文把候选评估固化成一条不可交换的流水线，原文：「Every candidate passes GatedEval in a fixed order: functional-equivalence verification first, performance measurement second.」以及「Correctness strictly precedes timing, preventing broken but fast candidates from receiving a positive optimization signal」。

Algorithm 1：五个出口

GatedEval(s', (𝒳, O), K₀):
  1  if ¬Assembles(s')        → return ⟨asm_invalid⟩
  2  c ← Build(s')
  3  if ¬StaticConsistent(c)  → return ⟨abi_invalid⟩
  4  for x ∈ 𝒳:
       if ¬eq(c, x)           → return ⟨divergent⟩
  5  ŝ(c) ← T(K₀) / T(c)
     return ⟨ok, ŝ(c)⟩
注意第 5 步的位置：计时是最后一件事。一个语义错了的候选永远拿不到时间数字，因此也永远不可能因为「快」而被搜索采纳。

失败不是简单地丢弃，而是变成结构化反馈回给 agent。论文枚举的失败类别是五种：assembly failure、metadata inconsistency、output divergence、runtime failure、insufficient speedup；对应架构图的五道 gate：G0 build valid → G1 static ABI / resource → G2 func equiv → G3 timing → G4 commit gate，横条标题写的是「Correctness-gated verification — correctness before speed」。

计时怎么测，以及为什么必须容忍噪声

做法是：warmup 之后取 $R$ 次 event-timed launch 的中位数，候选与 oracle 在相同设备、相同 launch 条件下测。（$R$ 的具体数值论文未给出。）

但论文诚实地承认了一个测量环境问题：「Because the hardware is shared and clocks cannot be locked」——共享硬件、频率锁不住。这意味着同一个二进制反复测，结果本身就在抖。他们的两个对策是：用大而有代表性的 launch 配置压掉 launch 与 event 的固定噪声；以及在接受阈值里显式建模方差。

commit gate：把噪声写进阈值

$$m^\star=\big(1+\max(\epsilon,\; k\cdot \mathrm{cv})\big)\cdot \hat s(K^\star)$$ $$g(c)\;\equiv\;\Big[\textstyle\bigwedge_{x} \mathrm{eq}(c,x)\Big]\;\wedge\;\hat s(c)\ \ge\ \max\big(m^\star,\; s_{\mathrm{floor}}\big)$$ $\mathrm{cv}$ 是计时的变异系数（标准差/均值），$\hat s(K^\star)$ 是当前 verified best 的加速比，$\epsilon$ 是最小改进 margin，$s_{\mathrm{floor}}$ 用来拒掉 trivial rewrite。实验取值 $\epsilon=0.002$、$k=0.85$、$s_{\mathrm{floor}}=1.0$。

把这个式子读一遍就明白它在防什么。假设当前 best 是 1.20×，某个候选测出 1.21×。这算不算进步？

  • 如果这次测量很稳，$\mathrm{cv}=0.002$，那么 $k\cdot\mathrm{cv}=0.0017 < \epsilon=0.002$，阈值取 $\epsilon$，$m^\star = 1.2024$。候选 1.21 > 1.2024，接受。
  • 如果这次测量很吵，$\mathrm{cv}=0.02$，那么 $k\cdot\mathrm{cv}=0.017$，$m^\star=1.2204$。候选 1.21 < 1.2204，拒绝——它的「进步」淹没在噪声里。
论文对这一项的说法是「The variance-aware threshold prevents measurement noise from advancing the search.」这句话的重量在长时程搜索里比看起来大得多。搜索会跑上百个候选、提交七八次；如果每次「进步」都有一半概率是噪声，那么几十步之后 best 的记录值会被噪声推到一个虚高的位置，而后续所有候选都要跟这个虚高的数字比——搜索会自己把自己卡死。$k\cdot\mathrm{cv}$ 这一项就是防止这种噪声棘轮。

还要注意两处容易读错的细节：$m^\star$ 是相对当前 verified best 算的，但对外报告的 speedup 始终相对原 object，即 $\hat s(K')=T(K_0)/T(K')$。另外全局 best 遵守 no-regress invariant——只会变好，不会退。

创新五：hot-window——把 context 缩小，但不缩小验收范围

一个真实的 kernel 汇编可能有几千条指令。把整份汇编塞进每一次优化 context，既装不下也没意义。AsmEvo 的做法用一句原文概括最准确：

「Instead of placing the entire assembly in every optimization context, AsmEvo selects a hot window together with the surrounding data dependencies and relevant metadata.」

定位手段是三件套：hardware counters、instruction sampling、static analysis，目标是找出 stall-dominant instruction windows。汇总给搜索驱动的信息有五类：instruction mix、dependency chains、memory behavior、occupancy constraints、resource pressure。

论文未说明具体用的是哪个 profiler——rocprof / rocprofv3 / ATT / omniperf 一个字都没提，架构图里只写「① Profile — Counters + sampling → hot window」。window 的长度、呈现格式、prompt 模板与 token 预算同样未说明。

关键的那半句：不弱化验收准则

window 编辑完之后，会被 spliced back into the complete assembly，然后做整 kernel 的 rebuild 与 verification。论文给这个设计的两句总结值得逐字读：

「reduces search context and discourages unrelated modifications without weakening the full-kernel acceptance criterion.」

这句话拆成两半意思完全不同。前半是效率手段：小 context 便宜、且天然抑制模型去改无关的地方。后半是安全声明：验收不是在 window 上做的。为什么这一点必须强调？因为局部看起来独立的指令序列在 fused kernel 里往往不独立——论文自己举的例子是「an apparently independent instruction sequence may affect a later reduction, normalization, or activation stage」。如果只在 window 内部检查等价，这类跨阶段的破坏就会漏过去。所以 AsmEvo 的 window 只是注意力的范围，不是责任的范围。

另外每次 commit 之后会重新 profile（Algorithm 2 第 18 行 "append to ℒ; re-profile"）。这是必要的：改完一处瓶颈，热点就搬家了，拿旧 profile 继续找下一个热点会一直在错的地方打转。

agent 到底发现了哪些优化

这是我读完全文最想告诉你、也最需要提醒你降低预期的一点：论文里没有任何一行汇编代码，没有一条指令助记符。我对全文做过检索，s_waitcnt、v_mfma、buffer_load、ds_read_b128、sched_barrier、s_nop、v_mov_b32 的出现次数全部为 0；全文唯一的 AMD 汇编语法字样是 .amdhsa_kernel，出现一次。

论文对优化类型的描述全是自然语言，且集中在 AITer 的 case study 那一段。可以引用的就这些：

「AsmEvo's gains arise from narrow opportunities that remain visible in recovered AMDGCN assembly: scheduling around long-latency memory operations, wait-counter placement, cache-hint and buffer-load variants, and reduced conversion or address-generation work.」

「Across the AITer cases, the most promising edits are localized rather than structural. ... Hoisting, interleaving, or tighter wait counters can reduce stalls without changing the launcher ABI.」

另外 team mode 分派给并行 worker 的五个正交方向，也可以当作优化类型的官方分类：latency hiding、dependency reduction、register-pressure control、memory-access restructuring、instruction simplification。

论文还有一句反面论证很有说服力：四个增益最大的 kernel 分别属于 convolution、activation、normalization、structured matmul，作者用它说明「why a single fixed peephole rule would be insufficient for the evaluated set」——即这些收益不能被固化成一组窥孔优化规则，因此才需要搜索。

如果你在别处看到关于这篇论文的解读里出现了具体的汇编 diff、LDS bank conflict 消除、ds_read_b128 加宽、v_mfma 打包之类的例子，那些都是基于上述优化类别的合理外推，不是论文原文。

创新六：长时程 agentic 搜索——职责怎么切，血统怎么记

搜索模型是 Claude Opus 4.8，provider-default decoding。默认配置是 4 个 GPU worker、每个 kernel 固定 0.5 天（12 小时）wall-clock 预算。

最重要的一句话

「the model may guide exploration, but it cannot declare either correctness or performance.」

职责划分是明确列举的。确定性 controller 持有：wall-clock 预算、workspace 状态、rebuild 与 verification 的调用、commit 决策、candidate lineage、终止条件。LLM 负责：分析 profiling 证据、挑瓶颈、提出局部汇编变换、解读结构化失败、在无效尝试后重新规划。

这个切法的实际效果是：agent 的所有错误都只是浪费预算，不会变成错误的产出。它可以提出一百个破坏语义的编辑，一个都过不了 G2。

血统树（lineage），而不是一条链

AsmEvo 维护的是树状而非单条破坏性链的候选血统。每个节点记录：parent、verified speedup、changed instruction windows、resource usage、optimization rationale。worker 既可以从当前 best 分叉，也可以退回到更早的某个 verified 版本重新出发。

还有一条很关键的卫生措施：每次评估之后 controller 把 worker 重置回 verified state（架构图里画成一条虚线 "reset to verified state"），原文的理由是 preventing unverified modifications from accumulating across iterations。没有这一步，一串各自「看起来没问题」的未验证改动会叠在一起，最后连是哪一处坏的都查不出来。

multi-start 与 verified composition

两种模式：single mode 从当前 best 提一个编辑；team mode 由一个 planner 给并行 worker 分派正交的优化方向（就是前面那五个），起点从多样的 verified 节点里选，不要求所有 worker 改同一个候选。

然后是把并行成果合起来。integrator 只考虑满足两个条件的候选：共享同一个 base，且改动的指令区域互不相交或互补。合并方式是增量应用，每一步都 rebuild + verify。合并结果只有在通过全部正确性 gate 并且优于两个 parent 时才 commit，否则保留两者中更好的那个单体。

为什么合并必须逐步重验，而不能「改动不相交所以合起来一定对」？因为汇编级的独立性判断在指令区域上成立，在硬件资源上不成立。两个各自合法的编辑可能各多用两个 VGPR，合起来就跨过了 occupancy 的档位；也可能各自调整了 wait counter，合起来某条 load 的等待就不够了。区域不相交只保证「文本上能合」，不保证「语义上能合」。

memory 与 anti-stall

有界的 run memory 里存四样：successful optimization insights、structured gate outcomes、failure signatures、以及重复候选的 hash。最后这一项是纯工程但很实在的——长时程搜索里模型反复提出同一个改动是常态，用 hash 去重直接省掉一次完整的 build + verify + timing。

anti-stall 监督：controller 检测到长时间无改进、重复提案、或基础设施故障时，会请求一次 redirect，内容是「总结已尝试的方向并标记 exhausted hypotheses」。之后搜索可以换一个瓶颈或回溯到更早的 verified 节点。持续停滞则升级为更宽的 multi-start 探索。所有被 redirect 之后产生的候选仍然走同一批 gate——这一点论文反复强调，任何机制都不能绕过验收。

名字里的 Evo：它其实不是进化算法

叫 AsmEvo，很容易让人以为里面有个种群在做变异和交叉。读完方法一节可以确认：没有。全文没有 population size、mutation rate、fitness-proportional selection、island model 这类概念，也没有引用 AlphaEvolve 或 FunSearch（参考文献里都没有）。

它实际的机制是三样：树状 verified lineage、multi-start、verified composition。如果一定要找对应关系，verified composition 大致对应「重组」，multi-start 大致对应「多样性维持」，但选择压力完全来自一个确定性阈值 $g(c)$，不是概率化的适应度采样。

比较准确的一句描述是：「带验证血统树的多起点长时程 agentic 搜索」。论文里进化式的相关工作（AVO、KernelEvolve、Lange et al.）只出现在 related work 里，不是它自己的机制。这个区分不是抠字眼——进化算法的收敛性质、探索/利用权衡分析都不适用于这里，用错框架去理解它反而会得出错误的预期。

实验：30 个 KernelBench 与 8 个生产 kernel

硬件是 CDNA3 的 AMD Instinct：KernelBench L1+L2 在 MI308X，AITer 与 Triton JIT HSACO 在 MI300X。未修改的二进制永远是 1.00× 基线。全部结果只报 speedup，不报原始延迟。

先看一件容易忽略的事：$K_0$ 是怎么来的

KernelBench 部分的输入二进制不是直接编译 benchmark。他们先用一个 GEAK 风格的 agent 配 GPT-5.0，把 PyTorch benchmark kernel 改写成 HIP 版本，迭代 5 轮，编译之后只把编译产物交给 AsmEvo。论文强调：「The selected Level 1 and Level 2 HIP inputs are all faster than their PyTorch operators in the source-level benchmark, so $K_0$ is not a weak baseline.」

这一句是整个实验部分最重要的一句。如果 $K_0$ 是随便编译出来的弱基线，那么 1.35× 的几何均值毫无意义——那只说明源码级优化没做够。他们的设计是：先让源码级 agent 把源码优化到超过 PyTorch，然后问「编译之后还剩多少」。1.35× 是叠加在源码级优化之上的增量。生产 kernel 那一侧更直接：AITer code object 与 vLLM/SGLang 推理时 emit 的 HSACO 都是 exactly as deployed，本来就是各家调优过的东西。

一个值得盯住的数字：commit rate 5.1%

反过来读这个数字更有意思：95% 的失败全部被 gate 吃掉了，没有一个进入产出。这正是「机制而非提示词」那套设计要买的东西。如果没有 GatedEval，一个 5% 命中率的生成器在 12 小时里会产出一堆看起来能跑、实际有 desync 或越界的二进制。搜索质量低不可怕，可怕的是低质量能蒙混过关。

局限：经验等价的边界在哪

作者自己的 Scope and Limitations 一节列了四点，我先原样转述，再补两点我认为论文没讲透的。

  1. 等价性是经验的，不是形式的。原句：「AsmEvo provides empirical differential equivalence rather than formal verification; its guarantee is limited to evaluated inputs and launch configurations.」
  2. 新的 shape 需要新的输入。换一组张量形状，就要重新推断输入或重新录一次 dispatch。
  3. harness 本身架构无关，但当前实现只针对 CDNA。recovery 与 metadata-aware rebuild 是 calibrated for CDNA-class AMD GPUs。
  4. 收益上限取决于编译后还剩多少 headroom。复杂的 application state 可能必须走 real-dispatch capture。

我认为最需要补一句的：非确定性完全没有讨论

全文没有出现 atomic、nondeterminism、data race 这些词。
这是个实质性的空白。差分验证的整个逻辑建立在「同样的输入跑 $K_0$ 得到确定的 post-state」之上。但 GPU kernel 里有一整类操作本身就不保证跑两次结果逐位相同——跨 workgroup 的浮点原子加、非确定顺序的归约、依赖 wave 调度顺序的写入。对这类 kernel，$\iota$ 里那条「整数 buffer 逐位相同」的要求可能连 $K_0$ 自己都通不过；而浮点侧的 $\theta=0.9999$、$\tau=10^{-3}$ 是否宽到能容忍归约顺序变化，又是否宽到会放过真实的语义改变，论文没有分析。

「每个候选重复 3 次」这个设计从侧面说明作者知道存在抖动，但 3 次只够过滤偶发故障，不构成对非确定性的处理。

第二点：没有任何消融实验

论文在方法一节声明过比较方式应该是「在同一 harness 内比较 search driver，holding recovery, rebuilding, correctness verification, and commit gates fixed」——这个设计很正确，但正文里没有给出这个对比的任何数据。全文没有 ablation 表、没有换模型的对比、没有「去掉 hot-window 会怎样」「去掉方差感知阈值会怎样」。所以论文里那些设计选择（$k=0.85$、team mode 的五个方向、verified composition）的必要性都没有实验支撑，只有设计论证。

另外还有两处信息缺口：Table 1 里 AITer 写的是「the four retained kernels」，retained 这个词暗示有 kernel 被剔除，但剔除了几个、为什么，论文未说明；成本方面除了 12h/kernel × 4 worker 之外，token 数、金额、总 GPU 小时全部未给。

定位

作者的自我定位很克制，值得照抄：「AsmEvo complements rather than replaces source-level compilers, autotuners, and inference libraries.」结论最后一句是这篇论文真正想立的论点：「deployed binaries retain recoverable low-level headroom and that agentic search can exploit it safely under deterministic gates.」

总结

把这篇论文的创新点按「原理上解决了什么问题」重排一遍：

  • 反汇编不可信 → 用逐字节 round-trip 把它变成可判定的。不论证工具正确，只检查这一次的输出重新编译后与输入相同。
  • 指令增删会打断相对分支 → re-symbolize 把偏移换成符号。这一个动作把可行编辑从「等长替换」放宽到「任意重排」，是所有调度类优化的前提。
  • 资源信息两处存放会 desync → 两处同时由确定性代码重算，接口四样冻结。agent 连碰这些字段的接口都没有。
  • 没有函数签名不知道喂什么输入 → 两层 oracle。能推就推（外加 canary 顺手抓越界写），推不出来就录制真实 dispatch；而把内存还原到原始虚拟地址让任意深度的嵌套指针无需被理解就继续有效。
  • 快而错的候选会污染搜索信号 → 计时严格排在等价验证之后。语义错的候选永远拿不到时间数字。
  • 时钟锁不住、测量在抖 → 把 cv 写进接受阈值。防的是长时程搜索里的噪声棘轮。
  • 整份汇编放不进 context → hot window 缩小注意力，但验收仍在整 kernel 级。window 是注意力的范围，不是责任的范围。
  • 单链搜索一步走错全废 → 树状 verified lineage + 每轮 reset 回 verified state。未验证的改动不允许跨轮累积。
如果只带走一句话：这篇论文真正的贡献不是「让 LLM 改汇编」，而是把「让 LLM 改汇编」这件本来极危险的事，用一组确定性闸门包装成了安全的。它的每一个设计决策都能回答同一个问题——「如果模型这里出错，坏结果会流到哪里去」，而答案总是「流不出去，只是浪费预算」。5.1% 的 commit rate 在这个框架下不是缺点，而是证明：搜索质量可以很低，只要低质量出不了门。
同时要清楚它没做到什么：等价性只在已评估的输入与 launch 配置上成立，换 shape 就要重新取样；非确定性 kernel 的处理完全没有讨论；没有任何消融实验来支撑内部设计选择；实现绑在 CDNA 上。这些都不否定结果，但决定了你能把这个结论推广到多远。
