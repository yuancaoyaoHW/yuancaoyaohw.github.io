DisDP：把计算、网络、存储全解耦

让 GPU 只做 GEMM，通信卸到 SmartNIC，优化器卸到单台 PS

0核心思想：让 GPU 只做计算

💡 核心矛盾

大模型训练采用 ZeRO / FSDP 这类模型分片数据并行（MSDP），把模型状态均匀切片分布在所有 GPU 上。但 MSDP 引入大量 AllGather / ReduceScatter 通信操作 —— 通信比计算多花 1.25×–4.5× 的时间，8 卡训练 175B 模型的 MFU 仅 15%。瓶颈不是「网络太慢」，而是 GEMM 计算核与 collective 通信核在同一颗 GPU 上互相干扰：GPU 非抢占式调度让占满全部 SM 的 GEMM 阻塞下一轮通信核启动。

🎯 DisDP 的解法

解耦（Disaggregation）：把原本挤在 GPU 上的「计算 / 网络（collectives）/ 存储（optimizer）」三件事，分别卸载到 GPU / SmartNIC+SmartSwitch / 单台 PS 三种专门硬件上。GPU 退回它被设计出来的本职工作 —— 只做 GEMM，把利用率从 15% 拉到 ~59%。一句话：不是把网络做得更快，而是把通信从 GPU 上挪走。

论文甚至证明：DisDP 在 100Gbps 以太网上比 ZeRO-Offload 在 4.8Tbps NVLink 上还快 2.22× —— 因为后者仍然受困于「同一颗 GPU 既算又收」的根本矛盾。

1为什么 MSDP 训练只有 15% MFU

1.1 计算-通信干扰：GPU 非抢占式调度的致命伤

直觉上，collective 核只占 GPU 几个 SM（≤10%），应该很容易和 GEMM 重叠。但 GPU 采用非抢占式调度：一个计算密集的 GEMM 核一旦占满所有 SM，会阻塞后续 collective 核的启动，即使 collective 有最高优先级、即使两者无数据依赖。

即便用 MPS 静态切分 SM 来消除计算单元争用（但 MPS 不兼容 dynamic parallelism 和 CUDA graph，LLM 训练框架强依赖这两个特性，实战不可用），还有第二层争用：GPU 显存带宽 / L2 cache 争用。论文实测，并发 GEMM 仍让 NCCL AllReduce 的算法带宽下降 30%。

算法带宽定义：
$$BW_{\rm alg} = \frac{S}{t}$$
S = collective 数据总量，t = collective 执行时间。GEMM 并发让 t 变大 → BW 下降。

论文的关键发现：把 GEMM 核和「外部 PCIe 设备（如 FPGA NIC）通过 DMA 读写 GPU 显存」并发跑，几乎无干扰。这正是把 collective 整栈搬到 SmartNIC 的动机 —— 走 DMA 而非 GPU SM，从根上消除干扰。

1.2 为什么 SmartSwitch 救不了 MSDP

SmartSwitch（如 SHARP、SwitchML）通过 in-network aggregation 能为 MRDP 优化 AllReduce。但 MSDP 用的是 AllGather (AG) + ReduceScatter (RS)，论文证明 SmartSwitch 对这两个 collective 无法降低通信时间，原因是发送/接收流量的不对称：

N 个 worker 对总数据 S 做 collective。无 SmartSwitch 时每个 worker：
$$\text{send} = \text{recv} = \frac{(N-1)S}{N}$$

SmartSwitch 帮 AG：发送降到 $$S/N$$，但接收仍为 $$(N-1)S/N$$
SmartSwitch 帮 RS：接收降到 $$S/N$$，但发送仍为 $$(N-1)S/N$$

通信时间 = max(发送, 接收) / 带宽。SmartSwitch 只压低了单向，另一向仍是瓶颈 → 时间不变。

1.3 参数服务器（MiSDP）的扩展性陷阱

MiSDP 把模型状态挪到 PS：worker 只 push 梯度 + pull 参数，通信量比 MSDP 少最多 1/3。但要线速处理 16 个 100Gbps worker 的梯度，需要 13 台额外 CPU 机器做非协同 PS。瓶颈在 PS 的内存子系统：worker 越多，PS 要消费的部分梯度越多，内存压力线性上升。

2DisDP：计算-网络-存储三路解耦

DisDP 的硬件由三部分组成：① 每张 GPU 配一块 FPGA SmartNIC，跑无干扰 collective；② 一台 SmartSwitch，聚合梯度 + 广播参数 + 维护多对一可靠连接；③ 单台 PS（可扩展 CPU 服务器），跑 out-of-core Adam。GPU 只管 forward/backward 的 GEMM。

软件接口极简：push(buf, len) / pull(buf, len) / wait(handle)。push 和 pull 在 SmartNIC 上是两条独立流（独立硬件模块），可并发跑以榨干双工带宽。

2.1 SmartNIC 无干扰通信：为什么必须是 FPGA

朴素方案是把 collective 卸到 SoC SmartNIC（如 BlueField），但它有两个致命瓶颈，且短期内无解：

问题 1 · 内部交换链路争用

Off-path SmartNIC 的 host/NIC/Arm 通过内部交换连接，Arm 以 lookaside 方式处理流量 → push/pull 要在 Arm 和内部交换间来回，Arm-交换 PCIe 链路成瓶颈。BlueField-2 并发 push/pull 需 400Gbps Arm-交换带宽，实际只有 250Gbps。

问题 2 · Arm 显存带宽瓶颈

大 working set 无法被缓存 → 流量在 host↔Arm 显存↔网络间搬运，每方向 2× 显存访问。BlueField-2 需 800Gbps 显存带宽服务 200Gbps 包，实际只有 204.8Gbps → 仅 20% 线路利用率。BlueField-3 仍未解决。

论文改用 FPGA SmartNIC（Xilinx U50）：on-path 架构在硬件流水线里处理包（消除内部交换争用），流水线级之间用片上 SRAM暂存（避免 off-chip DRAM 带宽瓶颈），从而打到线速。

动画 3 · SoC SmartNIC 为何打不到线速，FPGA 为何可以
SoC：Arm-交换链路 + 2× 显存访问 两大瓶颈；FPGA：on-path 流水线 + 片上 SRAM
步骤 1 / 3

2.2 SmartSwitch 多对一可靠协议

单台 PS 要服务几十个 worker，每条 reliable 连接都要 ACK 包，worker 越多 PS 的网络 IOPS 越快被耗尽。论文测：传统 one-to-one reliable 连接下，32 worker 吞吐降到 30Gbps，64 worker 降到 18Gbps。

DisDP 的解法：周期性 heartbeat 包 + SmartSwitch 聚合 ACK。每个 worker/PS 周期发 heartbeat，含 Ack（下一期望序列号）和 Credit（能接收的最大序列号）。SmartSwitch 维护一张 heartbeat 表，对各 worker 的 Ack/Credit 做最小聚合，只向 PS 发一个聚合 heartbeat。于是 PS 每个 heartbeat 周期只收发各一个 ACK，与 worker 数无关。RTO ~250μs。

注意：让 SmartSwitch 自己做 endpoint 跑完整 reliable 协议不可行 —— Tofino 流水线 ≤20 级，而 reliable RDMA/TCP 需 >50 级。

动画 4 · 多对一可靠协议：PS 的 IOPS 怎么被救回来
传统每包 ACK：ACK 风暴耗尽 PS IOPS；DisDP：SmartSwitch 聚合 heartbeat，PS 每周期只 1 个 ACK

2.3 步骤中心优化器流水线

100B 模型的 optimizer 状态远大于单机内存，传统做法用多台 CPU 服务器。DisDP 想用单台 PS跑 out-of-core Adam，反向阶段要 6 个步骤：① SSD→CPU 读参数 ② push 参数到 SmartNIC ③ pull 梯度到 CPU ④ SSD→CPU 读 12B 模型状态 ⑤ CPU 跑 Adam（17 FLOPs/元素）⑥ 写回 SSD。反向阶段需求：99 GFLOPS 计算、349 GB/s 显存带宽、81.4 GB/s SSD 带宽。

朴素层中心（layer-centric）流水线给每层分配固定线程。但 Step 5（CPU Adam）要 32 线程才线速，其余步骤只需 1 线程 → 每层都要占 32 线程，并行度被线程数卡死，流水线出现气泡。

DisDP 的步骤中心（step-centric）流水线按步骤而非按层分配线程：每个步骤一次处理一层，层在步骤间轮转。这样可以给 Step 5 分 32 线程、其余步骤分少线程，37 个线程就能跑满整条流水线。单台 6730P（PCIe Gen5 + 12 SSD）足以线速服务任意多 worker。

3实验结果：解耦比堆带宽更值

原型用 Xilinx U50 FPGA 做 SmartNIC，8 台单 A100 机器 + 1 台 PS，100Gbps 网络。

⚠ 关键反直觉

ZeRO-Inf+MPS 和 ZeRO-Inf+Preemp 这两种「理论上消除了 SM 争用」的优化，吞吐几乎一样（差 0.1%–0.4%），且都只有 DisDP 的 ~33%。这证明：计算-通信干扰的根因是 GPU SM 争用 + 显存带宽争用叠加，只解一个不够，必须把通信整个搬出 GPU。

消融：① SmartNIC 卸载贡献 1.58×（大 batch 下计算与通信时间相当，重叠收益最大）；② 多对一协议贡献 1.10×（PS 不再 colocated，反向通信量降）；③ 步骤中心流水线贡献 1.10–1.17×（让 PS 不成瓶颈）。三者叠加，缺一不可。

4权衡、局限与启示

代价 · 额外硬件

每张 GPU 要配一块 FPGA SmartNIC（U50），还要一台 SmartSwitch + 一台专用 PS。虽然总 capex 只有 DGX 的 60%，但部署门槛比纯 GPU 集群高 —— 需要可编程交换机和 FPGA 开发能力。

代价 · SmartNIC DMA 弱

U50 的 DMA 能力（outstanding PCIe transactions）比 CX-5 NIC 弱，2 GPU 无并发 GEMM 时 DisDP 反而比 NCCL AllReduce 慢 28%。需要更强的 SmartNIC 才能全面追平。

局限 · U50 算力

FPGA 的 collective 处理模块资源占用受 U50 规模限制，更复杂 collective（如 TP 的 AllReduce）是否能在单块 FPGA 线速处理，论文未充分讨论。

启示 · 解耦 > 堆带宽

最深刻的结论：在 100Gbps + 全解耦下，micro-batch≥16 时计算时间盖过通信，100Gbps 够用，不必上 NVLink。慢网+专用卸载硬件，比快网+GPU 兼职更经济。
