DualPace：让 CPU 解码不再等 GPU 开窗

把 KV cache 放到主机内存、在 CPU 上算 decode attention，是突破 HBM 容量限制的常见做法。但在 NEO 这类系统里，CPU 只是 GPU 流水线中的一个阶段：CPU 上的请求能不能前进，取决于 GPU 调度器这一轮有没有给它留出合适的重叠窗口。浙江大学宁波全球创新中心的这篇论文把这种耦合叫做 GPU-gated CPU offloading，并给出 DualPace：GPU 和 CPU 各有一个独立调度的引擎，各自管队列、时钟和 KV；CPU 引擎用 AMX 跑 BF16 稠密算子，批次较大时再按需把稠密阶段借给 GPU 执行（Dense Assist）。口号是「调度上解耦，执行上合作」。在 Azure-Conversation 负载上，DualPace 的可持续请求率比 NEO 高 6.9–43.2%，比 vLLM 高 11.5–90.6%。

① GPU 门控的 CPU 卸载

LLM 服务要同时控制两种延迟：首 token 延迟（TTFT）和生成过程中的 token 间隔（ITL）。continuous batching 能摊薄 GPU 执行成本，但并发上限由 HBM 决定：KV cache 随序列长度和批大小一起增长，长上下文或高负载下会占满显存。PagedAttention 减少了碎片，但没有去掉容量上限。

服务器的主机内存通常比 HBM 大得多，CPU 也越来越强。Intel AMX 提供高吞吐的 BF16 矩阵运算，让主机有可能成为一个计算层，而不只是 KV 的溢出空间。FlexGen、FastDecode、NEO 等系统已经在用这个思路：把请求的 KV 放在主机内存，在 CPU 上执行依赖 KV 的 attention，稠密阶段仍留在 GPU 上。

论文的观察是：这些系统扩大了 KV 容量，却没有让主机成为一个能自主推进的服务层。以 NEO 为例，它只在预测的 CPU attention 时间能被另一个子批次的 GPU 工作盖住、且整条流水线预计比纯 GPU 更快时，才把 CPU attention 纳入本轮。这些条件保证 CPU 不会拉长 GPU 关键路径，但也意味着 CPU 能做有用的工作，却不能决定自己的请求什么时候前进。

Figure 1 的现象：Llama-3.1-8B、一张 RTX 4090、12 个 Xeon Silver 4510 物理核，回放 2,000 条 Azure-Conversation 请求。DualPace 的 CPU 侧累计解码 token 曲线持续上升；NEO 的曲线一段一段地前进，中间夹着明显的平台期（放大图里有一段持续数秒的停顿）。约 600 s 之后 NEO 的 CPU 侧曲线完全变平，而它的总 token 数仍在上涨，说明此时只有 GPU 在干活。负载升高时，这些停顿直接反映为更高的 P99 ITL，尽管主机内存里仍驻留着待解码的请求。

所以瓶颈不只是主机内存容量或 CPU 算力，而是 CPU 上的请求没有独立的调度权。论文据此提出的设计原则是：把「在哪执行」和「谁来决定什么时候执行」分开。已有系统大多只决定前者，后者仍交给 GPU；DualPace 把两者都解耦。

② 为什么 decode 可以放到 CPU 上

论文先把一次前向拆成几个阶段。prefill 的输入是 $[B, L, H]$，decode 的输入是 $[B, 1, H]$：

  • pre-layer：embedding；
  • 每层：pre-attention（LayerNorm、QKV 投影、RoPE）→ attention → post-attention（O 投影、残差与 LayerNorm、FFN 的 gate/up、SiLU、down、残差）；
  • post-layer：最后的 LayerNorm、LM head、采样。

其中只有 attention 依赖历史 KV，其余都是与上下文长度无关的稠密算子。KV 放在主机内存时，有两种做法：

做法每层跨 PCIe 的数据量说明
把 host KV 搬回 GPU 算 attention$\Theta(BLH)$随上下文长度 $L$ 增长，PCIe 很快成为瓶颈
在 CPU 上算 attention$\Theta(BH)$只交换 Q 和 attention 输出，与 $L$ 无关

所以 KV 放在哪里，attention 就应该在哪里算。剩下的问题是：稠密算子要不要也放到 CPU 上？论文引用的测量给出了几个关键数字：

  • Sapphire Rapids 在 GEMV 上能达到 H100 的 15–35%，在 GEMM 上只有 4–11%。decode 的稠密算子在批次小时接近 GEMV，批次大时才变成 GEMM。
  • CPU 上的 PagedAttention 在 $B=1$ 时与 GPU 相当，批次较大时差距在 10× 以内。attention 本身是带宽受限的，CPU 的内存带宽差距没有算力差距那么大。
  • AMX 的 BF16 峰值在 Sapphire Rapids 上约 20 TFLOPS，在 Granite Rapids 上约 40 TFLOPS，分别是 AVX512 的 4.5× 和 9×。
  • 在论文的 4090 平台上，用 AVX512 跑 QKV/FFN 比 GPU 慢约 100×；换成 AMX（oneDNN BF16）后差距缩到约 10×。
这组数字决定了 DualPace 的形状：AMX 让 CPU 在小批次 decode 时能独立跑完整个前向，而不必每层都等 GPU 算稠密部分；但批次一大，稠密 GEMM 在 CPU 上仍然慢一个数量级，这时把稠密阶段临时交给 GPU 更划算。前者对应「调度上解耦」，后者对应「执行上合作」。

NEO 的做法是只把 attention 放到 CPU，稠密阶段全在 GPU 上。这样 CPU 上的请求每一层都要经过 GPU，GPU 调度器自然掌握了它们的节奏。下一节看这种设计具体怎样导致停顿。

③ NEO 的非对称流水线

NEO 把一轮迭代的请求分成两个子批次（下标 0、1 是子批次编号，不是层号）：

  • 子批次 0：所有 prefill、GPU 驻留的 decode，以及挑选出来的一部分 CPU 驻留 decode；
  • 子批次 1：其余的 CPU 驻留 decode。

两个子批次的 pre/post-attention 都在 GPU 上跑，CPU 只做主机 KV 上的 attention，所以激活值每一层都要跨一次 CPU–GPU 边界。NEO 让一个子批次的 CPU attention 与另一个子批次的 GPU 工作重叠。记 $T^{\mathrm{lin}}_j = T^{\mathrm{pre}}_j + T^{\mathrm{post}}_j$ 为子批次 $j$ 的 GPU 线性阶段时间，$T^{\mathrm{ga}}_0$ 为子批次 0 的 GPU attention 时间，$T^{\mathrm{ca}}_j$ 为 CPU attention 时间。两个重叠区要求：

$$T^{\mathrm{lin}}_0 \ge T^{\mathrm{ca}}_1, \qquad T^{\mathrm{lin}}_1 + T^{\mathrm{ga}}_0 \ge T^{\mathrm{ca}}_0 \tag{1}$$第一式：子批次 0 的线性工作要盖住 CPU Attention 1；第二式：子批次 1 的线性工作加 GPU Attention 0 要盖住 CPU Attention 0。

NEO 逐个试探性地加入 CPU decode 请求，只要任一条件的预测余量变负就把它撤出。即使两个条件都满足，也只有在预测请求率高于纯 GPU 执行时才启用这条流水线。CPU 工作只在 GPU 这一轮提供了足够长、且对吞吐有利的重叠窗口时才被接纳。

停顿从哪里来

关键在两边时间的增长方式不同。一个 prefill 给 GPU 线性阶段贡献很多行（整段 prompt），一个 decode 只贡献一行。于是：

  • prefill 多时，$T^{\mathrm{lin}}$ 长，窗口宽，CPU decode 能挤进来；
  • prefill 少、decode 多时，$T^{\mathrm{lin}}$ 变短，而 $T^{\mathrm{ca}}$ 要扫描 CPU 请求不断累积的 KV 历史，越来越长；
  • 随着 prefill 到达情况和 KV 长度变化，式 (1) 在可行和不可行之间反复切换，CPU 侧进度呈突发状；
  • prefill 排空后，纯 decode 的迭代再也提供不了足够的重叠，CPU 侧进度停在一个平台上。

论文的结论是：限制 NEO 的不是 CPU 的能力，而是 GPU-gated progress。CPU 驻留请求只能在 GPU 调度器给出合适窗口时前进。下面的动画按这个机制示意一轮轮迭代里窗口的开合。

④ 两个引擎、各自调度

DualPace 的架构（论文 Figure 5）是一个 LLMEngine 下面挂两套独立的东西：GPU Scheduler 和 CPU Scheduler，各自有一个 executor coordinator，下面是各自的 worker（持有模型分片和 KV cache），两边通过 PCIe 和共享内存连接。

两个引擎各有自己的请求队列、调度时钟和 KV 管理器。任意时刻，每个请求只归一个引擎所有：

  • GPU 引擎拥有所有 prefill 和 GPU 驻留的 decode，管理 HBM 上的 KV；
  • CPU 引擎拥有 CPU 驻留的 decode，管理主机内存里的 KV。

和异构流水线不同，这里没有全局迭代屏障，两个批次不必同时开始或结束。所以即使当前 GPU 批次没有合适的重叠窗口，CPU 驻留请求也能继续解码。这是解决 ① 中停顿的直接手段。

驻留由 GPU 调度器在 prefill 时决定

所有请求都从 GPU 引擎进入，因为 DualPace 把每个 prefill 都放在 GPU 上算。对每个新请求，GPU 调度器决定它 prefill 之后 KV 放在哪：

路径做法
Prefill-to-GPU在 GPU 上算 prompt，KV 留在 HBM，之后加入 GPU decode
Prefill-to-CPUHBM 放不下时，预先保留最终的 CPU KV 块，GPU 上只用逐层的临时 staging 缓冲；每层算出 K/V 后异步拷到预留的主机块，尽量与后续 GPU 计算重叠

已有的 decode 请求也可以换驻留位置。HBM 紧张时，GPU 调度器选一个 GPU 驻留请求 swap-out：保留对应的主机块，把已经生成的 KV 拷过去。拷贝完成之后，这个请求才对 CPU 调度器可见。反过来，HBM 宽裕时可以把 CPU 驻留请求 swap-in 回来。

迁移最小化

两个引擎独立组批，但迁移把 HBM 和 DRAM 的分配耦合在了一起。单独调度两边可能把主机内存超额分配；过于积极的迁移又会让请求在设备间来回搬，浪费 PCIe 带宽。DualPace 的原则是请求尽量留在当前引擎：

  • 定义请求 $r$ 的 finish-peak 足迹 $\hat{b}_r$：它在完成前可能需要的最多 KV 块数。
  • swap-out 只在 HBM 装不下 GPU 驻留请求下一个 token 的 KV 增长时触发。
  • swap-in 之前，GPU 调度器把 $\hat{b}_r$ 加进 HBM 准入预算，只有它和现有 GPU 请求的足迹一起放得下才执行。这样换回来的请求能一直留在 GPU 上直到完成，避免短命迁移和驻留震荡。

按 finish-peak 而不是当前块数做准入是偏保守的：请求可能提前结束（遇到 EOS），预留的空间就浪费了。论文没有讨论 $\hat{b}_r$ 在输出长度未知时具体怎样估计（例如是否取 max_tokens 上限），本文推测是按请求声明的最大生成长度计算。

⑤ KV 安全包络与迁移预留

主机内存是一个有限的执行层，不是无底的溢出缓冲。如果没有协调的准入，GPU 调度器可能不断把 prefill 导向 CPU 内存：短期内 TTFT 好看，但最终会耗尽两类空间，一是正在运行的 CPU decode 继续增长要用的空间，二是将来 GPU 驻留请求被驱逐时要落脚的空间。DualPace 跟踪四项 CPU KV 义务，都以物理 KV 块计：

$$B^{C}_{\mathrm{used}} + B^{C}_{\mathrm{planned}} + B^{C}_{\mathrm{growth}} + B^{C}_{\mathrm{migration}} \le B^{C}_{\mathrm{capacity}} \tag{2}$$四项依次是：已经落地的 CPU KV；本轮已决定但还没落地的分配（Prefill-to-CPU、立即 swap-out）；CPU 运行队列的剩余增长；为将来可能被驱逐的 GPU 请求预留的位置。

增长项对 CPU 运行队列 $\mathcal{Q}^{\mathrm{run}}_C$ 里的每个请求累加「到峰值还差多少」，$b_r$ 是当前块数：

$$B^{C}_{\mathrm{growth}} = \sum_{r \in \mathcal{Q}^{\mathrm{run}}_C} \max\{\hat{b}_r - b_r,\ 0\} \tag{3}$$CPU 上已在跑的请求，保证它们都能跑完。

迁移项是两个调度器之间的桥。设 $\mathcal{Q}_G$ 为本轮决策之后的 GPU 所有权队列（按驱逐优先级排序），$B^G_{\mathrm{capacity}}$ 为 GPU KV 容量：

$$B^{G}_{\mathrm{peak}} = \sum_{r \in \mathcal{Q}_G} \hat{b}_r \tag{4}$$GPU 上所有请求都长到峰值时需要的总块数。

若 $B^G_{\mathrm{peak}} > B^G_{\mathrm{capacity}}$，调度器从驱逐优先级的尾部开始扫描 $\mathcal{Q}_G$，把扫到的请求的 $\hat{b}_r$ 从 GPU 峰值里移到 $B^C_{\mathrm{migration}}$，直到剩下的部分放得进 HBM。这一项代表「目前归 GPU 所有、但不保证能一直留在 HBM」的 KV。

四项如何连起两个调度器：Prefill-to-CPU 候选会增加 $B^C_{\mathrm{planned}}$；Prefill-to-GPU 候选会延长 $\mathcal{Q}_G$，可能增加 $B^C_{\mathrm{migration}}$。两种去向都只在式 (2) 仍成立时才被接纳。CPU 调度器在接纳新的 CPU decode 时，把 $B^C_{\mathrm{migration}}$ 当作不可用容量。于是两个引擎不需要同步迭代，也不会互相把对方的退路吃掉。

每轮调度的细节（附录 A）

GPU 引擎每轮按这个顺序做：

  • 回收已完成的 Prefill-to-CPU 传输，等待上一组拷贝结束；
  • 恢复「下一个 token 在 HBM 上放得下」：驻留 decode 优先，从队尾驱逐，跳过主机上也放不下的牺牲者；驱逐不了就只跑放得下的子集，部分驱逐时本轮只做迁移；
  • 发布 $B^C_{\mathrm{migration}}$；
  • 接纳 GPU decode。若 CPU 批次已满、CPU 队列非空且本轮没有 swap-out，先做一次 FIFO 的提前 swap-in，再考虑 prefill；
  • 按 FIFO 接纳 prefill，受行数、token 数和 staging 上限约束。一轮里一旦出现第一个 Prefill-to-CPU，同轮后续的 prompt 也都去 CPU；
  • 用剩余 HBM 再做一轮 swap-in，或者给正在 CPU 上跑的请求打上延迟 swap-in 标记；
  • 提交迁移（先目的端后源端），最多跑一个 GPU 批次。

CPU 引擎每轮：快照预算；按 FIFO 保留运行中请求，被标记 swap-in 的请求让到前面，放不下的请求移到队首，此后不再接纳更老的等待请求；接纳已就绪的前缀；等待队首请求的就绪事件、从不跳过它，若只是被预留卡住就让出；只分配下一个 token 的块，跑一个批次。

论文强调的性质有三条：每个请求只有一个所有者；背压是局部的，主机内存紧张永远不会阻塞 GPU 上可运行的子集；迁移预留保证驱逐路径一直可用。

⑥ Dense Assist：执行上合作

单纯的双引擎设计会碰到一个两难。CPU 拥有的 decode 每个阶段都在本地跑，能保住独立进度，但 post-attention 的稠密算子和输出头会随 CPU 批次变大越来越贵。反过来，如果把请求交回 GPU 引擎做稠密计算，又重新依赖 GPU 侧的准入。DualPace 的办法是：CPU 引擎保留请求所有权和调度权，GPU worker 只在明确的模型阶段边界上执行选定的稠密阶段。

这就是 GPU Dense Assist。它是一个算子级请求：CPU worker 先独立把批次推进到某个协助边界，只把这个边界需要的张量发给 GPU；GPU worker 执行请求的 post-attention 阶段或模型 post-layer，把结果返回给同一个 CPU 批次。这些请求从不进入 GPU 调度器的队列，KV 留在主机内存，也不占用任何长期的 GPU KV 块。GPU 协助只是加速稠密计算，不改变驻留位置，也不转移调度权。

哪些阶段永远在 CPU 上

pre-layer，以及每层的 pre-attention 和 attention，固定走 CPU 路径。这段本地前缀是调度解耦的关键：CPU 引擎可以不等 GPU 调度器就接纳并启动一个批次。之后的 post-attention 和最后的 post-layer 不访问 KV，所以可以在本地跑，也可以走 Dense Assist，不影响所有权和 KV 驻留。

选哪条路由两个批大小阈值决定：$P$ 是 post-attention 能在 CPU 本地跑的最大批，$F$ 是 post-layer 能在 CPU 本地跑的最大批。对大小为 $b$ 的 CPU decode 批次：

$$\pi_{P,F}(b) = \begin{cases} \text{Full-CPU}, & b \le F \\ \text{Split-Final}, & F < b \le P \\ \text{Fused-Assist}, & b > P \end{cases} \tag{5}$$合法设置为 $(P, F) = (0, 0)$ 或 $0 \le F < P$。
模式post-attention（每层）post-layer（LM head）每个前向的 assist 次数
Full-CPUCPUCPU0
Split-FinalCPUGPU1
Fused-AssistGPUGPU（与最后一层合并）$N$

为什么单独把 LM head 拿出来？论文没有展开。本文推算：Llama-3.1-8B 的 LM head 权重是 $128256 \times 4096 \approx 5.3$ 亿参数，而单层 FFN（gate、up、down）约 $3 \times 4096 \times 14336 \approx 1.8$ 亿，LM head 是整个前向里最大的单个 GEMM，批次一大最先在 CPU 上变贵。

不抢占的阶段边界优先级

GPU 主执行不再是一次完整前向，而是一串 FIFO 阶段任务，在 pre-layer 之后、每个 transformer 层之后、post-layer 之前设安全边界。DualPace 从不抢占正在跑的 CUDA kernel，也不取消已提交的工作。每到一个边界，GPU worker 先处理已就绪的 Dense Assist，再取下一个主阶段。这样 assist 的响应时间最多是「当前阶段跑完」，GPU 执行顺序仍是确定的。

式 (5) 也说明了什么时候这套协调可以不要：设 $C$ 为 CPU 引擎能组出的最大 decode 批次，若 $C \le F$，所有可达批次都走 Full-CPU，Dense Assist 静态不可达。这时 DualPace 改用整前向的 GPU 主路径，去掉逐层的 assist 检查，两个引擎完全独立运行。

4090 平台上的实际阈值是 $(P, F) = (32, 16)$（来源见下一节）：CPU 批次 ≤ 16 全部本地跑；17–32 只把 LM head 交给 GPU；超过 32 每层的 post-attention 都交给 GPU。

⑦ 阈值从离线 profiling 来

DualPace 有三个控制量要在部署前定下来：Dense Assist 的路由阈值 $(P, F)$、GPU 每轮的批 token 上限、CPU decode 的批大小上限。三者都靠在目标机器上离线 profiling 得到，不需要在线调参。

路由阈值：不只看 CPU 时间

如果只追求 CPU 批次最快，答案几乎总是「能交给 GPU 就交给 GPU」。但每次 assist 都会占用 GPU 主路径的服务时间，挤掉 GPU 驻留请求的进度。所以 profiler 给每条路由 $r$ 一个综合代价：

$$S_r(b) = T^{\mathrm{CPU}}_r(b) + \lambda_{\mathrm{GPU}}\, D^{\mathrm{GPU}}_r(b) \tag{6}$$$T^{\mathrm{CPU}}$ 是 CPU 推进这个批次可见的时间；$D^{\mathrm{GPU}}$ 是 Dense Assist 从 GPU 主路径挤占的服务时间。论文取 $\lambda_{\mathrm{GPU}} = 1$。

两项都按 $N$ 层展开，$t_p$、$t_l$ 是 CPU 本地的 post-attention 和 post-layer 时延，带横线的是「等 GPU 返回」的时延（含 Assist Buffer 读写和控制面等待），$d$ 是 GPU 侧被占用的时间（CUDA 执行加 launch/收尾）：

$$\begin{aligned} T_{\mathrm{full}} &= N t_p + t_l, & D_{\mathrm{full}} &= 0 \\ T_{\mathrm{split}} &= N t_p + \bar{t}^{S}_l, & D_{\mathrm{split}} &= d^{S}_l \\ T_{\mathrm{fused}} &= (N-1)\bar{t}_p + \bar{t}^{A}_l, & D_{\mathrm{fused}} &= (N-1) d_p + d^{A}_l \end{aligned} \tag{7–8}$$Fused-Assist 的每层开销会被乘上 $N-1$，这是它只在大批次才划算的原因。

目标函数是在候选批大小集合 $\mathcal{B}$ 上的平均代价：

$$J(P, F) = \frac{1}{|\mathcal{B}|} \sum_{b \in \mathcal{B}} S_{\pi_{P,F}(b)}(b) \tag{9}$$

Algorithm 1 的搜索过程：

  • 候选集 $\Theta = \{(0,0)\} \cup \{(P,F) \mid P \in \mathcal{B},\ F \in \mathcal{B} \cup \{0\},\ F < P\}$；
  • 对每个候选算 $J$，取最优值 $J^*$，保留 $J \le (1+\varepsilon) J^*$ 的近优集 $\Theta_\varepsilon$；
  • 在 $\Theta_\varepsilon$ 里优先选平均 assist 调用次数最少的（Full 记 0 次、Split 记 1 次、Fused 记 $N$ 次），再比代价，最后比 $P$、$F$。

4090 平台上精确最优是 $(32, 0)$，即 32 以下全部 Split-Final。取 $\varepsilon = 0.25\%$ 后选中 $(32, 16)$，代价只高 0.070%，但 16 以下的批次完全不碰 GPU。这个容差的意义是：几乎同样快时，宁可少一次跨设备握手。

GPU 批 token 上限：1,024

Figure 7(c) 显示，不同 $(B, L)$ 形状的单层吞吐都随总 token 数 $n = BL$ 收敛到相近的平台；过了平台，再塞进可选的 prefill 或 swap-in 只会拉长这一轮。做法借鉴 chunked prefill：profile 一个 decoder 层，按 $n$ 分组取均值，做单调非减的最小二乘拟合（保序回归），用最后 $K = 5$ 个点估计平台值，取吞吐进入平台 $\delta = 1\%$ 以内的最小 $n$。结果是 1,024（Figure 7(d)，$n$ 从 $2^6$ 到 $2^{14}$，平台约 30 万 tok/s）。

CPU decode 批上限：256

用真实权重的单个 decoder 层，在上下文 64/128/256/512 下扫批大小。吞吐在批 256 附近达到峰值（约 1.5 万 tok/s），之后 AMX 和内存带宽饱和，不再增长。论文强调这个上限只是建议值，面向时延的部署可以取更小的批。

实现要点（§5）

原型用 Python/PyTorch 写，前端是 FastAPI/Uvicorn，结构参考 DistServe。LLMEngine 里跑三个 asyncio 任务：GPU 引擎、CPU 引擎、完成处理，各自按「调度、提交、等待、应用」循环，没有共享屏障。worker 是 Ray actor，但 RPC 只用于启动和关闭；运行时通过固定布局的共享内存控制块通信，CPU KV 和 assist 激活各有一个共享池，并注册给 CUDA，H2D/D2H 拷贝不经过 Ray 对象存储的序列化。assist 握手是 CPU-Ready → GPU-Running → GPU-Done 三态；GPU worker 用 CUDA event 跟踪当前任务、协作式让出，不做全设备同步。CPU 侧算子沿用 vLLM 的 packed CPU-linear 组织，稠密部分用 oneDNN BF16，attention 用 AVX512-BF16 + OpenMP 的 PagedAttention。

⑨ 局限与没回答的问题

论文没有单独的局限章节，只在 Code 负载的分析里划出了适用边界。下面是读完后觉得值得补充的几点。

  • 收益依赖负载形状。Code 负载上 vLLM 在两个 Qwen3 配置里胜出。DualPace 扩的是 decode 层的容量，输出短、prefill 占主导时，这部分容量用不上。真实部署里 RAG、代码补全这类长 prompt 短输出的流量不少，标题里的 +90.6% 只对应 Conv 这类场景。
  • 吞吐换来的是更长的单 token 间隔。vLLM 的 P99 ITL 和 TPOT 都更低。DualPace 在同等 SLO 下能接更多请求，但每个跑在 CPU 上的请求都比在 GPU 上慢。对交互式应用，1.5 s 的 P99 ITL 目标偏宽松，收紧后优势会怎样变化，论文没有扫。
  • 大模型、强 GPU 上提升变小。8B / 4090 的 +43.2% 到了 14B、32B / H20 上降为 +6.9%、+18.1%，ITL 目标下从 +50.5% 降到 +7.3%。H20 的算力被削减而 HBM 有 96 GB，多卡 TP 后 GPU 侧 KV 压力本就较小（本文推测）；换成 H100 这类算力更强、HBM 只有 80 GB 的卡，结果可能又不同。论文没有测 H100，也没有测 AMX 算力翻倍的 Granite Rapids。
  • 强依赖 AMX。整个「CPU 独立跑完整前向」的前提是 AMX 把稠密算子的差距从约 100× 缩到约 10×。AMD EPYC 和 Arm 服务器 CPU 没有 AMX，这套设计在那里是否成立是开放问题。
  • 代价权重没调。式 (6) 的 $\lambda_{\mathrm{GPU}}$ 固定为 1，等于假设 GPU 主路径上 1 ms 的损失和 CPU 批次上 1 ms 的损失等价。GPU 驻留请求更多或更少时，这个权重的最优值应该不同，论文没有做敏感性分析。
  • finish-peak 准入偏保守。按 $\hat{b}_r$ 预留空间，请求提前遇到 EOS 时预留就浪费了。论文没说明 $\hat{b}_r$ 在输出长度未知时怎么估计（见 ④），也没有量化预留空间的实际利用率。
  • 实验覆盖面窄。只有两条 Azure trace，各取前 2,000 个请求；消融和 assist 开销只在 4090 单平台上做；没有前缀缓存、没有投机解码等常见优化的组合实验。三个阈值都要在每个部署上重新 profile。
  • 原型是 Python 写的。调度循环、共享内存控制块和 assist 握手都在 Python/asyncio 里，空轮询每层 2–5 µs 的开销在更小模型或更快 GPU 上占比会更高。论文没有给出代码链接。

⑩ 一句话总结

NEO 这类 CPU 卸载系统让 CPU 只算 attention，CPU 驻留请求每层都要等 GPU 给出重叠窗口，prefill 一少就停顿；DualPace 借助 AMX 让 CPU 引擎独立调度、独立跑完整个 decode 前向，两个引擎各管各的请求和 KV，靠四项 KV 义务（used、planned、growth、migration）的安全包络协调准入和迁移，批次变大时再把 post-attention 或 LM head 以算子级 Dense Assist 的方式临时交给 GPU，所有阈值由离线 profiling 确定；在 Conv 负载上可承受请求率比 NEO 高 6.9–43.2%、比 vLLM 高 11.5–90.6%，代价是单 token 间隔高于纯 GPU 的 vLLM，且在长 prompt 短输出的 Code 负载上不一定胜过 vLLM。
