CUDA 软件栈分层动画：从一行 PyTorch 到 GPU，再到一次 LLM 推理

读 GPU 性能相关的资料时，cuBLAS、cudart、libcuda、nvidia.ko、PTX、SASS、Fabric Manager、DCGM 这些名字会同时出现，却很少有人讲清楚它们各在哪一层、谁调用谁。下面这张图把它们放进同一个分层结构里。点任意一个方块能看到它是什么、对应哪个文件或命令、你什么时候会碰到它；上方的 7 个场景可以单步播放，跟着一次调用从上走到下。

图怎么读

左侧主栏从上到下是一次调用经过的层次：

  • 用户态（你的进程里）：你的代码和 Python 库 → PyTorch 的 ATen 调度器或 torch.compile → cuBLAS / cuDNN / NCCL 等数学与通信库 → CUDA Runtime（libcudart.so）→ 用户态驱动 libcuda.so 和 NVML。
  • 系统调用：/dev/nvidia* 设备文件，用户态和内核之间只通过它们上的 ioctl 和 mmap 交流。
  • 内核态：nvidia.ko 管显存、页表和命令通道，nvidia-uvm.ko 管统一内存的缺页迁移。
  • 硬件：SM、HBM 显存、NVLink / NVSwitch。

右侧一栏是不在调用路径上、但同样会碰到的东西：编译工具链（nvcc、Triton、PTX、SASS、fatbinary）和后台常驻服务（nvidia-persistenced、Fabric Manager、DCGM）。

7 个场景

场景讲什么
① 逐层认识自上而下把每一层过一遍，先建立整体印象。
② 一次矩阵乘torch.matmul 怎么变成 cuBLAS kernel、经驱动写进命令缓冲区、由 GPU 执行。
③ 编译：PTX 与 SASSnvcc 产出的 fatbinary 里有什么，驱动什么时候直接用 SASS、什么时候 JIT 编译 PTX，「no kernel image is available」从哪来。
④ torch.compileDynamo → AOT Autograd → Inductor → Triton 的生成链路。
⑤ 容器与版本号镜像里装的是 Toolkit，宿主机提供驱动；nvidia-smi 里的「CUDA Version」是驱动支持的上限。
⑥ 常驻服务persistenced、Fabric Manager、DCGM 各管什么，一台服务器上谁装什么。
⑦ 一次 LLM 推理以 8 卡张量并行的 70B 模型为例：服务启动、分词调度、Prefill、all-reduce、Decode、CUDA Graph、采样与流式返回、连续批处理、KV cache 卸载，最后是按现象排查瓶颈的对照表。

最常用的几条结论

  • 驱动只能比 Toolkit 新，不能旧：CUDA 12.x 需要 R525 以上的驱动，CUDA 13 需要 R580 以上。nvidia-smi 显示的 CUDA 版本是驱动能支持的最高版本，不是装了哪个 Toolkit。
  • 容器只带用户态：镜像里放 cudart、cuBLAS、PyTorch；libcuda.so 和内核模块来自宿主机，由 NVIDIA Container Toolkit 在启动时挂进来。
  • Fabric Manager 版本必须和驱动完全一致，否则有 NVSwitch 的机器上 CUDA 初始化会失败。
  • 推理的两个阶段瓶颈不同：Prefill 受算力限制，决定首 token 延迟；Decode 受显存带宽限制，决定之后每个 token 的间隔。
模型是示意：方块之间的关系按公开文档整理，版本号和带宽数字是写作时的量级，具体以你所用版本的官方文档为准。
