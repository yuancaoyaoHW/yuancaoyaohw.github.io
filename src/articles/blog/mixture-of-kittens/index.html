Mixture-of-Kittens

Cursor 开源的 NVL72 MoE 训练 megakernel：把 dispatch / combine 通信直接焊进计算 kernel，单 kernel 完成前向与反向

MoE 层占 Composer 训练端到端时间的 一半以上。MoK 用"通信方向重选 + 计算通信同 kernel 融合 + 零 CPU-GPU 同步"三个动作，把 MoE 层吞吐推到公开基线的 2.37×（MXFP8 前向），端到端训练提速 1.41×——并保持完全确定性。

GB300 NVL72 专属 MXFP8 fwd 2.37× 端到端 1.41× tokens/s

为什么：MoE 层是训练的瓶颈

DeepSeek-V3 风格的 MoE 层（1 个共享 expert + 数百个路由 expert，如 GLM、Qwen、Kimi K2.7、DSV 都长这样）是整个训练栈里最"贵"的一层。每个 token 先进 router 投影选 top-k expert，再被送往对应 expert 的 FFN（up/gate 投影 → SwiGLU → down 投影），最后按 router 权重加权合并。在 expert parallelism（EP）下，expert 权重被切到 64 个 rank 上，token 必须在 GPU 之间来回搬运两次：dispatch（把 token 送到持有其 expert 的 rank）和 combine（把结果送回原 rank）。

关键事实：通信耗时和计算同数量级。传统实现（NCCL / DeepEP）把 dispatch、FFN、combine 当三个独立算子顺序执行，通信期间 GPU 空转。Cursor 的实测：MoE 层占端到端训练时间超过 50%，而其中通信已经从次要成本变成了主导成本——过去一年他们写过 MXFP8/NVFP4 训练 kernel、搞过 warp decode 推理，但都只优化了计算侧，通信没动。

核心判断： MoE 层的性能上限不再由 GEMM 决定，而由"token 怎么在 72 张 GPU 之间流动"决定。要继续压，必须把通信当成 kernel 的一等公民来设计，而不是调库。

NVL72 改变了问题形态

从 DGX 换到 GB300 NVL72，问题的约束条件变了两个，MoK 的设计几乎全部由这两个变化驱动：

  • 72 个 GPU 在同一个 NVLink 域内。NVL72 是一个机架 = 一个多节点 NVLink 域，任何两个 GPU 之间都有 NVLink（5 代，1.8 TB/s 双向）。这意味着通信不再需要经过 InfiniBand，可以做细粒度的计算/通信重叠——把通信切成小片掺进计算流水线里，而不必像 IB 时代那样攒大批量。
  • 集成 Grace CPU 相对 GPU 慢得多。Cursor 的 trace 显示 GPU kernel 经常被 CPU 侧工作（日志、推送训练指标）拖住——同一个训练栈在 DGX（Intel CPU）上没这问题。任何一次 CPU-GPU 同步，GPU 流都会追上 CPU 然后干等。所以设计约束是：尽量让 GPU 永远不回头等 CPU。
设计原则由此确立： 单 kernel 内完成全部 MoE 通信 + 计算；通信方向、调度、信令全部在设备端自洽；CPU 只负责"一键启动"。MoK 的每个技术决策都能追到这两条约束之一。

亮点一：pull/push 通信方向——被默认选项掩盖的三个 trade-off

把 token 从 GPU A 送到 GPU B，有两种力学：push（持有 token 的 GPU 主动把数据写进远程 GPU 的缓冲区）和 pull（需要 token 的 GPU 主动从远程 GPU 的缓冲区读）。DeepEP 等主流实现默认 push，理由是“push 协议开销小、更容易打满链路”。MoK 的观察是：push/pull 各有 trade-off，且方向选择直接影响调度、带宽、信令三个层面——全都选对了才对。

维度一：调度（schedule）复杂度

要让 dispatch 期间所有 NVLink 通道都忙、每个 rank 收到的 token 按 local expert 顺序排列、且零本地拷贝，需要一张排列表。push 的排列表是 {src_index, dst_rank, dst_index} 三列：行序决定发送顺序，必须让 dst_rank 轮转（保持所有链路饱和）、dst_index 在所有源之间均匀交错且按目标 rank 的 expert 序递增——构建这张表需要多趟排序，且每个 rank 的表都要考虑其他所有 rank（两个源不能写同一 dst_index）。

pull 的排列表退化到两列 {src_rank, src_index}，行号直接就是本地目标缓冲区的 token 下标——不需要排序：遍历 router 结果，凡是路由到本 rank 的 token，记下它的源 rank 和源下标即可。实测这个 schedule kernel 只占 MoE 总运行时间的 <3%，且完全在设备端执行。

代码佐证（scheduler.cuh）： 三阶段实现——count（统计每个 peer→local expert 的 token 数）→ pad（每个 expert 按 EXPERT_PADDING=256 向上取整，给 grouped GEMM 做行对齐）→ schedule（把 token 写入其 expert 的 256-padded 段，段内按 peer rank 交错）。容量用 {trap;} 显式崩溃而非静默越界，无效槽位填 -1 哨兵。整张表只有几 MB，且一次构建、四个方向复用。

维度二：NVLink 带宽利用率

NVLink 协议元数据（源/目的、ACK）与负载争抢链路。NCU 微基准（256×256 BF16 tile）显示：push 总字节数更少（少约 12.4 KB），但几乎全走单方向；pull 总字节更多，但元数据双向分摊。而 NVLink 的每个方向是独立车道，要打到 1.8 TB/s 必须双向全流。MoE 的 dispatch/combine 每次传输只有几 KB 且方向不平衡，正是最吃亏的场景——实测在 expert 负载不均衡时，pull 的 NVLink 带宽利用率比 push 高 29%。

维度三：信令（signalling）

GPU 必须知道"数据到了"才能开始算。push 的完成信号必须跨 GPU 传递：一个 rank 要等多达 71 个 peer 的信号 + 一次全机架 memory fence 才能开始 grouped GEMM——数据已经躺在目标缓冲区里，但谁都不敢用。多节点微基准：push dispatch 信令延迟 103 µs，pull 只要 18 µs（5.8× 差距），在单 kernel 里反复累积非常致命。

pull 的妙处在于：发起方就是消费者——本地发一个 load，等数据到，立刻能用，同一个实体完成信令，开销不随 EP 度增长，跨 GPU 信令直接消失。

亮点二：重叠粒度 = 每个 GEMM 至少两个 wave

粒度是计算/通信重叠里最微妙的旋钮。太细（Comet 式：每次只发够一个 MMA 的 token，Blackwell 上 256 个）——tensor core 是深度流水、带宽优化的加速器，频繁的 barrier 等待让它永远喂不饱；太粗（DeepEP 式：攒几千上万个 token 一起发）——第一个 wave 到来前和最后一个 wave 的 combine 前，tensor core 都在干等。MoK 的答案：中间值，且量化成"两个 wave"。

一个 wave 是 GPU 上所有 SM 并发执行一轮 work。设 $T$ 为每次传输的 token 数（minibatch 大小），选让每个 expert grouped-GEMM 至少跑满两个 wave，理由有二：

  1. 一个完整 wave 就足以饱和 tensor core；
  2. 两个 wave 时，第二波的 MMA 与第一波的 epilogue 和依赖算子（SwiGLU、下一个 grouped GEMM）重叠，把 tail effect 摊掉。

Blackwell 上每个 SM 固定处理 $128 \times 256$ 的输出 tile（$K$ 为归约维）。设 $H$ 为隐藏维、$I$ 为 expert 中间维、$C$ 为 SM 数，则 up/gate 投影（互不依赖、可并行跑）要求：

$$T \ge \frac{2 \cdot C \cdot 128 \cdot 256}{H}$$

down 投影（无法与别的算子并行）更紧：

$$T \ge \frac{2 \cdot C \cdot 128 \cdot 256}{I}$$

取两者较大者。以 Composer 2.5 的基座 Kimi 2.5 为例（$H=7168, I=2048$，Blackwell $C=148$）：up/gate 侧要求 $T \ge 1354$，down 侧要求 $T \ge 4736$——取 4736。微基准结果与启发式吻合。minibatch 做成可调参数（推荐区间 2048–16384），跑 workload 前先扫一遍配置。

为什么"两个 wave"是物理直觉而非经验拍脑袋： 一个 wave 对应 tensor core 吞吐的饱和点，第二个 wave 是"免费"的——它不增加关键路径长度，只是让流水线在换挡时不停顿。少于两个 wave，SM 出现 partial wave（部分 SM 空转）；多于两个，通信粒度过粗、首尾等待变长。这是一个有明确拐点的优化问题。

亮点三：inter-SM 分工——把 GPU 内部切成"通信核"和"计算核"

粒度定了，还要决定谁在什么时刻干活。MoK 用 inter-SM overlapping：把 SM 分成两组——comm SMs 专职 dispatch/combine，comp SMs 专职 expert FFN，两组之间用本地 counter 互相发信号。这之所以可行，是因为 Blackwell 的 TMA（Tensor Memory Accelerator）让 不到 1/3 的 SM 就能打满 NVLink 带宽——大部分 SM 应该留给计算。

信令原语是手写 PTX：barrier_arrive 用 red.release.gpu.global.add 原子加，barrier_wait 用 ld.relaxed.gpu 轮询 + __nanosleep(16) 退避 + fence.acquire.gpu。release/acquire 语义保证"先写数据、后抬信号"的顺序，全部在设备端自洽，CPU 零参与。

前向编排：先 dispatch 全部，再 combine 与 FFN 交织

comm SMs 先把所有 minibatch 的 pull dispatch 全部做完（comp SMs 边等边把 shared expert 的 FFN 塞进空档），每凑满一个 minibatch 就向 comp SMs 发信号；comp SMs 原子地跑 MLP-SwiGLU；全部 down 投影完成后回发信号，comm SMs 开始 push combine。因为 dispatch 阶段攒了大量就绪信号，combine 能和最后一批 FFN 无缝衔接。

反向编排：dgrad 先行，wgrad 殿后

反向复杂在要支持 forward replay（见下一节）。MoK 的编排：comm SMs 先做 reverse-combine，comp SMs 跑 FFN 反向中的 3 个 dgrad GEMM + SwiGLU backward（排除 wgrad），完成后反向 reverse-dispatch。3 个 wgrad 被推迟到所有 minibatch 的 dgrad 结束之后，两个理由：

  • 重叠：reverse-dispatch 不依赖 wgrad，wgrad 可以跟最后几轮 reverse-dispatch 并行；
  • 数值：wgrad 的归约轴是 token 轴，整轴一次性累加能最小化数值误差。

comp/comms SM 比例前后向分别可调（默认 fwd 40 / bwd 28 个 comm SMs），因为前后向的通信/计算比不同。

亮点四：ring token buffer——用"逆序填环"消灭 CPU-GPU 同步

最后一块拼图是 MoE 的动态性：路由结果出来之前，谁也不知道每个 rank 会收到多少 token。业界两种处理都不可接受：token dropping（超出固定缓冲的 token 直接丢弃）伤训练质量；CPU-GPU 同步（把每 rank token 数送回 CPU，由 CPU 分配精确大小的缓冲）在 Grace CPU 上就是灾难——GPU 会被拖住等 CPU 回复。

MoK 的做法：macrobatch ring buffer——一块几百 MB 的固定大小环形缓冲，按 minibatch 粒度循环使用，不丢 token、不同步 CPU。实现的关键是跨环边界重叠：dispatch 往环的头部写，combine 从环的尾部读（同一块区域），合并上一 macrobatch 的 combine 与下一 macrobatch 的 dispatch 交织执行，边清边填，槽位尽快复用。代码里前向通信就是这个循环：

// 先单独 dispatch 最后一个 macrobatch
for (task < num_dispatch_tasks(num_macrobatches - 1)) dispatch(num_macrobatches - 1, task);
// 然后逆序：每轮 combine 当前 macrobatch + dispatch 前一个
for (macrobatch_idx = num_macrobatches - 1; macrobatch_idx >= 0; --macrobatch_idx) {
    combine(macrobatch_idx, ...);
    dispatch(macrobatch_idx - 1, ...);   // 同一批环槽位，先清后填
}

reversed ring：为什么前向要逆序消费

ring 是环，前向写 N 个 macrobatch 就要覆盖 N−1 次，被覆盖的激活在反向时必须 forward replay（重算）。replay 只需重算到 SwiGLU——反向只需要 down 的输入激活和输出梯度，不需要 down 的前向输出。但重算多少，取决于环里最后存了谁：

  • 正序填充：最后写入的是部分填充的最后一个 macrobatch（token 总数不是 macrobatch_size 整数倍时），环里有效的激活最少，反向要多 replay；
  • 逆序填充：最后写入的是满的 macrobatch 0——环要么全满、要么存的都是有效 token，反向直接从环里读最早的 macrobatch（backward 的第一个依赖），replay 量最小化。

代码佐证：反向 grid 里 replay 任务数精确等于 (num_macrobatches − 1) × (macrobatch_size / minibatch_size)——第一个 macrobatch 永远在环里现成可用，其余 N−1 个才需要 replay。若把 macrobatch_size 设到极大（如默认 131072，环只用一次），replay 归零，代价是显存。

环竞争的代价——一个必须防御的坑： dispatch 覆写的行可能还在被上一 macrobatch 的 GEMM 读。MoK 用 transfer_ready / buffer_ready 两级 counter 保护：dispatch 一个 macrobatch 前，必须等上一轮"读同一批槽位"的 GEMM 和 combine 全部完成（barrier_wait 按 minibatch 精确计数）。反向更甚——9 类信号量（router_weights_ready / d_y_routed_ready / d_hidden_ready / d_gate_up_ready / d_x_routed_ready / replayed_* 三件套 / routed_buffers_done）把 replay 流水线、dgrad 流水线、wgrad 流水线串成一张依赖网。这是全 kernel 最容易写错死锁的地方。

亮点五：MXFP8、确定性与 CLC——工程细节里的增量

MXFP8：量化成本被融合吃掉

MoK 训练用 MXFP8（更快且无数值问题），但shared expert 留在 BF16——实测影响训练稳定性。MXFP8 的额外成本是"进 tensor core 前必须量化"。MoK 把它拆成三份消化：权重用独立优化 kernel 预量化（mxfp8_quantize，留给 FSDP 等外部优化机会）；激活量化融合进 dispatch all-to-all、expert grouped-GEMM 和 SwiGLU——dispatch 每拉回一批 token 直接量化成 FP8 + block scale 双写（正常 + 转置两份，给 up/gate 和 down 两种 GEMM 用）。scale 计算用 cvt.rp.satfinite.ue8m0x2.f32（向上取整 + 饱和到有限值），倒数用 (254 − scale) << 23 直接拼出 float32，免除法。

确定性：bitwise identical

FP 运算顺序固定 → 相同输入产出逐位一致的输出，与硬件调度、指令发射顺序无关。这是给内部消融和 on-policy RL 后训练用的——实验可复现是强化学习实验的刚需。

CLC：megakernel 主动给别的活儿让位

megakernel 是 persistent kernel，独占 GPU 会挡住机架间的 FSDP all-gather（InfiniBand/RoCE 通信也需要 SM 干活）。MoK 用 Blackwell 的 CLC（Cluster Launch Control）——硬件原生的 work-stealing 机制：megakernel 的任务通过 CLC 调度，高优先级流上的 kernel 可以插队，megakernel 让位而不必等自己完全结束。代码里每个任务簇都带一个 SM 掩码 bitfield（0xFFFF0000），把部分 SM 显式空出来给 RDMA 通信。

难点：megakernel 为什么难写

读完亮点，值得停下来想清楚：这套东西的工程难度在哪？不是"多写几个 kernel"，而是把正确性建立在极细粒度的跨 GPU 时序之上。逐条拆：

1. 全局一致的调度：每个 rank 的表都要考虑所有 rank

schedule 表的下标交错规则（peer 均匀散布 + expert 序递增 + 256 对齐）依赖所有源 rank 的写入互不冲突——这是全局约束，不是本地约束。构建时任何两个源撞了同一个 dst_index，数据就静默损坏。MoK 用 {trap;} 把"超容量"变成显式崩溃、用 -1 哨兵标记无效槽位，把"可能错"变成"必须错"。容量估算用 schedule_capacity = num_local_tokens × topk × max(2, ceil(ep_size × 0.5))——训练初期 expert 负载极不均衡时建议把 multiplier 调到 1，后期再降回 0.5。

2. TMA 流水线的共享内存编排

每个任务簇在共享内存里手工规划布局：token chunks、FP8 tile、scale tile、转置 tile、router 权重缓存，全部用 tensor_allocator 在 227 KB 共享内存里按字节对齐分配（smem_base_addr 对齐到 1024）。GEMM 的 load/epilogue 流水深度（6/8 级）、combine 流水（7 级）、CLC drain（8 级）互相纠缠——动一个数字，共享内存就爆或流水就断。

3. 反向的依赖网：9 类信号量的正确性

反向同时跑三条流水线：dgrad（reverse-combine → 3 dgrad GEMM + SwiGLU bwd → reverse-dispatch）、replay（re-dispatch → gate/up → SwiGLU fwd，只到 SwiGLU 为止）、wgrad（3 个 GEMM，最后收）。任何两个阶段之间的信号量计数错误（required_count 算错一个 cluster 的贡献）都会死锁或竞态。计数器是全局内存整数，release/acquire 语义靠 PTX fence 保证，没有工具能帮你验证。

4. SM 分区的精确性

博客明确说：多流 + green contexts 分 SM 不可靠——"exactly as intended"做不到。所以 MoK 用软件分区：任务按 cluster 索引静态分配，comp/comms 比例写死进配置（且前后向不同）。这避免了运行时不确定性，但也意味着每个 workload 都要重新调 5 个超参数（fwd/bwd comm SM 数、minibatch、macrobatch、schedule multiplier）。

端到端基准

512 张 GPU（多个 GB300 NVL72 机架），对照自家基于 DeepEP + 定制 MXFP8 kernel 的旧产线，只换 MoE 层实现：760.9 → 1070.2 tokens/s/GPU，1.41×。

诚实的解读： ① 2.37× 是 MXFP8 前向单层峰值，不是所有配置的均值——BF16 反向只有 1.58×；② 端到端 1.41× 对比的是 Cursor 自己的 DeepEP 产线，不是公开基线；③ 这是训练场景测的，推理（没有 wgrad/replay 压力、模型并行度不同）数字不会一样；④ 全部在 NVL72 域内测的，跨机架（IB）行为不在此列。亮点依然是可信的——博客、代码、基准脚本全部开源，可复现是这篇工作最大的加分项。

大图景：agent 时代的 kernel 工程

MoK 本身是技术成果，但 Cursor 在文末的"元叙事"更值得注意：kernel 优化空间的入门门槛正在被 AI agent 抹平。他们的说法很有信息量——去年写 megakernel 需要先造一层简化抽象（类似图里的"framework layer"）；今年不需要框架了：agent 一次性写出单算子 kernel（这部分几乎全自动），人类+agent 协作从零裸写分布式 megakernel，小团队就扛住了 3260 行生产级代码。

换个角度看：MoK 的 2.37× 是"AI 辅助写 kernel"这条曲线的又一个数据点。当单算子 kernel 被 agent 商品化，剩下的竞争壁垒是设计方向——怎么选通信方向、怎么排依赖网、怎么定 SM 掩码——这些恰恰是这篇博客里最"人味"的部分。

总结

  • 一句话：MoK 不是又一个更快算子，而是把 MoE 层的通信/计算/调度/信令/缓冲管理整体重排进单个确定性 megakernel，通信方向选择和 ring 缓冲管理是其中最有普适性的两个思想。
  • 可迁移的洞察：① push/pull 的选择要同时看调度、带宽、信令三个维度，默认选项（push）在 MoE 场景全面劣势；② 重叠粒度有明确物理拐点（两个 wave）；③ 环形缓冲的填充顺序决定反向重算量——"逆序填环"是个通用技巧；④ Grace CPU 慢的硬件上，消除 CPU 参与本身就是优化。
  • 局限：NVL72 专属、训练场景、5 个敏感超参数、依赖 kittens 生态。换个硬件或场景，这些数字要重新验证。
