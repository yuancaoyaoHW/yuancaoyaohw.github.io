PTStore：把 KV 缓存变成“CDN”

arXiv:2607.22648 · Euro-Par 2026 · Maghyastha, Underwood, Burns, Nicolae

把每个 GPU 上零散的 KV 张量，当成 CDN 里的内容副本：分布式存储、按热度复制、扁平元数据查询。

★ 核心一句话

PTStore 把 “跨节点共享 KV 前缀” 当成一个 分布式存储问题 来解：每个节点跑一个 server，增量存储让前缀像 trie 一样无冗余生长，扁平元数据让查询不用走分布式 trie，热度复制把热点张量拉到本地、用少量冗余换回 locality。长文档 Q&A 上比基线快 5–6×。

1 · 问题：单机前缀缓存的瓶颈

LLM 推理分 prefill（并行吃 prompt、算力密集）和 decode（逐 token 自回归）。两阶段都靠 KV cache 存注意力中间结果 K/V，避免重复算 attention。当多个请求共享同一前缀（同一段长文档、同一个 system prompt），前缀对应的 KV 张量也能复用——这就是 prefix caching。

现状的问题是 作用域太窄：vLLM 的 LRU 块缓存只在单 GPU；LMCache 把块 flush 到主机内存、跨同节点 GPU 共享；但跨 计算节点 的前缀复用几乎没人做好。结果是：节点 A 算过的前缀，节点 B 要重算一遍——在长 prompt（8k tokens）下，这是巨大的浪费。

2 · 前缀复用的本质：最长公共前缀（LCP）

前缀复用的核心操作是 找最长公共前缀（Longest Common Prefix, LCP）：给定一个新请求的 KV 序列，在所有已存对象里找最长的一段连续重合前缀，只把 增量部分 存下来。增量以 张量粒度 增量保存，多个对象的前缀像 trie 一样无冗余地分叉生长。

PTStore 的关键洞察：增量本身只有几字节（tensor ID 列表），所以 LCP 查询是 带宽轻量 的，可以放心地分布式广播。这跟“传整个 KV 张量去比对”完全不同。

3 · PTStore 架构全景

每个计算节点跑一个 server，聚合本节点的 host memory + 本地 SSD，服务本节点和远端的 GPU client。关键设计：

  • Owned cache：server 是某些增量的“owner”，最末层保证持久化。
  • Replication cache：缓存非 owned 的热门张量副本，可任意层驱逐。
  • 两级在同一个 host memory / SSD 层级里 竞争容量——这是核心 trade-off。

4 · 扁平元数据：免遍历查询

传统 trie 要从根走叶子才能重建一个对象。PTStore 用 单个扁平元数据：每个对象就是一串 unique tensor ID 列表，ID 同时编码 张量本身 和 存储它的 server。Load 时只要遍历这串 ID，查本地 replication cache 有没有；没有就按 ID 里的 server 地址远程拉。LCP 查询走 两级并行 reduce：每个 server 在本地 owned cache 并行匹配，再用一轮全局 reduce 汇总最长匹配。

▶ 动画：扁平 ID 列表 vs trie 遍历

5 · 热前缀复制：用冗余换 locality

对象分散到多 server 后，load 要联系多个 owner——即使并行，延迟也高过本地 host memory 访问。解法是 把热点张量复制到本地 replication cache。但这跟 owned cache 抢同一块内存：复制多了，冷张量更可能落到远端慢层，反而拖慢。PTStore 用一个 可配置阈值 + 上下限来切这个 trade-off。

▶ 动画：热度驱动的复制与 trade-off

6 · GDSF 淘汰：频率 × 大小

LRU 对前缀结构不友好：前缀 靠前的张量 更可能被命中（它们属于更多对象的公共前缀），但 LRU 看不出这个结构性。PTStore 改用 GDSF（web 缓存领域来的策略），按 frequency × size 排序驱逐。小而频繁的张量 vs 大而稀疏的张量，GDSF 能避免“一堆小热点把大张量挤出去、再被迫远程拉”的坏情况。

驱逐策略还要区分 replicated 和 owned：复制副本可以直接丢弃（最坏触发一次远程 I/O）；owned 张量必须 flush 到更慢的持久层。所以 PTStore 给 replication cache 设 下限和上限：先扔副本，触及下限了才动 owned。

▶ 动画：LRU vs GDSF — 同一缓存，不同选择

7 · RDMA 零拷贝聚合

为了不让张量碎成满天星，同一个增量被 consolidate 成一段连续区域存在单个 server（这个 server 成为 owner）。client load 时，如果张量不在本地 host memory，就用 bulk RDMA：每个张量给一个 (offset, size) 段，所有散落段在 一次 RDMA RPC 里并行读取——零拷贝，不用先拼成连续区再传。RDMA 段还随张量一起缓存，省掉下次的 setup 开销。

8 · 实验证据

在 ALCF Polaris（560 节点，每节点 4×A100、512GB DDR4、2×1.6TB SSD、Slingshot 10 互联）上，用 WikiQA 和 SQUAD 两个长文档抽取式 Q&A 数据集评测。对比四种方案：

方案前缀复用范围本地复制
vLLM Vanilla单 GPU 块缓存—
vLLM Prefix同节点主机内存无
EvoStore跨节点（RDMA）无
PTStore跨节点（RDMA）有（热度复制）

弱扩展（8→32 GPU，WikiQA）：四者都随规模线性扩展（RDMA 无通信瓶颈），但 EvoStore 因无本地复制、RDMA I/O 开销高，退化到接近 vLLM Prefix；PTStore 靠本地复制把远程 I/O 压下去，明显领先。

序列长度扩展（1k→8k，SQUAD）：1k 时三者接近（小张量放得进 HBM、重算也便宜）；从 2k 起 PTStore 反超，8k 时 ~2× 快于 vLLM Prefix、~20% 快于 EvoStore。序列越长，KV 张量越大、远程复用的收益越能压过 I/O 开销——长文档场景正是 PTStore 的甜区。

注意：5–6× 的总体提升来自“长 prompt Q&A”这类 prefill 密集、前缀高度可复用的负载；短 prompt 或前缀复用率低的场景，收益会收窄。论文也在未来工作里提到要做更多真实负载（多轮对话、代码补全）的对比。

9 · 一句话总结 + Q&A

记忆点：“CDN 思维做 KV 缓存——增量存、扁平查、热度复制、GDSF 驱逐、bulk RDMA 拉。”

Q：为什么不直接把 LMCache 扩展到跨节点？
LMCache 主要是同节点主机内存共享，跨节点要么不做、要么每张量单独远程拉，I/O 开销大且元数据同步难。PTStore 的 扁平元数据 + 热度复制 + GDSF 是专门为跨节点高频前缀复用设计的。

Q：复制占的内存从哪来？
从 owned cache 让出来。owned 末层保证持久化，replication 可以任意层驱逐。上下限控制切分比例，是个可调 trade-off。

Q：为什么 GDSF 比 LRU 好？
前缀结构里靠前的张量天然高频，但 LRU 只看“最近用没用”，不看频率也不看大小。GDSF 用 frequency×size 排序，避免“小热点挤走大张量、被迫远程拉大张量”的坏情况。

Q：和 Mooncake / SGLang RadixAttention 的区别？
RadixAttention 把 KV cache 当 radix tree，单节点内复用很好，但跨节点扩展受元数据同步拖累；Mooncake 是 KVCache-centric 分层（HBM/DRAM/SSD），但远程传输开销大。PTStore 的 扁平元数据 避开了 radix tree 跨节点遍历，热度复制 把高频访问拉回本地。
