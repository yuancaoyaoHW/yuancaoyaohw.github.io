一、自我介绍与项目真实性

Q1.1【P0-1】2 分钟自我介绍

问题：请做一个 2 分钟以内的自我介绍，说明你为什么适合大模型推理系统 / vLLM Runtime / NPU 推理优化方向。

标准答案：

我硕士毕业于XX大学计算机专业，目前在华为做 AI Infra Runtime，主要方向是 vLLM 在 Ascend NPU / MindSpore 后端上的推理 runtime 适配、correctness 排障和性能优化。

我过去一年最核心的项目是 EAGLE-3 speculative decoding 在 vLLM-MindSpore 和 vLLM-Ascend 上的落地。我负责过 draft proposer 输入构造、target hidden states / auxiliary hidden states 传递、target verification、rejection sampler、attention metadata、slot_mapping / block_table 和 KV cache 多并发回归等链路。

这个项目里有两类比较能体现能力的工作。第一类是 correctness 排障：10 并发下 draft model 第二次推理 batch1 之后输出同错，通过 dump block_table、position_ids、slot_mapping、KV cache slice、hidden states 和 logits，定位到 slot_mapping 没按底层 attention / KV 索引算子期望转成 int32，导致物理 KV slot 读写错位。第二类是性能优化：用 MSProf 定位 decode step 中 host 调度、小算子 launch 和首次编图 spike，把 prepare_inputs 里的 prefix / arange / slice / output_index 等索引逻辑迁到 device / 图内路径，并覆盖 draft lm_head warmup。

结果上，vLLM-Ascend PR #1032 合入了 EAGLE-3 proposer；在 Atlas 3000/310P3 上，Qwen2.5-7B + Eagle3-Qwen2.5-7B、spec=3 的实验中，输出吞吐从 9.22 tok/s 提升到 14.30 tok/s，TPOT 从 108.18 ms 降到 65.76 ms。我的优势是能把 speculative decoding 算法、vLLM runtime 状态和 NPU 执行性能放在一起看问题。

自检：不说 Ego3（应为 EAGLE-3）/ MS Proof（应为 MSProf）/ VM-Minus（应为 vLLM-MindSpore）；先主线项目→真实 bug→性能优化→指标；不平均讲 Suffix / KV-Select。

Q1.2【P0-2】如何证明自己是主力实现者

问题：在你做过的这些工作里，哪一段最能证明你是主力实现者，而不是只参与测试、调参或跟着改？

标准答案：

选 EAGLE-3 在 vLLM-MindSpore / Ascend NPU 上的适配和优化。原因是这段经历跨了模型网络、runtime 链路、NPU 图执行、correctness 排障和性能验证。

亲手做过的三个关键点：

  1. EAGLE-3 draft proposer / prepare_inputs 链路：把 target 输出 token、target hidden states、position_ids、attention metadata、slot_mapping 等组织成 draft model 能消费的输入。
  2. attention metadata 和 KV cache 地址适配：block_table 到 slot_mapping 的物理 slot 映射，以及多并发下 KV cache 不串请求。
  3. 性能路径优化：prepare_inputs / rejection_sampler 中小算子融合、host-device 调度减少、draft lm_head 首次编图 warmup。

最难 bug：多并发下 batch0 正常、batch1 之后 draft 输出同错。难点在于单 batch 基本对齐，只有多请求、第二轮 draft forward 后才明显暴露，且 EAGLE-3 同时涉及 target/draft 双模型、speculative token 展开、KV cache 物理地址和 sampler 状态。排查方式：固定输入和 seed，对比单并发、双并发和 10 并发，逐层 dump input_ids、position_ids、block_table、slot_mapping、KV cache slice、hidden states 和 logits。最后发现 slot_mapping 未转成底层算子期望的 int32，导致物理 KV slot 读写错位。修复后多并发 logits / hidden states 对齐，acceptance rate 恢复。

PR / commit / benchmark 证据：EAGLE-3 proposer / Qwen2、Qwen2.5 接入代码；slot_mapping、attention metadata、prepare_inputs 相关修改；吞吐、TPOT、acceptance rate / accepted length、logits 对齐和多并发回归记录。

保守表达点：rejection sampling 数学口径、hidden states 具体取法、通用 proposer 接口抽象——这三块不确定的细节不讲死。

Q1.3【P0-10】回应"只是适配和修 bug"

问题：你的项目是不是主要在做适配和修 bug，不像底层推理系统优化？

标准答案：

我理解这个质疑。这个项目确实包含适配和 bug 修复，但它不是简单 API glue，而是把 EAGLE-3 speculative decoding 的语义真正落到 vLLM runtime 和 Ascend NPU 推理系统里。

第一，适配跨多个层次：vLLM scheduler、draft proposer、target verification、rejection sampler、attention metadata、KV cache、MindSpore graph 和 NPU 执行路径。EAGLE-3 不是只多跑一个 draft model，它会改变每轮 decode 的 token 组织方式、hidden states 传递方式、position_ids / slot_mapping 展开方式，以及 target / draft 两套状态管理。

第二，解决的 bug 不是普通业务 bug：多并发下 batch0 正常、batch1 之后 draft 输出同错，最后定位到 slot_mapping dtype 不符合底层 attention / KV 索引算子期望，导致物理 KV slot 读写错位。涉及 PagedAttention、多 batch、KV cache 物理地址、draft model 多轮状态和底层算子约束。

第三，也做了性能优化：用 MSProf 定位 decode step 里的 host 调度、小算子 launch、prepare_inputs 索引构造和首次编图 spike，把部分 prefix / arange / slice / output_index 逻辑迁到 device / graph 内，并通过 draft lm_head warmup 减少真实请求时延 spike。关注的是 serving hot path 的 TPOT 和 throughput。

核心句：适配不是 API glue，而是 runtime 语义对齐和性能闭环。能把算法、runtime 和硬件执行结合起来做闭环：既看 acceptance rate / accepted length，也看 TPOT、throughput、host enqueue、kernel launch、KV cache 访存、graph compile 和多并发 logits 对齐。

Q1.4【P0-11】技术分歧 / reviewer 故事

问题：你有没有和 reviewer、同事或上游社区产生过技术分歧？

标准答案：

有一次更准确地说是 review 方案取舍，不是强冲突。EAGLE-3 接入时，reviewer 担心 proposer 改动会侵入 vLLM V1 speculative decoding 原有抽象——EAGLE-3 有 target hidden states / auxiliary hidden states、draft model runner 和特殊 input builder，如果直接把这些字段塞进通用链路，会让后续 suffix decoding 或 ngram proposer 也被迫理解 EAGLE-3 的细节。

我最初方案偏直接打通链路，先保证 correctness 和性能能跑通。后面根据 review 意见，调整成边界更清楚的方式：

  • proposer 只负责 candidate tokens 和 proposer-specific state；
  • target verification 链路尽量复用；
  • sampler 统一负责 accept / reject / recover sample；
  • state manager 统一处理 request state、KV cache 和输出 commit。
  • EAGLE-3 特有的 hidden states 和 draft input 构造尽量收在 builder / adapter 内，不散落到 runner 各处。

为说服对方，补了几类证据：单并发 / 多并发 logits 对齐、acceptance rate / accepted length 回归、开启和关闭 speculative 的 E2E 行为对比、prepare_inputs / sampler 相关 benchmark。最终方案不是简单坚持原直接实现，而是在保持功能打通的同时降低主链路侵入性。

二、EAGLE-3 数据流与算法原理

Q2.1【P0-3】一次 EAGLE-3 decode step 数据流

问题：从一次 decode step 开始，按时间顺序讲清 EAGLE-3 数据流。

标准答案：

先固定视角：这里讲的是已经完成 prefill、进入 decode 的 active requests，不把 scheduler 新接入 prefill 请求混进单个 decode step。

  1. target model forward：基于当前 request state、position_ids、attention metadata、block_table / slot_mapping 和 KV cache 做一次 target forward，得到下一 token 的 logits / sampled token；EAGLE-3 场景下还需要拿到 target hidden states 或 auxiliary hidden states，作为 draft model 的条件输入。具体取哪些 hidden states 要以模型结构和实现配置为准，不在没有代码依据时讲死是第几层。

  2. proposer / prepare_inputs：构造 draft input_ids、position_ids、attention_metadata、slot_mapping、可能的 block_table / request offsets / token offsets，并把 target hidden states 传给 draft model。draft model 连续提出最多 num_spec_tokens 个 candidate tokens，同时产生 draft probabilities 或 draft logits。

  3. target verification：不是逐个 token 串行验证，而是把 draft tokens 组成扩展序列，在 causal mask 和位置正确的前提下，用 target model 一次 forward 并行得到这些候选位置上的 target logits / probabilities。

  4. rejection sampler：按 target distribution 和 draft proposal distribution 逐 token 决定 accept / reject。最终只把 confirmed tokens commit 到 request state 和输出缓冲；更新 confirmed seq_len、positions、accepted length、finished / EOS / stop 状态。KV cache 也要按最终确认的逻辑状态处理，不能让未确认或逻辑不可达的 draft / rejected 状态污染后续可见路径。

多并发下最容易错的两个对齐：

  1. request 到 batch / token-level flatten 的映射：input_ids、position_ids、hidden states gather、accepted mask、final token 回写。
  2. KV cache 物理地址映射：block_table、slot_mapping、seq_lens、physical block、block offset 和 KV cache slot。

Q2.2【P0-4】Rejection sampling 严格口径

问题：为什么 speculative decoding 必须做 rejection sampling？拒绝后 token 怎么来？为什么分布仍和 target 一致？

标准答案：

核心原因不是"判断 draft 对不对"，而是最终输出分布必须和 target model 一致。draft model 只是 proposal distribution，不能直接替代 target distribution。rejection sampling 的作用是利用 draft 提速，同时用 target distribution 校正最终输出。

temperature = 0 时：deterministic / greedy 路径，比较 target 和 draft 在对应位置的贪心 token。一致就接受；一旦不一致，就停止继续接受后续 draft tokens，并使用 target 的贪心结果作为该位置最终 token。

temperature > 0 时：draft 在某个 token x 上的 proposal 概率记为 q(x)，target 对同一 token 的概率记为 p(x)。

  • 接受概率 = min(1, p(x) / q(x))。
  • 被接受，继续看下一个 speculative token；
  • 被拒绝，则在剩余质量分布上采样一个 token：对 max(0, p - q) 做归一化后 recover sample。
  • proposal 已覆盖的概率质量 + 拒绝后的剩余概率质量 = target distribution。

线上 acceptance rate 很高但输出和 baseline 对不齐时，优先怀疑 sampler 两个实现点：

  1. logits 到 probabilities 的处理顺序是否和 baseline 完全一致：temperature、top-k、top-p、mask、softmax、renorm、dtype 精度和每个 request 的 sampling params。
  2. accept/reject 和 recover sample 是否正确：p/q gather、max(0, p-q) 归一化、随机数消费顺序、per-request seed、accept mask 和 final token commit 顺序。

自检：必须说"分布一致性"，不只说"判断 draft 是否预测正确"；必须说 min(1, p/q) 和 max(0, p-q)；不要把 logits 说成 logics（应为 logits）。

Q2.3【严格第2题】Rejection sampler 接受/拒绝机制

问题：speculative decoding 里的 rejection sampling 具体怎么决定一个 draft token 是接受还是拒绝？要求解释 target probability / draft probability、接受概率、拒绝后的处理、重新采样分布，以及为什么能保证最终采样分布与直接 target model 采样一致。

标准答案：

对一个 draft 提出的 token x，取其在当前上下文下的 q(x)=p_draft(x) 和 p(x)=p_target(x)。注意每个 speculative token 的条件上下文不同，所以 p 和 q 都是该位置、该上下文下的条件概率。

  • 接受概率 = min(1, p(x)/q(x))。
  • 若接受，继续检查下一个 draft token；
  • 若第一次拒绝，则拒绝位置之后的 draft tokens 全部丢弃，并从 normalize(max(0, p - q)) 的 residual distribution 中重新采样一个 token。
  • 若所有 draft tokens 都接受，某些实现还会额外从 target 的最后位置采样 bonus token。

为什么分布一致：这个过程通过接受 draft 分布中与 target 重叠的部分，并在拒绝时从 target 多出的 residual 部分采样，使边际分布等价于直接从 target model 采样。

公式记忆点：

  • 接受概率 = min(1, p/q)
  • recover distribution = normalize(max(0, p - q))
  • 随机数 u 服从 Uniform[0,1]，判断 u <= min(1, p/q)

Q2.4【严格第14题】Rejection sampler 具体数值例子

问题：draft token 是 A，q(A)=0.6，p(A)=0.3。

  1. random rejection sampling 下，这个 draft token 的接受概率是多少？
  2. 如果随机数 u=0.4，接受还是拒绝？如果 u=0.6 呢？
  3. 如果拒绝，recover distribution 应该基于什么分布构造？
  4. 如果某个 token B 满足 p(B)=0.4, q(B)=0.1，它在 recover distribution 里对应的未归一化概率是多少？
  5. 如果融合 kernel 把 p-q 写成了 q-p，acceptance rate 和输出质量大概率会出现什么现象？

标准答案：

  1. 接受概率 = min(1, p/q) = min(1, 0.3/0.6) = 0.5。
  2. u=0.4 ≤ 0.5 → 接受；u=0.6 > 0.5 → 拒绝。
  3. recover distribution 基于 max(0, p - q) 构造，然后重新归一化后采样（不能只用 p-q，因为负数概率没有意义）。
  4. B 的未归一化 recover mass = max(0, 0.4 - 0.1) = 0.3。
  5. 把 p-q 写成 q-p 会把 draft 过度覆盖、target 不足的概率区域搞反，recover token 会偏向 draft 已经过强的区域，导致最终分布偏离 target。acceptance rate 本身不一定必然上升（accept mask 由 p/q 控制）；但输出质量和分布一致性大概率会错。如果同一个 kernel 里也混淆了 accept/recover 逻辑，acceptance rate 也可能异常波动。

三、Speculative Decoding 收益与边界

Q3.1【P1-3】Speculative decoding 收益边界

问题：为什么 speculative decoding 能提升吞吐？什么时候收益差甚至负收益？

标准答案：

普通 decode 每输出一个 token 通常需要一次 target decode step。speculative decoding 额外付出 draft generation、target verification、rejection sampler 和状态管理开销，但如果一轮平均能接受 A 个 token，就把一次 target verification 的成本摊到 A 个输出 token 上，减少 target decode step 次数和每 token target 成本。

收益成立四个条件：

  1. accepted length 足够高；
  2. draft model 足够便宜；
  3. target verification 能高效并行；
  4. prepare_inputs、sampler、KV cache commit 等 runtime 额外开销不能太大。

收益差的场景：

  • draft / target 分布不匹配
  • 高熵输出、temperature 较高
  • 短输出
  • num_spec_tokens 过大导致后段 token acceptance 降低
  • draft model 太大
  • verification 序列并行效率不好
  • batch 内请求长度差异大
  • NPU 上小算子 / host 调度开销抵消收益

Q3.2【P1-4】Adaptive speculative / fallback

问题：如果线上 acceptance rate 低，如何做动态策略？

标准答案：

动态策略一定不能在 draft generation 或 target verification 中间切换。必须等当前 decode step 完成，confirmed tokens、KV cache、request state、scheduler state 都 commit 后，再决定下一轮策略。

用 rolling window 统计每个 request 或 batch 的 acceptance rate / accepted length。

  • 如果连续几轮低于阈值，可以先降低 num_spec_tokens；
  • 如果仍然低，再 fallback 到普通 decode。

避免抖动：需要 hysteresis、cooldown 和最小生效周期，比如连续 N 轮低 acceptance 才降级，连续 M 轮恢复才重新开启。

fallback 保证 non-spec path 不受影响：

  • 默认 config 可关闭 speculative；
  • 异常、低收益或 sampler 校验失败时回退普通 decode；
  • 测试覆盖开启/关闭 speculative 的输出一致性、KV cache 状态隔离和性能不回退。

Q3.3【简历第18题】speculative decoding 与 KV-select 的瓶颈对比

问题：speculative decoding 和 KV-select 分别适合优化什么瓶颈？如果两者叠加使用，可能有什么冲突或收益抵消？

标准答案：

  • speculative decoding 优化的是"步数 / 每轮推进 token 数"——减少 target decode step 数，适合 target 单步昂贵且 draft 接受率高的场景。
  • KV-select 优化的是"单步长上下文 attention 的 KV 读取和 QK/softmax 计算"——减少每步长上下文 attention 的 KV 读取，适合长上下文且 attention 访存瓶颈明显的场景。

叠加冲突：

  • KV-select 如果改变 target logits 分布，可能降低 draft-target 一致性，从而降低 acceptance rate。
  • 两者都可能引入额外 runtime glue logic、gather/scatter、小算子、shape 复杂度和图编译路径，叠加后可能互相抵消收益。
  • correctness 口径：如果 target verification 使用 KV-select 后已经不是原始完整 target model 分布，那么 speculative decoding 保证与原 target 采样分布一致的理论前提会被破坏，除非接受这个近似或重新定义 target 分布。

验证方式：需要分别 benchmark baseline、spec only、KV-select only、spec + KV-select，并观察 TPOT、throughput、acceptance length、质量指标和 NPU utilization。

四、多并发 correctness 排查

Q4.1【P0-5】多并发 correctness 排查流程

问题：单请求 EAGLE-3 输出和 baseline 对齐，但多并发输出开始漂，acceptance rate 异常波动。你怎么排查？

标准答案：

先把问题做成 deterministic case：固定输入、固定 sampling params、固定 seed，先跑单请求 baseline，再跑双请求和 10 并发 mixed case。最好让不同 request 的 accepted length 不同，故意制造 request state 分叉。

第一轮 dump 覆盖输入组织、中间验证和输出提交三段（不要只看输入）：

  • input_ids、position_ids、seq_lens / q_seq_length / batch_valid_length
  • block_table、slot_mapping、attention_metadata
  • target hidden states / draft hidden states、target logits / draft logits
  • processed_probs、accept mask、recovered token、final sampled token
  • 每个 request 的输出状态

分叉判断（找第一次 divergence）：

  • input_ids / position_ids / slot_mapping 不一致 → 查 batch mapping、position 构造、block_table / slot_mapping
  • hidden states 不一致 → 查 attention metadata、KV cache、model forward
  • target logits 不一致 → 仍然查 logits 前
  • target logits 一致但 processed_probs 不一致 → 查 logits processing（temperature、top-k、top-p、mask、softmax、renorm、dtype、sampling params 是否串请求）
  • accept_mask 不一致 → 查 rejection sampler 的 p/q gather、随机数比较、accept 判定
  • accept_mask 一致但 final_tokens 不一致 → 查 recover sample、bonus token、token 拼接、request output commit

如果单并发正确、多并发错误，最优先怀疑：request -> batch index 映射、block_table / slot_mapping 物理 KV 地址映射、accepted length 不同导致的 seq_len / position / KV cache 写回错位。

修复后补三类回归：

  1. 单请求下不同 accepted length 的 correctness 回归
  2. 多请求下每个 request accepted length 不同的交叉回归
  3. 部分请求 reject / EOS / stop 提前结束时，其余 request position / KV cache / output commit 不受污染的回归

Q4.2【P0-6】slot_mapping / block_table / KV cache bug

问题：slot_mapping 未转 int32 为什么导致 10 并发下后 9 个 batch 同错？

标准答案：

slot_mapping 不是普通 position，它表示当前 token 在 paged KV cache 中的物理 slot。完整映射链：

  1. request 的 logical position 先通过 position // block_size 得到 logical block
  2. 再查 block_table 得到 physical block id
  3. 最后用 physical_block_id * block_size + position % block_size 得到物理 slot

block_ids * block_size + clamped_positions % block_size 本质是在把 physical block id 和 block 内 offset 展平成当前 token 的 KV cache slot index。

bug 关键不是"310 不支持 int32"，而是底层 NPU attention / KV cache 索引算子期望 slot_mapping 是 int32。如果上层保留为默认 int64 或不符合算子期望的 dtype，框架可能不直接报错，但算子侧索引解释或地址计算会异常，导致读写到错误物理 slot。

为什么单 batch 不明显、多 batch 第 2 次明显：

  • 单 batch 时第一个 request 往往映射到低位或起始 slot，即使索引路径有问题，也可能碰巧读写到正确区域。
  • 多 batch 时每个 request 的 physical block / slot 不同，错误 dtype 可能让 batch1+ 读到同一段错误地址或 zero KV，所以后 9 个 batch hidden states / logits 变得相似甚至同错。
  • 第二次 draft 推理更明显，是因为第一次 decode / cache update 后，KV cache 已经有多 request 写回状态，错误 slot_mapping 开始影响下一轮 attention 读写。

证明链路：dump block_table / physical_block_ids、positions、slot_mapping、KV cache 对应 slice、attention output / hidden states / logits。修复 .to(torch.int32) 后期待：不同 request 的 slot_mapping 映射到各自 physical slot，KV cache slice 不再互相覆盖，hidden/logits 不再同错，acceptance rate 恢复到接近单 batch 的合理范围。

Q4.3【P1-1】PagedAttention 基础追问

问题：block_table 和 slot_mapping 的区别是什么？

标准答案：

  • block_table 更偏 sequence / request 级，记录 logical block 到 physical block 的映射。因为 paged KV cache 里逻辑连续的 token 不一定存放在物理连续内存中，所以需要 block_table 找到每个 logical block 对应的 physical block。
  • slot_mapping 更偏 token 级，表示当前 token 对应的物理 KV slot，通常由 block_table 和 position 推导得到：logical_block = position // block_size，physical_block = block_table[logical_block]，slot = physical_block * block_size + position % block_size。

两种错位现象：

  • 如果 block_table 对但 slot_mapping 错：历史 block 映射可能没错，但当前 token 读写的具体物理 slot 错了。
  • 如果 slot_mapping 对但 block_table 错（不常见）：当前 token 写入位置看似正确，attention 读取历史 KV blocks 时却查错 physical block。

一句话区分：position 是 request 逻辑序列里的 token 位置，offset 是 position 在当前 block 内的相对位置，slot_mapping 是结合 physical block id 后得到的 KV cache 物理 slot 地址。

Q4.4【P1-2】第一次 divergence 定位表

问题：如何快速判断问题在 logits 前还是 logits 后？

标准答案：

找第一次 divergence 的 tensor：

第一次 divergence 的 tensor 优先怀疑的模块
input_ids / position_ids / slot_mapping 不一致 prepare_inputs、batch mapping、attention metadata
hidden states 不一致 attention metadata、KV cache、model forward
target logits 不一致 仍然查 logits 前（input、position、KV cache、model forward）
target logits 一致但 processed_probs 不一致 logits processing（temperature、top-k、top-p、mask、softmax、renorm、dtype、sampling params 是否串请求）
processed_probs 一致但 accept_mask 不一致 rejection sampler 的 p/q gather、随机数比较、accept 判定
accept_mask 一致但 final_tokens 不致 recover sample、bonus token、token 拼接、request output commit

关键原则：如果 hidden states 和 target logits 已经对齐，一般不优先继续查 KV cache；应该先查 logits 后处理和 sampler。第一次 divergence 在 processed_probs，就不要继续优先查 KV cache。

Q4.5【简历第11题】speculative verification attention mask 可见性

问题：在 speculative verification 阶段，假设一个 batch 里有多个请求，每个请求都有多个 speculative tokens。attention mask / attention metadata 必须保证哪些 token 能看见哪些 token？

标准答案：

在 verification 阶段，每个请求内部的多个 speculative tokens 需要构造局部 causal 关系：

  • 第 k 个 speculative token 可以 attend 到该请求的历史 KV 和本轮候选序列中第 1 到 k-1 个 speculative token；
  • 不能 attend 到第 k+1 之后的 future token；
  • 不同请求之间必须完全隔离，不能互相 attend，即使它们在 batch flatten 后相邻排列。batch 只是为了并行计算，不代表序列之间可以互相可见。

attention metadata 必须同时描述：每条 sequence 的历史长度、query token 起始位置、block_table 和 causal mask 边界。

mask 错和 KV 地址映射错是两类问题：

  • mask 错：可见性边界错（看见 future token、看见跨请求 token、看不见应有历史 token）
  • slot_mapping / block_table 错：物理 KV 地址读写错位

两者都可能导致 logits 异常，但排查路径不同。

Q4.6【简历第24题】rejected token 的 KV cache 处理

问题：如果 target verification 一次 forward 了 3 个 speculative tokens，但最后只接受了第 1 个 token，那么 target model 为第 2、第 3 个 token 计算出来的 KV cache 应该怎么办？

标准答案：

被拒绝的 token 不能进入后续有效上下文。工程上物理内存可以不立即清零，但必须通过 committed sequence length、slot reuse、block manager 状态和 attention metadata 保证不可达。

更严谨说法：target verification 可能为多个 speculative token 写入 KV，但最终只提交 accepted token。Rejected token 对应的 KV 不能被后续上下文看见；实现上可以不立即清零，但要通过 committed sequence length、slot reuse、block manager 状态和 attention metadata 保证不可达。

测试方案：构造必拒绝第 2/3 token 的 deterministic case；故意把 rejected token 的 KV slot 写入特殊值或 NaN/大值；下一轮 decode 对比 logits 是否与"只 forward accepted prefix"的 baseline 完全一致。如果一致，说明 rejected KV 没有被读取。

五、性能优化

Q5.1【P0-7】prepare_inputs / rejection_sampler 融合优化

问题：vLLM 调度 180ms 到 90ms 是怎么量的？prepare_inputs 具体优化了什么？

标准答案：

180ms 不是整个服务端到端耗时，而是在 10 并发、大部分请求完成 prefill 后，从 target decode N 结束到 target decode N+1 之前这段 step 间隔里看到的 runtime 调度和准备开销。这个窗口包含 prepare_inputs、rejection_sampler、bookkeeping、draft prepare / propose 等相关开销，但不等同于大模型 matmul 计算。

prepare_inputs 慢的核心不是大矩阵计算，而是索引 tensor 构造和小算子调度。例如 prefix / prefix-sum、按 request 生成 range / arange、slice 写回、output_index 生成等逻辑，如果在 host 或多个小 op 路径上执行，会引入 kernel launch、host enqueue、host-device 同步和中间 tensor 创建/拷贝。decode step 每次 token 数很少，固定调度开销会被放大。

优化做法：把部分索引生成逻辑融合到 device / 图内路径。以 output_index 为例：原来可能对每个 request 根据 prefix offset 生成 arange，再 slice 写入输出 tensor；融合后 kernel 直接读取 sum_tokens / sum_query_lengths 等 prefix 信息，在 device 端生成每个 token 的 relative index 或 position index，减少 Python loop、多次 arange、slice 写回和小 kernel launch。

收益主要来自减少 kernel launch、host 调度、中间 tensor 写回和 host-device 同步，而不是减少大量数学计算。

风险不能说"没有"，更稳的说法是逻辑等价、风险可控，但要重点验证：动态 batch size、不同 query length、不同 speculative length、空请求 / finished 请求、temperature=0 和非 0 两条 sampler 路径，以及 shape 变化是否触发 fallback 或重新编译。

小例子：

  • query lengths = [2, 3, 1]
  • sum_query_lengths end offsets = [2, 5, 6]，如果需要 start offsets 则是 [0, 2, 5, 6]
  • relative output_index = [0, 1, 0, 1, 2, 0]
  • 如果 start positions = [10, 20, 30]，最终 position index = [10, 11, 20, 21, 22, 30]

最容易 off-by-one 的地方是第 0 个 request 的 start=0、end-exclusive slice、以及最后一个 token 边界。

Q5.2【P0-8】lm_head 首次编图 spike 与 warmup

问题：draft lm_head 首次真实请求 300ms spike 是什么？warmup 怎么设计和验证？

标准答案：

如果 MSProf 里看到 lm_head 首次出现约 300ms，而后续同 shape 稳定只有几 ms，判断这是 graph compile / 首次编图或 graph cache miss，而不是 lm_head 稳态计算本身慢。warmup 的目标是把编译开销从真实请求路径前移到服务启动路径。

只 warmup target model 不一定覆盖 EAGLE-3 draft model：因为 target model 和 draft model 是不同网络、不同权重、不同执行图。普通 prefill / target decode warmup 可能只覆盖 target forward 和 target lm_head，不会触发 draft proposer、target hidden states 输入、draft model decode、draft lm_head 和 EAGLE-3 特有 shape 路径。

warmup 至少要覆盖：target prefill、target decode、draft model decode、draft lm_head、典型 batch size、典型 seq length / spec length、dtype、attention mask / metadata 路径，以及 EAGLE-3 的 auxiliary hidden states 输入路径。

验证不能只说"启动时 warmup 了"：对比 warmup 前后首个真实请求 timeline，确认 300ms compile 节点从请求路径消失，没有转移到别的 runtime 阶段；同时看首轮 decode latency、draft lm_head timeline、graph cache hit 或 compile event、TPOT / P99 是否改善。

风险：启动时间增加、显存峰值或图缓存占用增加、shape bucket 过多导致编译时间膨胀、覆盖不足导致线上仍有冷启动 spike，以及 warmup 请求状态必须隔离，不能污染 KV cache 或统计指标。

Q5.3【P1-5】动态 shape / graph compile 边界

问题：MindSpore 静态图下动态 shape 怎么理解？

标准答案：

稳妥表达：参与过 EAGLE-3 在 MindSpore 图模式下的输入适配，主要关注 positions、slot_mapping、hidden states 等动态输入在 decode 场景下的对齐。不主动说"主导了 MindSpore 静态图动态 shape 设计"，除非能拿出具体代码和机制。

vLLM serving 天然有动态性：batch size、每个 request 的 token 数、prefill / decode、seq length、speculative length、accepted token 数、slot_mapping、block_table 和 attention metadata。MindSpore 静态图偏好稳定 shape 和执行路径，所以两者有适配成本。

更稳的判断：如果动态 shape 设置完整、相关动态维度被声明清楚、图拓扑和执行分支不变，shape 变化不应触发重复编图。若出现 spike，先用 MSProf 确认是否有 compile / build graph event；如果没有，再排查 kernel launch、host enqueue、tiling、workspace、fallback、内存分配和小算子碎片。

不要说"没有冲突"或"完全没有风险"。

Q5.4【P1-6】MSProf 性能归因

问题：拿到 MSProf 火焰图后如何区分模型计算慢和 runtime 调度慢？

标准答案：

同时看 host timeline 和 device timeline：

  • 模型计算慢：device kernel 持续占用，matmul / attention kernel 本身耗时长。
  • runtime 调度慢：host 侧 enqueue / compile / sync / Python 调度时间长，device kernel 之间有空洞，小 kernel 很多但单个计算时间短，或者 H2D / D2H 拷贝和同步点频繁。

判断 300ms 是否是首次编译：看它是否只在第一次某个 shape / path 出现，同 shape 后续是否消失，timeline 中是否有 compile / build graph event。

判断 500us 小开销是否值得优化：不只看单次占比，还要看出现频率、是否每个 decode step 都重复、是否影响 P99、是否被 speculative decoding 放大，以及优化风险。

把火焰图结论变成优化计划时，要形成闭环：假设、单点改动、对照实验、观察指标、回滚条件。比如假设 draft lm_head 首次编译导致 spike，改动是 warmup draft lm_head，验证是固定输入和并发，对比 MSProf、TPOT、P99 和首轮 decode latency，确认节点消失且没有转移。

Q5.5【PR代码级】mint.arange / mint.cumsum 替换

问题：range 编译 200ms 和 ops.cumsum 改 mint.cumsum 是你优化的吗？

标准答案：

这两个点不是我主导的。是 MindSpore 同事建议替换的，我负责接入和验证，不把它说成我独立设计的优化。

  • mindspore.arange → mint.arange：原接口在当前后端上可能触发额外编译或不走更优的图算子路径，换成 mint.arange 后走了更适合动态图/静态图编译和后端适配的实现。
  • ops.cumsum → mint.cumsum：用于生成 cu_num_tokens（cumulative token counts），即每个 request 在拼平 token 序列里的累计 offset。后续 index 生成、slice 边界、position 计算都依赖它。mint.cumsum 更适合当前 MindSpore 后端和图模式路径。

验证：输入 query lengths [2,3,1]，exclusive prefix 是 [0,2,5]，inclusive cumulative end offsets 是 [2,5,6]，具体用哪个取决于后续接口约定。

影响链路：cumsum → token offset/slice boundary → positions/output_index → slot_mapping → attention/KV cache → logits 精度。

Q5.6【PR代码级】decode mask 1x1

问题：decode 阶段为什么理论上只需要 1*1 或很小的 mask？500us 开销来自哪里？

标准答案：

decode 阶段每个 request 通常只处理当前新 token，query length 是 1；而 prefill 阶段要处理 prompt 多 token，需要完整 causal mask（例如 128x128 这种较大的 mask）。decode 不需要这么大的 mask。

原来没传 1*1 mask 时：系统走了更大的 prefill mask 路径，导致额外 mask 构造、传输或 attention kernel 处理开销。500us 不是大计算，而是错误路径带来的小但稳定的 decode 开销。

mask 给谁用：最终服务于 draft model decode attention 路径里的 attention kernel / attention metadata，而不是业务层"给模型用"。

验证语义不变：固定输入下比较修复前后 attention output、hidden states、logits；覆盖 batch size > 1、不同历史 seq len、不同 speculative length；确认只有 mask shape/path 变化，attention 语义不变。

为什么 EAGLE-3 更敏感：speculative decoding 会额外引入 draft decode / verification 相关步骤，decode path 被调用更频繁，小开销会被重复放大，所以 500us 级别的 mask 开销也值得优化。

六、Benchmark 与公平性

Q6.1【P0-9】Benchmark 口径和公平性

问题：你简历里写吞吐 9.22 到 14.30 tok/s、TPOT 108.18 到 65.76 ms，这个 benchmark 怎么保证公平？

标准答案：

这组数据是在 Atlas 3000/310P3 上，用 Qwen2.5-7B + Eagle3-Qwen2.5-7B，基于 MT-Bench 前 80 轮做的验证，spec=3。它可以作为早期通用对话分布下的性能验证，但不说它完整代表线上所有流量。

吞吐口径：输出 token throughput（总输出 token 数 / 端到端总耗时）。 TPOT 口径：每输出 token 的平均 decode 耗时；需要明确是否包含 prefill、是否端到端、统计窗口是否是完整 benchmark 还是 decode-only。如果是 vLLM benchmark 工具输出，补充具体参数、并发度、prompt / output length、采样参数、warmup 是否剔除、是否固定 seed，以及 baseline 和 optimized 是否使用相同输入和环境。

spec=3 时：一次 target verification 理论上最多可以接受多个 draft token，并可能有 bonus / guaranteed token 口径差异，所以面试里不能简单说 acceptance length 一定是 1 到 3。实际 mean accepted length 达不到上限，是因为越往后的 draft token 分布偏差越大，acceptance rate 通常递减，同时 draft 生成、target verification、sampler 和 prepare_inputs 都有额外开销。

如果面试官质疑公平性，优先补充五类条件：

  1. 模型和权重版本一致
  2. 相同 prompts / output length / sampling params / seed
  3. 相同 batch size / 并发度 / max tokens / num_spec_tokens
  4. 相同硬件、驱动、MindSpore / vLLM 版本和 warmup 状态
  5. 同时报告 acceptance rate / accepted length、TTFT、TPOT、throughput、P95/P99、显存、logits 对齐和质量回归

MT-Bench 前 80 轮只适合作为早期 smoke test 和通用问答验证。上线前还要补：真实流量 replay、不同 context length / output length bucket、长上下文、代码生成、NL2SQL、needle retrieval、高并发混合负载，以及质量回归。

Q6.2【简历第7题】acceptance length / token acceptance rate 指标关系

问题：在 Ascend 910B 上 num_spec_tokens=2 时，mean acceptance length 达 1.63，token-1 / token-2 接受率分别为 70% / 47%。解释这三个指标之间的关系。

标准答案：

先明确统计口径：如果 accepted length 包含 target 本身保证推进的 token，那么 num_spec_tokens=2 时范围是 1 到 3；mean=1.63 表示每轮平均推进约 1.63 个输出 token。token-1 70%、token-2 47% 表明第二个位置接受率明显下降，所以继续增大 spec token 可能边际收益下降。

mean acceptance length 的取值范围取决于统计口径：

  • 如果只统计 draft tokens，范围是 0 到 num_spec_tokens；
  • 如果包含 target guaranteed token / bonus token，范围可能是 1 到 num_spec_tokens+1。

mean acceptance length=1.63 不能简单解释为"平均 60% 接收率"，应该解释为每轮平均推进约 1.63 个 token，相比无投机每轮 1 个 token 有潜在收益，但实际收益还要看 draft/verification/rejection/runtime 开销。

七、系统设计

Q7.1【P1-9】通用 speculative runtime 设计

问题：如果设计一个不只支持 EAGLE-3 的 speculative runtime，你怎么拆模块？

标准答案：

至少拆四个模块：

  1. proposer：负责提出 candidate tokens 和 proposer-specific state。EAGLE-3 proposer 可以用 draft model 和 target hidden states；suffix / ngram proposer 可以用历史 token 或 CPU 逻辑，但对外都输出候选 token 和必要概率 / 状态。

  2. verifier：负责组织 target model verification 输入并执行 target forward。它不应该理解每个 proposer 的内部细节，只消费候选序列和通用 metadata。

  3. sampler：负责 accept / reject / recover sample，统一处理 target / draft probabilities、accept mask、final token。

  4. state manager：负责 request state、KV cache、accepted length、position、finished / EOS / stop、output commit 和 rollback / fallback。这个模块不能散落在 runner 各处。

容易绑死 EAGLE-3 的字段：

  • hidden states 这种 EAGLE 特有输入
  • draft model runner / extra model handle
  • request state 里混入某个算法专属字段

为了支持多 proposer，优先统一：target verification 链路 和 accept/reject + state commit 链路。

request 级状态：当前已确认序列长度、proposer 相关状态、已接受 token 数、finished / EOS / stop 状态、suffix cache 或 draft cache 等 request-local 状态。

batch 级状态：slot mapping、block table、batch 内 request index 映射、本轮 speculative length / accepted mask。

Q7.2【P1-10】Eagle3DraftInputBuilder 设计

问题：你会怎么设计 Eagle3DraftInputBuilder？

标准答案：

输入：target output tokens、target hidden states / auxiliary hidden states、scheduler metadata、seq_lens / q_seq_length、block_tables、draft KV state、num_spec_tokens、sampling params 和 request mapping。

输出：draft input_ids、position_ids、attention_metadata、slot_mapping、block_table、request offsets、token offsets，以及必要的 hidden states view / gather 结果。

assert 应覆盖：shape、dtype、device、slot_mapping 必须为 int32、position 单调、slot 不越界、request 边界不串、EOS / finished request 不进入 builder、batch 内 offsets 和 token 数一致。

debug dump 不应污染主链路：最好做成可配置的 dump hook，按 request id / step / tensor name 输出，并能固定 seed 复现。

八、补充项目

Q8.1【P1-7】KV-Select 稀疏化项目

问题：KV-Select 省的是哪部分成本？怎么证明不是用质量换速度？

标准答案：

KV-Select 主要减少长上下文 decode 阶段 attention 对历史 KV 的计算和访存压力。收益不只是 attention score FLOPs 下降，更关键的是减少历史 KV cache 读取带来的带宽压力；显存占用和调度开销未必是主收益。

sign-bit / hamming-topk 的直觉：用便宜的二值近似相似度先做粗筛，避免对全部历史 KV 都计算完整 attention score 和全量排序。具体是通过当前 query 与历史 key 在随机超平面空间的哈希投影，比较 sign-bit 二值码的一致程度（通常用异或 / popcount 得到距离或相似度），再做 TopK。它适合长上下文、并发较高、KV 访存压力明显的场景。

质量验证不能只看吞吐，至少看三类：

  1. 长上下文检索类，如 Needle-in-a-Haystack
  2. 代码生成 / NL2SQL 这类高精度结构化任务
  3. 多轮对话或长文问答的一致性和事实保真

还要扫 TopK、context length、batch size，并记录质量下降边界。

生产上最担心两个失败模式：

  1. 漏掉远距离关键 token 导致答案错误
  2. 局部相似性偏置导致忽略全局依赖

代码生成、NL2SQL、法律/金融等高精度场景要谨慎启用。

Q8.2【P1-8】Suffix Decoding 项目

问题：Suffix Decoding 在 request 级需要维护什么状态？收益边界在哪里？

标准答案：

Suffix decoding 更适合高重复输出或模式化输出场景。

request 级状态至少包括：

  • generated token history
  • match pointer
  • candidate suffix tokens
  • 当前匹配长度
  • 上轮是否命中
  • 用于回退的普通 decode 状态

收益来自直接复用或预测重复 suffix，减少 target decode step。

边界：短输出、低重复、高熵生成、强采样或用户输入变化很大时，命中率低，额外匹配开销可能抵消收益。

和 EAGLE-3 一样，动态启停必须在 step 边界做，不能在候选生成和验证中间切换；fallback 后 request state、KV cache 和 output commit 必须保持一致。

九、代码级追问：slot_mapping 公式推演

Q9.1【PR第16题】block_size=16, positions=[16,17,18], block_ids=3

问题：

  1. 这三个 token 的 block 内 offset 分别是多少？
  2. 对应的 slot_mapping 分别是多少？
  3. 如果 position 是 [15,16]，它们分别落在哪个 block 内 offset？为什么这是边界高风险点？
  4. 如果 clamped_positions % block_size 写错成 clamped_positions / block_size，会出现什么错误？
  5. 如果 block_ids 对了但 positions off-by-one，slot_mapping 会怎么错？

标准答案：

  1. [16,17,18] % 16 = [0,1,2]，block 内 offset 分别是 0、1、2。
  2. 公式是 block_ids * block_size + offset。block_ids 都是 3，block_size=16，所以 slot_mapping 是 [3*16+0, 3*16+1, 3*16+2] = [48,49,50]。不是 [0,1,2]（这是常见错误，把 offset 当成 slot_mapping）。
  3. position 15 的 offset 是 15；position 16 的 offset 是 0，并且逻辑上进入下一个 block。这个边界容易出错，因为 % block_size 从 15 回到 0，同时 block_id 必须同步切换。
  4. 把 % 写成 /，offset 不再是 block 内位置，而变成 block 序号或浮点/整除结果，会导致同一个 block 内多个 token 映射到错误 slot，KV cache 读写地址整体错乱。
  5. position off-by-one 会让 slot mapping 前移或后移一个 slot，表现为覆盖旧 KV、跳过新 KV、读错上下文，最终 logits 和接受率异常。

Q9.2【PR第17题】block_table 跨 block 映射

问题：block_size=16，logical positions=[15,16,17]，block table：

logical block 0 -> physical block 3
logical block 1 -> physical block 8
  1. 这三个 position 分别属于哪个 logical block？
  2. 对应的 physical block id 分别是多少？
  3. 三个 position 的 block 内 offset 分别是多少？
  4. 最终 slot_mapping 应该是多少？
  5. 如果代码错误地认为三个 token 的 block_ids 都是 3，会发生什么？

标准答案：

  1. 15 // 16 = 0，16 // 16 = 1，17 // 16 = 1。
  2. logical block 0 映射到 physical block 3，logical block 1 映射到 physical block 8，所以 physical block ids 是 [3,8,8]。
  3. offset 是 [15,0,1]。
  4. 最终 slot mapping 是 physical block 展平地址：[3*16+15, 8*16+0, 8*16+1] = [63,128,129]。不是 [15,0,1]。
  5. 如果错误地认为三个 token 的 block_ids 都是 3，那么 position 16、17 会写到 physical block 3 的 offset 0、1，也就是 slot [48,49]，而不是 physical block 8 的 [128,129]。这会覆盖或污染另一个逻辑位置的 KV cache，导致后续 attention 读错。

记忆点：面试时先列三列（logical block、physical block、offset），最后再算 slot。最终公式永远是 slot = physical_block_id * block_size + offset。

Q9.3【PR第18题】多 batch slot_mapping

问题：batch size=2，block_size=16：

request0: physical block id = 3, position = 16
request1: physical block id = 8, position = 16
  1. 两个 request 的 block 内 offset 分别是多少？
  2. 两个 request 的正确 slot_mapping 分别是多少？
  3. 如果 dtype / 算子路径错误导致 request1 也读写到 request0 的 slot，会表现成什么现象？
  4. 为什么这种错误可能让"第一个 batch 正常，后面的 batch 得到相同错误结果"？
  5. 你会 dump 哪两个 tensor 最快证明两个 request 被映射到了同一个 physical slot？

标准答案：

  1. 两个 request 的 position 都是 16，16 % 16 = 0，所以 block 内 offset 都是 0。
  2. request0 的 physical block id 是 3，slot 是 3*16+0=48；request1 的 physical block id 是 8，slot 是 8*16+0=128。正确 slot_mapping 是 [48,128]。不是 [0,0]。
  3. request1 如果也读写到 request0 的 slot，会导致 request1 attention 使用 request0 或错误位置的 KV cache，表现为 request1 logits/hidden states 和自身单 batch 不一致，甚至多个后续 batch 得到相同错误输出。
  4. 第一个 batch 对应的物理 slot 恰好被错误路径命中，所以它看起来正常；后面的 batch 本应映射到不同 physical block，但错误 dtype/索引路径让它们读到同一段错误 slot 或低地址 slot，所以结果一致地错。
  5. 最快应该同时 dump slot_mapping 数值和对应 physical KV cache block 的读写变化。只 dump KV cache 不 dump slot_mapping，很难直接证明是映射到同一 slot。

Q9.4【PR第19题】4 token slot_mapping 练习

问题：block_size=16，4 个 token：

physical_block_ids = [0, 1, 3, 8]
positions = [0, 17, 31, 32]
  1. 每个 token 的 block 内 offset 是多少？
  2. 每个 token 的最终 slot_mapping 是多少？
  3. 哪个 token 正好处在 block 边界之后？
  4. 如果只 dump offset，会误判什么？
  5. 面试时你会用哪一句话区分 position、offset、slot_mapping？

标准答案：

  1. offset 是 [0,1,15,0]。
  2. 最终 slot：
  • 0*16+0=0
  • 1*16+1=17
  • 3*16+15=63
  • 8*16+0=128
  1. position 17 是 block 边界之后的 token；position 32 也是新 block 的起点。更严谨地说，17 是越过 16 边界后的第二个位置，32 是另一个 block 边界起点。
  2. 只 dump offset 会丢失 physical block 信息，无法判断最终读写的是哪个物理 KV cache slot。
  3. "position 是 request 逻辑序列里的 token 位置，offset 是 position 在当前 block 内的相对位置，slot_mapping 是结合 physical block id 后得到的 KV cache 物理 slot 地址。"

十、代码级追问：prepare_inputs / rejection_sampler 融合

Q10.1【PR第4题】prepare_inputs 小例子现场推

问题：batch size=3，每个 request 本轮 query token 数分别是 [2, 3, 1]。

  1. sum_query_lengths 应该长什么样？
  2. 如果 output_index 表示每个 token 在对应 request 内的相对位置，它最终应该是什么？
  3. 如果还要叠加每个 request 的起始 position，比如起始 position 是 [10, 20, 30]，那最终 position index 应该是什么？
  4. 原来用 arange + slice 怎么生成这些值？融合 kernel 又是怎么避免这些小 op 的？
  5. 这个例子里最容易出现 off-by-one 的地方在哪里？

标准答案：

  1. [2,5,6]（cumulative end offsets）。如果实现需要 start offsets，通常会再补一个前导 0，得到 [0,2,5,6]。
  2. [0,1,0,1,2,0]（每个 request 内部从 0 开始编号，按 batch 拼平）。
  3. [10,11,20,21,22,30]（request 起始 position + request 内相对位置）。
  4. 原实现会对每个 request 循环，根据 start = prefix[i-1]、end = prefix[i] 生成 arange(0, end-start)，再加上该 request 的起始 position，最后 slice 写到输出 tensor 的 [start:end]。融合 kernel 则让每个 token index 根据 prefix 找到所属 request，再直接计算 token_idx - request_start + position_start，避免 Python loop、多个 arange、slice 写回和小 kernel launch。
  5. 最容易 off-by-one 在三个边界：cumulative offsets 是 end-exclusive 还是 inclusive；sum_query_lengths[i-1] 和 sum_query_lengths[i] 的边界；第 0 个 request 是否正确使用 start=0。

Q10.2【PR第10题】rejection_sampler 算子融合

问题：原始 rejection_sampler 里哪些步骤会产生很多小算子或 host/device 调度？

标准答案：

容易产生小算子的步骤（至少 4 个）：

  1. logits 处理和 softmax / probability 生成
  2. gather draft token 对应概率
  3. 比较 p/q 与随机数
  4. 生成 accept mask
  5. 找到第一次 rejected 位置
  6. 构造 recovered distribution
  7. sample recovered token
  8. 拼接/过滤最终 token

融合后输入输出 tensor：

  • 输入：target logits 或 target probs、draft probs、draft token ids、random uniforms、temperature/sampling params、num_spec_tokens、batch/request mask
  • 输出：accepted mask、recovered token ids、final sampled token ids、每个 request 的 accepted length

temperature=0 和 temperature>0 两条路径：可以分别走不同融合 kernel 或不同分支，关键是减少原来 Python / 多小算子的调度，不一定强行塞进一个超大 kernel。

correctness 验证分三类：

  1. greedy 路径：看 argmax/token 是否一致
  2. random 路径：固定随机数，比较 accept mask 和 final token
  3. recover sample 路径：构造必拒绝 case，比较 recovered distribution 和 recovered token

核心公式：

  • random accept 判断核心是 u <= min(1, p_target(draft_token) / p_draft(draft_token))
  • recover sample 核心是从 max(0, p_target - p_draft) 归一化后的分布采样

correctness 不只看最终 token，也要看 accept mask、accepted length、recover token 和 logits/probs 差异。

Q10.3【PR第12题】sampler 输出 accepted length 的作用

问题：为什么 sampler 需要输出 accepted length / valid token 数，而不是只输出 final token ids？

标准答案：

accepted length / valid token 数用于告诉 runtime 每个 request 本轮推进了多少 token，从而更新 request output、seq len、position、KV cache slot、下一轮 input、scheduler 状态，而不只是"批量输出 tokens"。

例子：

  • 如果一个 request 的 3 个 draft token 中前 2 个接受，第 3 个拒绝并 recover 了 1 个 token，那么本轮有效输出 token 数是 3 个（2 个 accepted draft token + 1 个 recovered token）。
  • 如果 3 个 draft token 全部接受，并且实现里支持 bonus token，那么本轮最多可能输出 4 个 token。

valid token 数影响的字段（至少 4 个）：output_token_ids、seq_lens、position_ids、slot_mapping/block_table，以及 request output buffer / finished state。

完整影响链路：output_token_ids -> seq_lens -> position_ids -> slot_mapping/KV cache -> next input_ids -> scheduler bookkeeping。

如果 valid token 数算错但 final token ids 看起来对：会导致下一轮 position、seq length、KV cache 地址、draft input 对不齐，可能表现为重复 token、跳 token、读错 KV cache、acceptance rate 异常或 logits 漂移。

十一、代码级追问：off-by-one 与状态推进

Q11.1【PR第14题】valid_token_num=[1,3,2] 的状态更新

问题：3 个 request 上一轮开始前的 seq_lens 分别是 [100, 200, 300]，sampler 本轮 valid token 数是 [1, 3, 2]。

  1. 本轮 commit 之后新的 seq_lens 应该是多少？
  2. 下一轮普通 decode 的 position_ids 应该是多少？
  3. 如果 request1 的 3 个有效 token 是 [a, b, c]，下一轮普通 decode 的 input_id 应该是哪个？
  4. 如果下一轮还要做 speculative verification，target verification 输入和普通 decode 输入有什么不同？
  5. 这个例子里 slot_mapping 应该按哪些 position 去算？

标准答案：

  1. commit 后新的 seq_lens 是 [100,200,300] + [1,3,2] = [101,203,302]。
  2. 如果 seq_len 表示已经确认的 token 数，下一个要生成/写入的新 token 的 position 就是当前 seq_len（0-based），所以普通 decode 下一轮 position 应该是 [101,203,302]，不是 [102,204,303]。
  3. request1 本轮有效 token 是 [a,b,c]，下一轮普通 decode 的 input token 应该取最后一个 confirmed token，也就是 c。
  4. 普通 decode 每个 request 通常只喂最后一个 confirmed token；speculative verification 则要把上一轮 proposer 生成的 draft tokens 也作为 target model 的验证输入，因此一个 request 可能喂多个 token，并且 position、slot_mapping、attention metadata 都要覆盖这些 draft 位置。
  5. slot_mapping 应按本轮 target model 实际要计算的 token positions 来算。普通 decode 是 [101,203,302] 这些下一个写入位置；speculative verification 则是每个 request 的 draft token 对应的一串 positions，例如 request1 如果要验证 3 个 draft token，就可能对应 [203,204,205]。

牢牢记住：seq_len 个 token，对应最后 position 是 seq_len-1，下一个 position 是 seq_len。seq_len+1 是跳过当前应该写入的位置；seq_len-1 是覆盖最后一个旧位置。

Q11.2【PR第15题】off-by-one 单测设计

问题：某个 request 目前已经确认了 5 个 token，它们的 position 是 [0,1,2,3,4]。

  1. 下一次普通 decode 要生成的新 token 的 position_id 应该是多少？
  2. 如果 speculative verification 要验证 3 个 draft tokens，它们的 position_ids 应该是多少？
  3. 如果代码错误地从 seq_len + 1 开始，会漏掉哪个 position？最终会导致什么现象？
  4. 如果代码错误地从 seq_len - 1 开始，会重复哪个 position？KV cache 会有什么风险？
  5. 你会用什么单测专门防这种 off-by-one？

标准答案：

  1. 5。已有 positions [0,1,2,3,4]，已确认 token 数是 5，下一次普通 decode 新 token position 是 5。
  2. [5,6,7]。验证 3 个 draft tokens 时，对应 positions 是 [5,6,7]。
  3. 如果从 seq_len + 1 开始，就是从 6 开始，会漏掉 position 5（不是 position 0）。结果是 KV cache / position 序列出现空洞，模型相当于跳过一个时间步，后续 attention 和 rope/position encoding 都会错。
  4. 如果从 seq_len - 1 开始，就是从 4 开始，会重复已经存在的 position 4，可能覆盖已有 KV slot 或让新 token 读写到旧位置，导致 KV cache 污染。
  5. 构造固定 seq_len=5、spec_len=3 的单测，断言 ordinary decode position 是 [5]，verification positions 是 [5,6,7]，slot_mapping 对应连续新 slot；再测试 valid_token_num=[1,3,2] 的多请求 case，确保每个 request 独立推进。

基础概念

FA-Q1 标准Self-Attention 的计算流程、时间和空间复杂度

问题：标准 Self-Attention 的计算流程是什么？时间和空间复杂度分别是多少？

标准答案：

计算流程：

  • Q = XW_Q, K = XW_K, V = XW_V（线性投影）
  • S = QK^T / √d_k（注意力分数矩阵 N×N）
  • P = softmax(S)（注意力权重矩阵 N×N）
  • O = PV（输出矩阵 N×d）

复杂度：

  • 时间复杂度：O(N²d)，其中 N 为序列长度，d 为头维度
  • 空间复杂度：O(N²)，需要存储中间矩阵 S 和 P（均为 N×N）

瓶颈：当 N 很大时（如长文本），N×N 的中间矩阵会消耗大量 HBM（GPU 显存），成为 memory-bound 操作。

FA-Q2 IO 感知算法与 GPU 存储层次

问题：什么是 IO 感知（IO-aware）算法？为什么 GPU 计算需要考虑 IO？

标准答案：

GPU 多级存储层次结构（A100）：

存储层级 容量 带宽 延迟
SRAM (Shared Memory / L1) ~20 MB ~19 TB/s 极低
HBM（显存） 40/80 GB ~1.5 TB/s 较高
主机内存 数百 GB ~64 GB/s (PCIe) 高

核心矛盾：GPU 的算力（FLOPs）增长远快于显存带宽的增长。大量算子在等待数据搬运而非计算，属于 memory-bound。

IO 感知算法的核心思想：通过重新设计算法的数据访问模式，尽量减少 HBM ↔ SRAM 之间的数据搬运次数（减少 IO），使算子从 memory-bound 转变为 compute-bound。

Flash Attention 核心原理

FA-Q3 Flash Attention 的核心思想

问题：Flash Attention 的核心思想是什么？

标准答案：

Flash Attention 的核心思想有两点：

1. Tiling（分块计算）：将 Q、K、V 矩阵分成小块（block），每次只加载一小块到 SRAM 中计算，避免将完整的 N×N 矩阵 S 和 P 写入 HBM。

# 标准 Attention:
全量 S=QK^T -> 写回 HBM -> 读回算 softmax -> 写回 HBM -> 读回算 PV

# Flash Attention:
对每个 Q 的 block, 循环遍历 K/V 的 block, 在 SRAM 中完成全部计算

2. Recomputation（重计算 / 反向传播时不存中间矩阵）：前向传播时不存储完整的 S 和 P 矩阵，反向传播时根据 Q、K、V 重新计算，用计算量换内存。

FA-Q4 分块情况下如何正确计算 Softmax（Online Softmax）

问题：Flash Attention 如何在分块（Tiling）的情况下正确计算 Softmax？

标准答案：

这是 Flash Attention 最精巧的部分——Online Softmax。

标准 softmax 需要遍历所有元素两次：

  1. 第一遍：求 max（数值稳定性）
  2. 第二遍：求 ∑exp(x − max)

这在分块计算时不可行，因为处理第 i 个 block 时还不知道全局 max。

Online Softmax 的解决方案（基于 Milakov & Gimelshein, 2018）：维护两个 running statistics：

  • m_i：当前已处理 block 的最大值
  • l_i：当前已处理 block 的指数和

每处理一个新的 block j：

m_new = max(m_old, max(S_ij))
P_ij = exp(S_ij − m_new)
l_new = exp(m_old − m_new) · l_old + ∑P_ij
O_i  = diag(exp(m_old − m_new)) · O_i + P_ij · V_j

关键：通过 exp(m_old − m_new) 这个修正因子，对之前累积的统计量进行"回溯修正"，使得分块计算结果与全量 softmax 数值等价。

FA-Q5 Flash Attention 前向传播完整伪代码

问题：请给出 Flash Attention 前向传播的完整伪代码。

标准答案：

# 输入: Q(N x d), K(N x d), V(N x d), 存储在 HBM
# 输出: O(N x d), 存储在 HBM
# block 大小: B_r (Q 的行 block), B_c (K/V 的行 block)

O = zeros(N, d)                    # 在 HBM 中
l = zeros(N)                       # softmax 分母
m = -inf(N)                        # running max

for j = 0 to N/B_c - 1:            # 遍历 K, V 的 block
    K_j = K[j*B_c : (j+1)*B_c]     # 从 HBM 加载到 SRAM
    V_j = V[j*B_c : (j+1)*B_c]     # 从 HBM 加载到 SRAM

    for i = 0 to N/B_r - 1:        # 遍历 Q 的 block
        Q_i = Q[i*B_r : (i+1)*B_r] # 从 HBM 加载到 SRAM

        S_ij = Q_i @ K_j^T         # 在 SRAM 中计算

        m_new = max(m_i, rowmax(S_ij))
        P_ij = exp(S_ij - m_new)
        l_new = exp(m_i - m_new) * l_i + rowsum(P_ij)

        O_i = diag(exp(m_i - m_new)) @ O_i + P_ij @ V_j
        # 写回 HBM
        m_i = m_new, l_i = l_new, O_i = O_i

# 最终归一化
O = diag(1/l) @ O

FA-Q6 Flash Attention 的 IO 复杂度

问题：Flash Attention 的 IO 复杂度是多少？与标准 Attention 对比如何？

标准答案：

算法 HBM 访问量 说明
标准 Attention O(N²d + N²) 需要读写完整的 S 和 P 矩阵
Flash Attention O(N²d²/M) M 是 SRAM 大小

推导（设 block 大小 B_r = B_c = B）：

  • 外层循环 N/B 次，内层循环 N/B 次
  • 每次内循环：加载 Q_i (Bd) + K_j (Bd) + V_j (Bd)，写回 O_i (Bd)
  • 总 IO ≈ (N/B)² × Bd = N²d/B
  • 取 B = M/d（使 block 能放入 SRAM），得 IO = O(N²d²/M)

关键结论：IO 关于 N 是次二次的（d²/M 通常远小于 1）。对于 A100（M ≈ 100 KB 可用 SRAM，d = 64–128），Flash Attention 显著减少 HBM 访问。

反向传播与重计算

FA-Q7 Flash Attention 的反向传播

问题：Flash Attention 的反向传播如何处理？为什么不存储完整的注意力矩阵？

标准答案：

标准 Attention 反向传播需要前向的中间矩阵 P（N×N），存储代价巨大。

Flash Attention 的策略——Recomputation：

# 前向: 只存储最终的 O, l, m（均为 O(N) 大小，不存 P 的 O(N²)）
# 反向: 利用 Q, K, V 重新计算 S 和 P（同样使用 tiling 策略）

为什么可行：

  • S = QK^T / √d 可以直接从 Q, K 重算
  • P = softmax(S) 可以从 S 重算
  • 额外计算量约等于一次前向传播
  • 但节省的 HBM 读写量远大于重算代价

实际效果：在 A100 上，重算的 FLOPs 增加约 2×，但由于减少了 HBM 访问，整体 wall-clock 时间反而更快（memory-bound → compute-bound）。

Flash Attention 2

FA-Q8 Flash Attention 2 的改进

问题：Flash Attention 2 相比 Flash Attention 1 做了哪些改进？

标准答案：

改进点 Flash Attention 1 Flash Attention 2
循环顺序 外层遍历 K/V，内层遍历 Q 外层遍历 Q，内层遍历 K/V
非 matmul FLOPs 在 inner loop 中做 rescaling 将 rescaling 移到 outer loop
并行化 在 batch 和 head 维度并行 增加序列长度维度的并行
warp 利用 未优化 warp 间工作分配 优化 warp 间分工，减少 shared mem 读写
性能(A100) 理论 FLOPs 的 25–35% 理论 FLOPs 的 50–73%

核心改进详解——调换循环顺序：

# FA1: outer=K/V, inner=Q  → 每个 Q block 都要做 rescaling
for j in K_blocks:
    for i in Q_blocks:
        rescale O_i                    # 频繁 rescale

# FA2: outer=Q, inner=K/V  → 一个 Q block 处理完所有 K/V 后才做最终 rescale
for i in Q_blocks:
    for j in K_blocks:
        accumulate O_i
    # 只在最后 rescale 一次

好处：

  1. 减少 rescaling 次数（从 N/B 次降到 1 次）
  2. 更好的数据局部性（一个 Q block 持续留在寄存器中）

FA-Q9 Flash Attention 2 如何优化 warp 利用率

问题：Flash Attention 2 是如何优化 warp 利用率的？

标准答案：

GPU 中一个 Thread Block 由多个 warp（32 线程为一组）组成。

FA1 的问题：所有 warp 协作计算同一个 Q_i K_j^T，warp 之间需要同步和 shared memory 通信。

FA2 的优化：

  • 将 Q_i 的行切分给不同 warp
  • 每个 warp 独立负责 Q_i 的一部分行与完整的 K_j 做 matmul
  • warp 之间无需同步（因为各自算各自行的 attention）
  • 减少了 shared memory 的读写（数据更多留在寄存器中）
Warp 0: Q_i[0:4]   @ K_j^T -> O_i[0:4]     # 各自独立
Warp 1: Q_i[4:8]   @ K_j^T -> O_i[4:8]
Warp 2: Q_i[8:12]  @ K_j^T -> O_i[8:12]
Warp 3: Q_i[12:16] @ K_j^T -> O_i[12:16]

Flash Attention 3（Hopper 架构）

FA-Q10 Flash Attention 3 针对 Hopper（H100）的优化

问题：Flash Attention 3 针对 Hopper（H100）架构做了哪些优化？

标准答案：

H100 引入了几个关键硬件特性：

  1. WGMmma（Warp Group MMA）——Tensor Core 异步指令：可以在后台执行矩阵乘法（不阻塞线程），FA3 利用这一点实现计算与数据搬运的重叠（overlap）。

  2. TMA（Tensor Memory Accelerator）：专用硬件单元负责 HBM ↔ SRAM 的数据搬运，释放线程来做计算。

  3. FA3 的核心策略——流水线化（Pipelining）：

# 时间步 t:
TMA:     加载 block t+1 到 SRAM              # 异步
WGMmma:  计算 block t 的 matmul               # 异步, 后台
Threads: 对 block t-1 做 softmax/rescale      # 同步

三级流水线：数据加载、矩阵乘法、非 matmul 计算同时进行。

性能：在 H100 上达到理论 FLOPs 的 75–82%。

实际应用与变体

FA-Q11 Flash Attention 的适用场景

问题：Flash Attention 对哪些场景最有效？哪些场景不适用？

标准答案：

最有效的场景：

  • 长序列（N 大），如 Longformer、长文档处理
  • 大 batch size + 大模型 → 显存成为瓶颈时
  • 训练阶段（需要存储激活值做反向传播）
  • 需要精确 attention（非近似）的场景

不太适用 / 需要注意的场景：

  • 非常短的序列：overhead 可能大于收益
  • 需要稀疏 attention pattern：FA 默认是 dense 的（但有变体支持 masking）
  • 非标准 attention：如 linear attention、performer 等已有 O(N) 复杂度的变体
  • 推理阶段（decode）：每次只生成一个 token，此时用 PagedAttention（vLLM）更合适

FA-Q12 Flash Attention 与 xFormers、PagedAttention 的关系

问题：Flash Attention 与 xFormers、PagedAttention 的关系和区别？

标准答案：

特性 Flash Attention xFormers PagedAttention
核心方法 Tiling + Online Softmax + Recomputation 类似 tiling，实现不同 KV cache 分块管理（类似虚拟内存）
目标 减少 HBM IO 减少显存占用 减少推理时 KV cache 显存碎片
主要阶段 训练 + 预填充 训练 + 预填充 推理（decode）
精确性 精确 精确 精确
框架 独立 CUDA kernel PyTorch 生态 vLLM 推理框架

关键区别：

  • Flash Attention 优化的是单次 attention 计算的 IO
  • PagedAttention 优化的是多次 decode step 之间 KV cache 的显存管理（解决碎片和浪费问题）
  • 两者可以互补：预填充用 Flash Attention，decode 用 PagedAttention

FA-Q13 Causal Mask 的处理

问题：Flash Attention 如何支持 Causal Mask（因果遮罩）？

标准答案：

Causal Attention 要求位置 i 只能 attend 到位置 ≤ i 的位置，即 S[i][j] = −∞ 当 j > i。

Flash Attention 中的处理方式：

for i in Q_blocks:
    for j in K_blocks:
        # 判断当前 block 对 (i, j) 的关系
        if j_block_end > i_block_end:
            continue                          # 完全在未来 → 整个 block 跳过
        elif j_block_start > i_block_start:
            S_ij[:, j_col > i_row] = -inf      # 部分在未来 → 在 SRAM 中对未来位置设置 -inf mask
        # else: 完全在过去 → 无需 mask
        # 正常执行 online softmax + accumulate

优化点：

  • 完全被 mask 的 block 直接跳过（节省约 50% 计算量）
  • 部分 mask 的 block 只在边界处应用 mask

深层理解与延伸问题

FA-Q14 为什么 Flash Attention 是精确的而非近似的

问题：为什么 Flash Attention 是精确的（exact）而非近似（approximate）的？

标准答案：

虽然 Flash Attention 使用了分块计算和重计算，但其结果是数值等价的（在浮点精度范围内），原因：

  1. Online Softmax 是精确的：数学上可以证明，online softmax 的递推公式与全量 softmax 的结果完全一致
  2. 矩阵乘法的分块是精确的：PV = ∑_j P_j V_j，分块求和与全量求和结果相同
  3. 重计算是确定性的：S = QK^T 和 P = softmax(S) 的重算结果与前向传播完全一致

注意：浮点数的结合律不严格成立，所以实际上可能存在极小的数值差异（~10⁻⁶），但对训练和推理没有实质影响。

FA-Q15 Block size 的选择

问题：Flash Attention 的 block size 如何选择？选择的依据是什么？

标准答案：

Block size 的选择需要在多个因素之间平衡。

约束条件：

B_r · d + B_c · d + B_r · B_c + B_r · d ≤ M   (SRAM 大小)

其中各项分别对应 Q_i、K_j、S_ij、O_i 的存储需求。

选择策略：

  • SRAM 容量上限：block 越大，SRAM 中能放下的数据有限
  • 越大越好（减少 IO 次数）：block 大 → 循环次数少 → HBM 访问少
  • 但不能太大（SRAM 放不下）：溢出到 HBM 反而更慢
  • 考虑硬件对齐：block 大小需要对齐 Tensor Core tile size（如 16×16 的 MMA tile）

典型值（A100, d = 128）：

  • Flash Attention 1: B_r = 128, B_c = 128
  • Flash Attention 2: B_r = 128, B_c = 256（利用更大的 SRAM）

FA-Q16 从 memory-bound 到 compute-bound

问题：如何理解 Flash Attention 将 attention 从 memory-bound 转变为 compute-bound？

标准答案：

Roofline Model 分析：

计算强度 (Arithmetic Intensity) = FLOPs / Bytes accessed from HBM

# 标准 Attention:
FLOPs      = 4N²d
HBM Bytes  = O(N²)                # 存储S和P
AI         = 4d / N  →  N 大时极低  →  memory-bound

# Flash Attention:
FLOPs      = 4N²d
HBM Bytes  = O(N²d²/M)
AI         = 4M / d  →  与 N 无关! →  compute-bound
  • 标准 Attention 的操作点位于带宽瓶颈区（Roofline 图的斜坡部分）
  • Flash Attention 的操作点向右移动，进入算力瓶颈区（平坦部分）

这意味着：增加算力就能线性提升性能，而非被带宽限制。

FA-Q17 MHA / MQA / GQA 的处理

问题：Flash Attention 对 MHA、MQA、GQA 分别如何处理？

标准答案：

类型 K/V head 数 Flash Attention 处理
MHA 与 Q head 相同 每个 head 独立计算，完全并行
MQA 所有 Q head 共享 1 组 K/V 所有 Q head 复用同一个 K/V block
GQA Q head 分 G 组，每组共享 K/V 每组内 Q heads 复用 K/V

GQA/MQA 与 Flash Attention 的结合：

  • K/V 的 HBM 访问量减少 G 倍（GQA）或 H 倍（MQA）
  • 进一步降低了 IO，提升了整体性能
  • 现代大模型（如 Llama 3、Mistral）普遍采用 GQA + Flash Attention

FA-Q18 FlashDecoding / Flash-Decoding++

问题：FlashDecoding / Flash-Decoding++ 解决什么问题？

标准答案：

问题场景：在推理的 decode 阶段，Q 只有一行（当前生成的 token），但 KV cache 可能很长。

Flash Attention 在 decode 阶段的问题：

  • Q 只有 1 行，无法在序列维度做 tiling
  • 如果 batch × heads 数量小，GPU 利用率低

FlashDecoding 的解决方案：

  • 在 KV cache 的序列维度上做并行
  • 每个 thread block 处理 KV cache 的一段
  • 最后做 reduce 合并各段的结果
KV Cache: [k1, k2, k3, ..., k_N]
   |
   v
Block 1: k1..k_B   → partial_O_1
Block 2: ...        → partial_O_2
Block P: ...        → partial_O_P
   |
   +--- reduce ---+  → final_O

Flash-Decoding++ 进一步优化：

  • 对 softmax 的 rescaling 做了更细粒度的优化
  • 统一了 prefill 和 decode 的实现
  • 在长 context 推理场景下性能提升显著

FA-Q21 Flash Attention 的局限性与未来改进方向

十三、DFlash 原理与工程实现（知乎检索）

来源：知乎检索（zhihu-search 技能），76 篇文章去重后提炼 论文：DFlash: Block Diffusion for Flash Speculative Decoding（ICML 2026, arXiv:2602.06036, UC San Diego / z-lab） 与前面章节的关系：DFlash 是 EAGLE-3 之后的新一代投机解码方案，用并行块扩散取代自回归起草，与候选人简历的 EAGLE-3 经验直接对比。

DF-Q1 DFlash 的核心思想是什么？

问题：DFlash 的核心思想是什么？它解决了 EAGLE-3 的什么瓶颈？

标准答案：

DFlash = 块扩散（block diffusion）并行起草 + KV 注入（KV injection）。

它解决的 EAGLE-3 瓶颈：

  • EAGLE-3 的 draft model 仍是自回归的——逐 token 生成，draft 延迟随候选长度线性增长。
  • 高并发下（batch size > 8）EAGLE-3 性能急剧下滑：投机推理的额外验证开销与显存占用让系统从计算受限转为访存受限，吞吐甚至会低于不用投机解码的原生推理。

DFlash 的两板斧：

  1. 块扩散并行起草：一个极小的非自回归 draft 模型一次前向并行吐出一整块草稿 token（默认 block_size=16，LLaMA 3.1 为 10），消除自回归等待。
  2. KV 注入：把 target 模型多层 hidden states 投影后直接写进 draft 的 KV cache 每一层，让深草稿模型也能获得一致且强烈的 target 信息条件约束，消除信号衰减。

关键数据（Qwen3-8B）：DFlash 实现 6× 无损加速，是 EAGLE-3 的 2.4 倍；代码生成场景平均单轮确认 6-7 个 token，远超 EAGLE-3 的 2-3 个。

DF-Q2 DFlash 的 Block Diffusion 训练策略

问题：DFlash 的块扩散训练是怎么做的？随机锚点是什么？

标准答案：

块大小：默认 16（LLaMA 3.1 为 10）。

训练时的随机锚点策略：

  • 随机选择 2 个位置作为"锚点"——这两个位置不被遮罩，保持可见。
  • 其余 14 个位置全部遮罩。
  • 草稿模型基于锚点 token 和目标模型注入的特征，并行预测所有遮罩位置。
  • 这种随机锚点策略迫使模型学会从任意已知 token 出发推理整块内容，泛化能力更强。

block size 的训推泛化（论文 Table 8）：

  • 大 BS 训练能泛化到小 BS 推理（OK）
  • 小 BS 训练不能泛化到大 BS 推理（不行）
  • 论文把"自适应 block size 调度"留作 future work。

DF-Q3 KV Injection 与输入端拼接的区别

问题：DFlash 的 KV Injection 和 EAGLE-3 的输入端拼接特征有什么本质区别？为什么更优？

标准答案：

EAGLE-3（输入端注入）：把 target hidden state 拼接到 draft model 输入 embedding 上，只在第一层注入。深层 draft 网络的信号衰减严重——越往后越弱。

DFlash（KV Injection）：把融合后的 target 特征直接注入到 draft 模型每一层的 Key 和 Value 投影中，并缓存在 KV Cache 里。这样深层 draft 网络也能获得一致且强烈的 target 信息条件约束。

消融实验（论文 Table 9）：

  • KV 注入在 AR 和 diffusion drafting 上都更优
  • 纯 5 层 block diffusion 草稿（不用 target feature）只有 2-3× 加速（Table 10）
  • 结论：DFlash 的加速不是 diffusion 本身带来的，而是"diffusion 并行 + target conditioning"的组合。

DF-Q4 DFlash 的 Non-Causal Attention

问题：DFlash 为什么用 non-causal attention？和 EAGLE-3 的 causal attention 有什么区别？

标准答案：

DFlash 默认 non-causal（causal=False），EAGLE-3 是 causal。

原因：mask token 之间不应有因果遮挡——它们是并行预测不同位置，互相独立，不存在"第 i 个依赖第 i-1 个"的关系。所以用 non-causal attention，让所有 mask 位置可以互相 attend。

代价：DFlash 使用 bidirectional attention，比 EAGLE-3 的 masked attention 计算量大。

DF-Q5 DFlash 在 vLLM 中的 CUDA Graph 设计

问题：DFlash 在 vLLM 中为什么只需要一套 FULL graph，而 EAGLE-3 需要两套？

标准答案：

EAGLE-3：prefill（draft step 0）和 decode（step 1+）形状不同，需要两套 graph。

DFlash：一个 graph manager 每步 query 数恒为 1 + N（固定：1 个 anchor + N 个 mask 位置），只需一套 FULL graph。

好处：

  • 减少图编译开销（只编译一次）
  • 简化 graph manager 逻辑
  • 固定 shape 避免动态 shape 触发的重新编图

mask token id：来自 dflash_config.mask_token_id，在 parallel_drafting_token_id 字段中指定。

DF-Q6 DFlash 草稿模型的层数与轻量化

问题：DFlash 的草稿模型有几层？为什么这么少？

标准答案：

DFlash 草稿模型 5-8 层 Transformer（vLLM 实现中为 5 层），参数规模严格控制。

对比 EAGLE-3：EAGLE-3 只有 1 层。

为什么 DFlash 可以用更多层：

  • DFlash 是并行的，延迟与层数线性但与块长解耦——5 层出 16 个 token 的延迟 < EAGLE-3 单层出 4 个 token 的延迟（EAGLE-3 要循环 4 次）。
  • KV Injection 让深层不衰减，所以深一点反而效果好。

消融（论文 Table 6）：8 层 τ（接受率）最高但延迟增加，5 层综合 speedup 最优（质量 vs 开销平衡）。

对比早期 diffusion drafter：DiffuSpec 曾用 7B 参数的庞大草稿模型——内存占用巨大，推理延迟甚至超过目标模型本身，完全不具备部署价值。DFlash 用实践证明：轻量 + 强引导远胜重量 + 弱引导。Qwen3.5-35B-A3B 仅增加约 42MB 额外参数。

DF-Q7 DFlash 与 Spec V2 的关系

问题：DFlash 和 SGLang Spec V2 是什么关系？Spec V2 相比 V1 改进了什么？

标准答案：

DFlash 是算法，Spec V2 是调度引擎——两者正交。

Spec V2 的核心：overlap scheduler（重叠调度器）

  • 把 host（CPU）端的清理与 KV 预分配，藏到 GPU 前向计算的背后
  • 靠 FutureMap、异步拷贝、双 CUDA stream 消除 host-device 同步点
  • 不改模型不改算法，获得 33%+ 吞吐提升

Spec V1 的问题：host-device 同步是推理性能的隐藏杀手——CPU 端清理/分配和 GPU 计算串行执行。

工程经验：

  1. 重叠即性能：Host-device 同步是隐藏杀手
  2. 即时物化 > 缓存：KV 投影产物不存储——即时完成即丢弃，零额外显存 + Radix Cache 前缀天然共享
  3. Triton Kernel 是必选项：层批量化 + Norm+RoPE 融合在单 kernel 内完成
  4. 块大小是核心调参项：block_size 4/8/16 需根据 workload benchmark 确定

DF-Q8 DFlash 的局限与边界

问题：DFlash 有哪些局限？

标准答案：

算法局限：

  1. 长块后段接受率衰减：虽然并行出 16 个 token，但越往后位置预测偏差越大——DSpark 正是为此而生。
  2. bidirectional attention 计算量大：比 EAGLE-3 的 masked attention 开销大。
  3. 每次重新计算：DFlash 输入 5 token，过一次 5 layer draft model——每一层都要重新计算全部 token；EAGLE-3 单 token 计算后可复用 hidden state 生成 KV cache，每层只算一个 token。
  4. 实际部署中不一定胜过 EAGLE-3：vLLM 实测中，设置 DFlash 和 EAGLE-3 一次性生成 5 token、接受率拉平后，DFlash 性能不如 EAGLE-3（因为 DFlash 每层计算量大）。

工程局限（SGLang 实现）：

  • 吞吐和延迟受 block_size、accept rate、headroom、page size、draft window size 影响
  • 显存压力随 block_size 增大

高并发场景：DFlash 比 EAGLE-3 好，但不是没有衰减——仍有 draft 额外显存占用问题。

十四、DSpark 原理与工程实现（知乎检索）

来源：知乎检索 论文：DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation（DeepSeek, 2026.06） 开源：DeepSpec 代码库（github.com/deepseek-ai/DeepSpec） 部署：DeepSeek-V4-Pro-DSpark 已上线真实流量

DS-Q1 DSpark 的核心思想

问题：DSpark 的核心思想是什么？它解决了 DFlash 和 EAGLE-3 的什么问题？

标准答案：

DSpark = 半自回归生成（Semi-Autoregressive Generation）+ 置信度调度验证（Confidence-Scheduled Verification）。

它解决的两个矛盾：

方案 生成模式 速度 后段接受率
EAGLE-3 纯自回归（逐 token 串行） 慢（draft 延迟随长度线性增长） 后段好（有依赖）
DFlash 纯并行（一次 forward 出整块） 快（O(1) draft 延迟） 后段衰减严重（无依赖）
DSpark 半自回归（并行骨干 + 轻量序列头） 快（保留并行骨干） 后段救回（序列头注入依赖）

DSpark 的洞察：

  • 并行块受 latency 约束、能堆深网络，在首 token上获得 0.10~0.19 的容量优势。
  • 这一首位容量优势足以弥补后续位置的衰减——整块平均接受长度被前几个位置主导。
  • 仅需 2 层 DSpark 即可超越 5 层纯并行 DFlash，证明注入极少量局部自回归远比无脑堆叠网络深度更具性价比。

实测数据（V4-Flash）：

  • 单用户生成速度提升 60%-85%
  • 高并发场景下有效吞吐量翻 4 倍
  • 输出无损（与原生串行 100% 一致）

DS-Q2 DSpark 的架构组件

问题：DSpark 的草稿模型有哪些组件？哪些冻结、哪些训练？

标准答案：

DSpark 草稿模型由 5 个部件组成：

部件 是什么 训练时 参数来源
Embedding 层 token id → 向量 冻结 从 target 拷贝、不动
并行骨干 几层 Transformer，吃 anchor + mask + 注入的 target 特征，一次前向出整块隐状态和基础 logits 训练 新初始化（5 层）
序列头（Markov/RNN） 给基础 logits 补依赖前缀的偏置，补回 token 间依赖 训练 新初始化（低秩 r=256）
置信度头 一个 Linear→1，预测每位的接受概率 训练 新初始化
LM head 隐状态 → 词表 logits 冻结 从 target 拷贝、不动

两个"冻结"的设计意图：

  1. 共用语义空间：draft 和 target 共用同一套"token id ↔ 向量 ↔ logits"语义空间，draft 算出的隐状态过同一个 LM head，分布天然和 target 在同一坐标系里可比，验证时的接受率才有意义。
  2. 省训练显存：LM head 是 [hidden × 词表] 的大矩阵（词表几万），冻结它省下大量训练显存和算力。

真正要学的只有中间三块——骨干、序列头、置信度头。

DS-Q3 半自回归生成（Semi-Autoregressive Generation）

问题：DSpark 的"半自回归"具体怎么实现？Markov Head 是什么？

标准答案：

流程（Step 0 + Step 1）：

Step 0：DFlash-style 并行生成

  • 通过一次 forward 快速得到多个 draft position 的 base logits。
  • 以生成 "How can I do it" 为例，当前前缀是 "How can"。Target LM 先正常 forward 并采样出 anchor token "I"。
  • DSpark 从 Target LM 多层 hidden states 中抽取并融合上下文特征 G_ctx = [g_how, g_can, g_I]。
  • 构造并行 draft block，预测 "do", "it" 等。

Step 1：Markov Head 串行修正

  • 把 Step 0 采样的 token 逐个输入 Markov Head，输出下一个 token 纠正后的概率变化。
  • 选择下一个 token 时，根据 MTP 的原始概率 + Markov Head 的纠正概率一起决定。
  • 纠正阶段是串行的，这就赋予了 MTP 一定的准确性。

Markov Head 是什么：

  • 一个小的感知机模块，计算非常快，耗时可以忽略不计。
  • 训练目标：让 Head 的输出每一个词的概率都和大的模型的输出尽量完全相同。
  • 实际上因为模块很小，输出概率不可能完全相同，只能接近，但做矫正也够了，能大幅度降低 MTP 导致的幻觉问题。

不用 RNN：DSpark 不用 RNN，而是用 Markov Head——把块内联合显式拆成条件乘积，注入极少量局部自回归。

输出 10 个 token 的句子只需前向传播 2-4 次，保留了 MTP 的速度。

DS-Q4 置信度头（Confidence Head）

问题：DSpark 的置信度头预测什么？为什么需要校准？

标准答案：

置信度头预测"前缀存活概率"：对每个草稿位置 k 输出一个标量 c_k ∈ (0,1)，含义是"在前面都被接受的前提下，位置 k 的 draft token 能通过验证的条件概率"。

公式：

c_k = σ(w^⊤ [h_k; W_1[x_{k-1}]])
c_k* = 1 - ½·‖p_k^d - p_k^t‖_1   (监督信号：draft 分布与 target 分布的总变差距离对应的解析接受率)

关键细节——要的是"绝对刻度"而不只是"排序"：

  • 很多阈值法只需要置信分能把 token 质量排对序就行。
  • 但 DSpark 的调度器要拿这些分数连乘算期望接受长度，必须是校准过的真概率。
  • 神经网络的置信普遍过度自信，所以作者加了一个后处理 STS（Sequential Temperature Scaling）。

STS（顺序温度缩放）：

  • 在验证集上从左到右、对累计连乘概率逐位做 1D 温度搜索
  • 最小化 ECE（Expected Calibration Error）
  • 温度缩放保序，不破坏已学到的排序
  • 把平均校准误差从 3%~8% 压到约 1%
  • 在线运行：系统边跑边调，根据当前工作负载的实际接受率动态修正阈值。代码任务跑多了，它就学会对代码草稿更宽容；聊天任务来了，自动收紧阈值。

DS-Q5 硬件感知前缀调度器（Hardware-Aware Prefix Scheduler）

问题：DSpark 的硬件感知调度器怎么工作？贪心早停为什么保证无损？

标准答案：

模型：

  • 设一个 batch 有 R 条活跃请求。
  • 因为投机解码只接受连续前缀，位置 j 能存活的概率是置信分的累乘：a_{r,j} = ∏_{i≤j} c_{r,i}。
  • 引入一条引擎吞吐曲线 SPS(B)（batch 为 B 时每秒能跑多少步，引擎启动时离线 profiling 一次、存成代价表、O(1) 查表）。
  • 调度器要最大化的是系统级期望吞吐。

贪心调度算法：

  1. 把所有候选 token 按存活概率从高到低排。
  2. 逐个尝试加入，每加一个算一下吞吐涨没涨。
  3. 涨了就留，不涨就停。

为什么"不涨就停"而不是继续试别的——这是无损性保证：

  • 推测解码要求"接受决策不能依赖未来 token"，否则会破坏精确的分布恢复（论文附录有数学反例证明）。
  • 早停机制确保了录取决策只依赖已经处理的前缀，维持了无损性。

负载自适应场景：

场景 并发条件 平均验证预算
V4-Flash 空闲 少于 200 并发 4~6 tokens/请求
V4-Flash 繁忙 多于 200 并发 自动收紧至 ~2 tokens/请求
V4-Pro 空闲 少于 150 并发 4~6 tokens/请求
V4-Pro 繁忙 多于 150 并发 自动收紧至 ~2 tokens/请求

并发低时调度器把静态 MTP-1 的 2 token 扩到 4~6，消耗空闲算力；并发高时自动收紧验证长度，保护批容量。

DS-Q6 DSpark 的无损性保证

问题：DSpark 如何保证最终输出分布与 target model 一致？

标准答案：

三个层面保证无损：

  1. 半自回归生成不影响 target 分布：半自回归、非自回归、纯自回归，主要说的是 draft 草稿生成方式，而不是说 target model 的生成分布变了。target verify 仍然是自回归分布。

  2. 置信度调度只决定"验多长"，不改 accept/reject 判定：调度器选的是"送多少 token 去验证"，但每个 token 的 accept/reject 仍由标准 rejection sampling 决定（接受概率 min(1, p/q)，拒绝从 max(0, p-q) recover sample）。

  3. 贪心早停的无损性：

  • 调度器"不涨就停"——但停掉的是后续 token 的验证，不是改变已验证 token 的接受判定。
  • 推测解码要求"接受决策不能依赖未来 token"。早停确保录取决策只依赖已经处理的前缀。
  • 论文附录有数学反例证明：如果继续尝试别的（非早停），会破坏精确的分布恢复。

实测：输出与原生串行生成 100% 一致。

十五、DFlash / DSpark / EAGLE-3 选型与对比

Sel-Q1 三种方案的本质区别

问题：DFlash、DSpark、EAGLE-3 三种方案的本质区别是什么？

标准答案：

三种方案的本质区别在于"生成速度（并行度）"与"草稿质量（接受率）"的权衡：

方案 生成模式 速度 后段接受率 核心机制
DFlash 纯并行 / 无修正 极快（O(1) draft 延迟） 崩塌严重 Block Diffusion，一次 forward 出整块
DSpark 半自回归 快（保留并行骨干） 后段救回 DFlash + Markov Head + 置信度调度
EAGLE-3 纯自回归 慢（随长度线性增长） 后段好 逐 token 循环 forward

DFlash 的本质：完全打破自回归依赖，用位置编码或修改 Attention Mask，在单次前向传播中强行"同时"预测未来多个位置。拥有极致的时间复杂度，但缺乏 Token 间的显式上下文依赖，预测长度越长，准确率崩塌越严重。

DSpark 的本质：半自回归——并行骨干网负责提供极致的速度，最终的"顺序头"（Sequential Head）像一位经验丰富的编辑，对并行产生的所有结果进行精细的校对和润色。

EAGLE-3 的本质：自回归——Draft 模型在生成候选 Token 时存在串行依赖，但每一步都有上下文依赖，后段质量好。

Sel-Q2 逐位置条件接受率曲线

问题：DSpark 论文用的"逐位置条件接受率"图说明了什么？

标准答案：

论文 Figure 2：横轴是 draft 块内位置（1 到 7），纵轴是该位置的条件接受率——只在前面都被接受的前提下，这个位置的 draft token 能被 target 接受的概率。

这张图讲了两件事：

  1. 位置 1 的容量优势：第一个 token 只依赖 target 上下文，胜负纯看架构容量。Eagle3 受 latency 约束只能用浅网络，而并行 drafter 是 latency 约束、可以上深网络——所以 DFlash 起点就比 Eagle3 高（Math 0.88 vs 0.81，Chat 类似）。

  2. 后段衰减：DFlash 从位置 2 开始急剧下降，Eagle3 衰减平缓。DSpark 的曲线在前几个位置保持 DFlash 的高起点，后段衰减明显比 DFlash 平缓，接近 Eagle3。

DSpark 的胜利点：并行块的首位置容量优势足以弥补后续位置的衰减——整块平均接受长度被前几个位置主导，导致并行草稿反而比自回归更优。

问题：什么场景用 DFlash，什么场景用 DSpark，什么场景用 EAGLE-3？

按场景选型：

场景 推荐方案 理由

Sel-Q4 DSpark 相对 EAGLE-3 的离线优势

问题：DSpark 相对 EAGLE-3 的离线优势是多少？为什么？

标准答案：

离线加速：DSpark 相对 EAGLE-3 +27%~31%。

根本原因（不是单纯堆更多 draft 层）：

  • DSpark 在 acceptance 曲线上同时取了 DFlash 和 Eagle3 两者之长——首位置用并行深网络拿容量优势，后段用序列头注入依赖救回衰减。
  • EAGLE-3 受 latency 约束只能用浅网络（1 层），而后段衰减虽然平缓，但起点低。
  • DSpark 用并行骨干突破首位置容量上限，用 Markov Head 补回后段依赖——两头都占。

Sel-Q5 MTP 与 speculative decoding 的关系

问题：MTP（Multi-Token Prediction）和 speculative decoding 是什么关系？

标准答案：

MTP 和 speculative decoding 经常一起出现，但二者作用在不同阶段：

  • MTP 首先是一种训练目标。标准 next-token prediction 在位置 t 只预测 x_{t+1}；MTP 在位置 t 同时预测 x_{t+1}, x_{t+2}, ..., x_{t+k}。
  • speculative decoding 是推理协议——用小模型先猜、大模型一次性验证。

关键区分：

  • MTP 可以不做 speculative decoding——额外模块可以直接丢弃。
  • speculative decoding 可以不用 MTP——候选也能来自独立小模型、EAGLE 或并行 drafter。
  • MTP 模块只有接入 Draft、Verify、Accept 流程后，才成为推测解码的一部分。

MTP head 能输出多个 logits，不代表这些 token 可以直接提交。尤其在采样场景中，额外 head 的输出分布和 target 的真实分布可能不一致，仍需 rejection sampling 校正。
