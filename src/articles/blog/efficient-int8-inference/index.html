01 · 一句话判断

真正的贡献不是“量化”，而是把量化变成编译器问题。

论文把瓶颈从数值格式一路追到权重布局、epilogue、kernel 选择和多实例部署，最终用 Roofline + Amdahl 把“为什么只能到 5.82×”讲清楚。

为什么只调用 torch._int_mm 不够？

原语只给 INT8×INT8→INT32 GEMM：权重可能要每次转 blocked layout，scale/bias/GeLU 需要另起算子，oneDNN 元数据也会反复构造。论文在 TorchInductor 中匹配子图，把它们压成一个带 epilogue 的 qlinear_pointwise，并把常量 layout conversion 在编译期折叠。

为什么还要 template kernel？

qlinear_pointwise 泛化好，但不对所有 M×K×N 都最优。Inductor 生成 AMX / AVX512_VNNI 候选，编译后做一次 micro-benchmark，按 shape 记住最快实现。这是“通用后端 + 形状特化”的折中。

我的工程解读

优先 static

线上输入分布稳定、吞吐优先时，把 scale 搜索、weight layout、补偿向量都搬到离线。

谨慎 dynamic

输入分布变化大时更灵活，但小模型或短序列可能被 per-row scale 搜索和 quant/dequant 开销吞掉收益。

先看 shape

同一硬件上 256×4096×1024 的 INT8/FP32 GEMM 上限 15.19×，比 256×1024×1024 的 9.35×高很多。

07 · 不能过度外推

论文的边界，也决定了你如何复现实验。

这些数字是经过精心设置的 server CPU 场景，不是所有推理请求的通用倍数。

1
批量与序列长固定batch=1、sequence length=256；改变形状会改变 kernel 选择、AI 和 LLC 行为。
2
多实例吞吐导向4 核/实例、跨物理核 pinning、weight sharing；单实例 latency 不等于这里的 RPS。
3
AOTI + AMP 是前提论文基线启用 AOTI；Granite Rapids 的 BF16 对照也通过 AMP。
4
线性块 ≠ 纯 GEMM它包含 bias、activation、residual 等 fused post-ops；表中的“GEMM speedup”是近似代理。
5
Ice Lake 有额外补偿s8→u8s8 转换需要 zero-point compensation；论文预计算它，但仍会影响实际收益。
6
Roofline 是上限，不是承诺Granite Rapids 上 static BERT 的端到端 5.82× 只兑现了 7.06× ceiling 的约 82%。
