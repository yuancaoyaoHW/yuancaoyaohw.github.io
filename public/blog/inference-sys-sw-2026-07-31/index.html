01服务层 Rust 化 — 吞吐上限

SGLang 在一天内合并了 7 个连续的 Rust server PR，覆盖从 tokenizer / detokenizer、HTTP API codec 到 runtime 线程模型的完整服务链路。vLLM 同步推进 Rust frontend。两个项目独立做出同样选择——推理引擎正在走数据库和浏览器引擎的路径：性能关键路径迁移到编译型语言，保留 Python 作为模型开发层。

Rust 服务层 vs Python 服务层 — Token 流转对比

PR #32872 — SGLang Rust Server: Tokenizer / Detokenizer / Egress

三个全新 Rust 模块，+3973 行，覆盖 token 编解码全链路：

模块行数职责

02Kernel 专用化 — 成本下限

vLLM 对 DSv4 的两个 PR 展示了推理优化进入成熟期的典型模式——不再增加新功能，而是从现有路径中挤出浪费。SGLang 的 SM90 DeepGEMM MegaMoE 则代表另一方向——在 H100/B200 上为 DSv4 FP8 铺设专用 A2A 路径。

Kernel 优化双路 — 减法 vs 加法

PR #50298 — DSv4 Kernel 1.88x：传 out tensor 消去冗余 kernel

核心改动：combine_topk_swa_indices 函数新增 out 参数，调用方传入预分配的 tensor，避免函数内部再做一次 torch.full kernel 调用。

# Before: 函数内部每次分配
combined_indices = torch.full((num_tokens, combined_topk), -1, ...)
combined_lens = torch.empty(num_tokens, ...)

# After: 调用方从 workspace manager 预分配
combined_indices, combined_lens = out  # 复用已有 buffer

为什么 1.88x：消除了每次 prefill chunk 的一个 torch.full kernel launch + 一个 torch.empty 分配。8192 token / C128A 配置下这是热路径。测试也从 zeros 改为 randn + 正确性验证。

PR #50312 — DSv4 PP Buffer：448 MiB 显存节省

PP last rank 上的 _mtp_hidden_buffer 之前无条件分配，现在只在 MTP 实际启用时分配：

# Before: 只要 is_last_rank 就分配
if get_pp_group().is_last_rank:
    self._mtp_hidden_buffer = torch.empty(
        max_num_batched_tokens, self.hc_dim, ...)

# After: 检查 speculative config 是否真的需要 MTP
needs_mtp = spec_config is not None and (
    spec_config.use_eagle() or spec_config.uses_draft_model())
if get_pp_group().is_last_rank and needs_mtp:
    self._mtp_hidden_buffer = torch.empty(...)

448 MiB = 8192 × 7168×4 × 2 bytes。对 NVIDIA / AMD / XPU 三条路径都做了同样修复。

03KV Cache 加固 — 规模化站稳

KV Cache 传输组件本周的合并揭示了一个清晰信号：它们已走出"功能能跑"阶段，进入"故障不崩"的生产硬化期。Mooncake 修多 NIC 竞态和 SIGBUS 硬崩溃，LMCache 用 Query tensor 让 token dropping 从随机变精准。

KV Cache 生产硬化 — EFA 竞态修复 + Token Dropping

PR #3177 — Mooncake EFA: CUDA Context 竞态修复

Bug 现象：fi_mr_regattr() on FI_HMEM_CUDA memory 间歇性失败，报 Operation not supported。失败后 buffer 从所有 NIC 上注销，后续 KV 传输报 remote session is not alive——错误指向远端，实际是本地注册失败。

Root cause（极为精彩的归因分析）：libfabric 的 cuda_get_dmabuf_fd() 调用 driver API cuMemGetHandleForAddressRange()，不做 context 管理，假设调用线程已有 current context。registerLocalMemoryBatch() 用 std::async(std::launch::async) per buffer，工作线程可能从未触碰 CUDA API → 没有 current context → dmabuf export 返回 CUDA_ERROR_INVALID_CONTEXT。libfabric 把它吞掉，最终变成 ENOTSUP。

间歇性：因为 std::async 可能复用线程，一个线程先注册了 device 0 的 buffer（绑了 context），再注册 device 3 的就复用了错误的 context。

Fix：调用 cuDevicePrimaryCtxRetain() 获取与 CUDA runtime 相同的 primary context，按 device ordinal 检查当前 context 是否匹配。retain 故意不释放（避免拆掉整个进程的 context）。

PR #3145 — Mooncake ShmTransport: SIGBUS 四连修

四个边界 case 修复，参考了 Ray Plasma 的 shared-memory lifecycle 模型：

  • CXL consumer 用了 O_CREAT：peer backing file 不存在时创建 0-byte 文件，mmap 后访问超越 EOF 触发 SIGBUS
  • Producer create 缺 O_EXCL：reopen 已存在 object 然后 ftruncate，导致另一个进程的 mapping 崩溃。修复：O_CREAT|O_EXCL + pid-qualified 名称重试
  • relocate_map_ 不清理 stale mmap：peer unregister 后旧 mapping 一直留着。修复：cache miss 时 munmap + erase
  • 清理配置中未使用的 async_memcpy_threshold

PR #4042 — LMCache: Query Tensor 捕获 + 精准 Token Dropping

前序 PR #3950 实现了随机 token dropping（decode 1.5x–1.7x 吞吐）。本 PR（+7917 行，42 文件）让 dropping 变聪明——用 Query tensor 决定哪些 token 该丢。

核心组件 QRingBuffer：GPU tensor [num_layers, num_blocks, block_size, hidden_dim]，paged 布局复用 LMCache 的 paged-KV 传输 kernel。通过 attn_metadata.slot_mapping 做行到 token 的精确匹配——continuous batching 下一个 step 的 Q tensor 拼了多个请求的行，需要精确归属。

信号：KV Cache 组件正从推理引擎的"插件"演变为有独立 release cycle 和 HA 机制的完整系统层。

04跨 PR 趋势分析

Rust 化不是"在改写"，是"在铺设"

SGLang 的 Rust server 不是把 Python 代码逐行翻译——它在构建一个全新的无锁服务层架构：ring buffer 通信、shard 分片、pinned thread。vLLM 的 Rust frontend 在做基础设施硬化（日志、错误链、readiness）。两个项目独立做出同一选择。

Kernel 优化"减法"和"加法"是两条路

路径代表 PR思路可维护性
减法vLLM #50298, #50312从已有路径消除浪费（去多余 kernel 调用、去无用分配）高——通用改进，不绑定模型/硬件
加法SGLang #29016为特定模型+硬件铺专用 fast path低——SM90+DSv4+FP8 三元绑定，换代要重写

vLLM 的两个"减法" PR 合计改动 68 行，但拿到 1.88x kernel 提速 + 448 MiB 省显存。SGLang 的"加法"PR 拿到 22% 吞吐提升，但代价是维护一条 DeepGEMM + SM90 + DSv4 + FP8 的专用路径。

KV Cache 从"插件"到"系统层"的转折点

维度MooncakeLMCache
阶段生产硬化性能突破
典型 bug多 NIC 竞态、SIGBUS 硬崩溃—
典型改进CUDA context 绑定、shm 生命周期Query ring buffer + smart token dropping
信号7×24 部署的 corner case 才暴露从有损换吞吐到精准丢弃

Mooncake 的两个修复最值得注意的不是代码量，而是 debug 难度——fi_mr_regattr 的 ENOTSUP 把 CUDA context 缺失的真实原因吞掉了，导致错误指向远端而非本地。这种"错误信息被多层抽象吞掉"的问题在系统软件成熟期反复出现。

一句话结论：推理引擎正从三个方向同时被系统软件化——服务层 Rust 化决定吞吐上限，Kernel 专用化决定成本下限，KV Cache 加固决定规模化能不能站稳。
