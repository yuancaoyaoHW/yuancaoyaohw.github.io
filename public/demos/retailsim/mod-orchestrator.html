编排层 · orchestrator

调度器：让所有模拟散户按同一只钟行动

它决定每个模拟交易日分几个阶段、每个阶段叫醒谁、发生的每件事记在哪里，并保证任何一天都能原样重放或从中分叉。

产物 RunManifest/runs/<run_id>/响应缓存跨运行共享只追加事件日志

01职责一览

一句话：orchestrator 掌管仿真时钟和"谁在什么时候被叫醒"，把每次运行的全部过程写进一个只追加的目录，并用一份运行清单说清这次运行是怎么来的。

其他模块各管一摊：events 产出新闻卡片，agents 让散户思考，market 判定成交（MVP 不自建撮合§8），accounts 记账。它们彼此不直接调用，只通过 schemas 里定义的类型交换数据§3.3。把它们按顺序接起来、保证顺序每次都一样的，就是本模块。模块说明里列的职责是"时钟、激活、种子、快照、分叉、运行清单与运行目录布局"，主要产物是 RunManifest§3.3。

输入
  • configs/ 里的运行配置（运行模式、种子、模型、基线与消融开关）§3.3
  • events 的 EventCard，按 available_at 进入候选池§5.2
  • population 的人设库与智能体分档（Tier-A / Tier-B）§14.1
  • 行情经 pit.query(table, asof=clock) 读取§5.5
→
本模块 orchestrator
  • 推进仿真时钟，按阶段划分一天§3.4

02为什么需要它

几百个由 LLM 驱动的散户同时在发帖、看帖、下单。没有一只统一的钟，结果会随执行顺序变化，成本会随人数线性上涨，未来信息也会漏进过去。

第一个原因是顺序。同一阶段被叫醒的智能体是并发跑的（异步批量调用 LLM）。如果甲在这一阶段发的帖子乙马上就能看到，那么乙的决定就取决于甲先跑完还是后跑完，同一份配置跑两次可能得到两个结论。设计文档的做法是阶段之间严格按时钟推进，一个阶段里发的帖子要到下一阶段才可见§9.1。这样同一时刻不存在循环依赖，并发结果和执行顺序无关。

第二个原因是钱。每次激活最多两次 LLM 调用：第 1 次人人都调，约 3.0k 输入、200 输出 token；第 2 次只给要发帖的人，约 3.6k 输入、300 输出§14.2。MVP 按 550 个智能体、每个交易日 2 个激活点算，交易日每天上限约 7.26M 输入 / 0.55M 输出，一年 242 个交易日约 17.6 亿 / 1.33 亿；123 个非交易日的 20:00 激活点一年再加约 4.5 亿 / 0.34 亿§14.2。这是假设人人被叫醒、人人发帖的上限。真实散户大多数日子不看盘，所以文档把"按需激活"列为降本第一杠杆：日激活比例从 100% 降到 30%，调用量按比例下降§14.3。决定谁该醒的逻辑放在调度器里，成本才会跟着信息量走，而不是跟着人数走§3.1。

第三个原因是可复现和可分叉。项目要回答"如果那天没有这条政策会怎样"这类反事实问题，需要从某天的快照分叉出去，只改一处，其余完全一样§9.3。持续运行的前向数据还要求当天写入、带时间戳、只追加、永不重算§9.3§11.3§13.1。这两件事都要求运行过程被完整记录，并且有一份清单说明用了哪版代码、哪个模型、哪个种子。

第四个原因是防泄漏。所有数据读取都经过 pit.query(table, asof=clock)，强制 available_at ≤ clock§5.5。这里的 clock 就是调度器维护的仿真时钟。时钟错一个阶段，盘前的散户就可能看到收盘价。

反例：没有调度器会发生什么（示意）把所有智能体放进一个循环里依次调用：排在前面的人先发了"明天必涨"，排在后面的人立刻看到并跟风买入。换一个循环顺序，跟风的人变了，整体看多比例也变了。再把这次运行重跑一遍，模型服务商悄悄更新了别名指向的版本，结果又不同，而且没有任何记录能说明为什么不同。设计文档用"日期化的模型版本写进清单 + 回放只读缓存"堵住后一个漏洞§14.4。

03机制详解

五件事按顺序讲：时钟怎么把一天切成阶段，每个阶段叫醒谁，发生的事怎么记，一次运行的身份证（运行清单）写什么，以及怎样重放和分叉。

3.1 仿真时钟：交易日五段，非交易日一个晚间点

仿真时钟是一个只往前走的"当前时刻"。它有两个用途：决定现在轮到哪个阶段，以及作为 asof 参数限制所有数据读取，只能看到 available_at ≤ clock 的信息§5.5。available_at 指一条信息最早公开可得的时间，晚间和周末发生的事件会进入下一个激活点的候选池§5.2。

设计文档把一个交易日按 A 股作息切成晚间/隔夜、盘前、集合竞价、盘中检查点、收盘后五段，周末和节假日每天另有一个 20:00 激活点§3.4。MVP 的固定激活点是盘前和收盘后（非交易日为 20:00），盘中检查点只由事件触发§3.4。行情以日线为主：盘前激活看到 T−1 收盘与隔夜信息（available_at ≤ 09:15），收盘后激活看到 T 日收盘§3.4§5.5。

各阶段能产出什么有明确分工§3.4§6.1：

  • 盘前是当日唯一产生例行订单的激活点。前晚"明日打算"为买或卖的人在这里强制激活，看到昨晚的打算和隔夜信息后定实际意向。
  • 集合竞价不调用 LLM：盘前 execution = open 的订单在这里按真实开盘价判定（§8.2 第 1 步）§8.2。
  • 盘中检查点只由量级 ≥ 3、available_at 落在交易时段的事件触发，在其后最近的检查点叫醒接触到该事件的人。可以下单，但执行方式只限 chase，成交价取检查点至收盘的分钟均价加滑点。分钟线只为事件日的指数与被激活者持仓补；拿不到分钟线时，这次激活只出态度与帖子，交易意向转为"明日打算"，运行清单标"盘中无行情"。盘中激活的 token 单独计量。
  • 收盘后出 BeliefUpdate 和"明日打算"（买 / 卖 / 持有 / 观望 + 标的），写入记忆，不出订单。
  • 非交易日 20:00 按 νi × 周末系数抽人，只有信息与社交，同样出"明日打算"，节后跳空由此产生。周末系数取真实股吧非交易日与交易日发帖量之比。账户不结算、不出快照，出入金意向顺延到下一交易日（银证转账只在交易日办理〔需复核〕）。长假前最后一个交易日的盘前 prompt 写明"明天起休市 N 天"；Tier-A 每周反思放在周末激活点。

"明日打算"与次日盘前实际意向之差记为隔夜变卦，是言行不一的一种，和"帖子 vs 成交"并列；长假中间的改动只作描述§3.4。决策表的 plan_ref 把实际意向链回前晚的打算，调度器负责让两次激活能接上§10.3。持续运行中各激活点按真实时间跑：盘前调用在 08:00–09:15 跑完，盘中检查点和 20:00 晚间激活按时运行，都带时间戳落盘；成交在收盘后判定§3.4。

下图点击任一阶段可看详情，按钮切换"MVP 口径"和"§3.4 表逐行读"。实心圆是固定激活点（到点一定叫醒该档的人），虚线圆是条件激活（被抽中、被事件触发或被强制才醒），灰点表示该口径下这里不调用 LLM。

3.2 激活调度：每个阶段叫醒谁

"激活"指在某个阶段为某个智能体真正调用一次 LLM，让它走一遍感知、解读、社交、形成意图的流程§6.1。没被激活的人这一阶段什么也不做：保持持仓、不发帖§9.1。设计文档给出的判据是"当且仅当"，满足下面任意一条就激活§9.1：

例行查看（随机抽中）

每人有一个活跃度参数 νi。当日是否查看组合服从 Bernoulli(1 − exp(−νi·ai(t)))，其中 ai(t) 随注意力事件、持仓波动和情绪上升§6.3。外向、短线风格、退休时间多的人 ν 更高§6.3。非交易日按 νi × 周末系数抽§9.1。即便查看了，也只在目标仓位与现仓位之差 |w* − w| 超过个人阈值 τi 时才调仓§6.3。

事件触发（四种）与强制激活
  • 持仓单日波动超过个人阈值
  • 通过自己的媒介接触到量级 ≥ 3 的事件（量级 3 指板块级或明显超预期的宏观信息§5.2）；交易时段内的事件在最近的盘中检查点激活
  • 所在群聊讨论到自己的持仓
  • 所持标的涨停或跌停
  • 强制：前晚（或长假中最后一次）"明日打算"为买或卖者，在次一交易日盘前激活

以上均见§9.1。个人阈值和 ν 的具体取值文档未定义。

每次激活的触发原因写进激活表的 trigger 字段，取值为 ν 抽中 / 事件 / 强制 / 群聊§10.3。被抽中但缺席的人照样记一行：解析失败、拒答、超时三种原因写进 absent_reason§9.1§10.3。持续运行中，盘前调用到 09:15 仍未完成的智能体当日记为未激活、原因"超时"，不推迟下单；超时率与解析失败率、拒答率一起进运行清单并告警§9.1。

事件量级 magnitude（1–5）直接参与激活判断，所以文档特别规定它不能用市场反应回填§5.2。如果按"当天跌了 5% 所以这条新闻重要"来补量级，未来收益就会通过激活模式泄漏进模拟。

Tier-A 与 Tier-B 的区别只在记忆深度、反思频率和激活频率上，两层用同一个模型，避免把人设差异和模型大小混在一起§14.1。Tier-A 50 人（大 V 20 + 深度样本 30），每个激活点都醒；Tier-B 500 人，靠事件和低频例行查看醒来§14.1。Tier-C（批量规则更新的大群体）不在 MVP 内§14.1。

同一阶段内并发，阶段之间按钟。被叫醒的人在同一阶段里异步批量调用 LLM§9.1§14.4。每个激活点分四步执行§14.4：先并发或批量发出该点全部第 1 次调用并校验 JSON；再由内核统一做约束与成交判定§6.3§8.2；然后只对要发帖的人发第 2 次调用，帖子在成交判定之后写，输入含当日意向与实际成交§6.1；最后按种子顺序进行群聊接话。MVP 不自建撮合：模式 A 按真实行情判定能否成交，脚本化情景把给定价格路径当作真实行情，模拟订单不影响价格§8.2。顺序无关靠两条规则共同保证：成交判定在所有第 1 次调用返回之后统一做；本阶段发的帖子要到下一阶段才可见§9.1。唯一例外是群聊：同群在阶段内顺序进行最多 M 轮接话，只走第 2 次调用，不影响当阶段交易§9.1§6.1。

信息发布者（L0–L4 各层的发帖方§3.2）只发帖不交易，也不计入人群统计§5.6，它们的设定见 信息发布者页。文档没有单独规定发布者的激活节奏。

3.3 只追加的事件日志：一切状态都能重算

"事件溯源"的意思是：系统不直接保存"账户现在有多少钱"，而是保存"发生过哪些事"，当前状态由这些事从头累加得出§3.1。在本项目里，每一笔下单、拒单、成交、费用和公司行为都写进事件日志，账户状态可以通过重放这些事件重建，并且与运行清单一一对应§8.4。拒单也要记，因为"想买没买成"本身是散户行为的一部分§8.1。

"只追加"指日志只能在末尾加新行，不能改写或删除旧行。由此有两个推论。第一，按 sim_date 存的每日快照只是缓存，丢了可以从日志重算，业绩也一样§8.4。第二，持续运行的前向数据当天写入、带时间戳、永不重算§9.3§11.3；事后用新版本模型重跑的结果不算前向证据§13.1。目录布局和只追加约束由本模块定义，accounts 和 outputs 通过本模块拿到读写路径（模块说明）。

存储用 Parquet 文件，查询用 DuckDB 和 Polars§14.4。事件日志每一行具体有哪些字段，文档未定义。

3.5 重放与分叉

可复现靠四样东西一起：事件溯源、LLM 响应缓存、固定种子、锁定模型版本§3.1。其中最关键的是响应缓存。缓存键是以下内容合起来的哈希：模型 ID 与带日期的版本号、推理引擎版本、结构化输出后端、schema、采样参数、种子、完整消息§14.4。任何一项变了，键就变了，不会误用旧答案。解析失败的尝试也写入缓存，重试种子进缓存键，重放时复现同一重试序列§6.2§14.4。

重放是用同一份清单把某段日子再跑一遍。重放只从缓存读，缓存缺失直接报错，绝不静默重新调用模型§14.4。这样做的原因是 API 模型无法保证同输入同输出，只有自部署时才能用 vLLM 的批不变性或 SGLang 的确定性推理§14.4；对 API 模型来说，缓存档案就是唯一的确定性来源。同一份清单重放结果必须完全一致，这也是一项防泄漏测试§5.5。

分叉是从某天的快照出发，改一处条件再往后跑。典型用法是假设情景：从某日快照分叉，注入一张假设的 EventCard（origin=counterfactual，只在沙盒里存在§5.2），跑 3 条剧本价格路径 × N 个种子 × M 个模型§9.3。分叉点之前的调用全部命中缓存，只有分叉点之后才产生新调用§14.3。不过次数会成倍放大：Phase 1 的 3 种子 × 2 模型就是 6 倍，再乘 3 条价格路径又是 3 倍§14.2。汇总结果记录跨种子的均值和标准差，跨种子方差大的切片要打标记§9.4。

版本线是持续运行的管理单位：一组固定的代码、prompt、底座版本与内核参数为一条线，记 line_id§9.3。任一项改动即开新线，从最近的日终快照分叉，账户、记忆、信任网络按 run_id 写时复制；新旧线并行约 20 个交易日，差异记入运行清单后停旧线。历史产出不改、不重算§9.3。情景分叉用同一机制，从持续运行或历史推演某日快照分叉，分叉点之前的 LLM 调用走缓存§9.3。

补跑处理漏跑的日子：按 PIT 补跑以保持账户与记忆连续，当日盘前订单仍按 T 日行情判定成交。补跑产出在激活表标 backfilled=true，不算 V2 前向证据（补跑时当日真实帖已存在），只作开发与校准样本；补跑日占比写进 V2 报告和运行清单§9.3§9.4。

07与其他模块的关系

调度器不做判断、不判定成交、不记账，它只决定"现在几点、该谁、记到哪"。下面按它和每个模块交换的东西列出。

schemas

定义 RunManifest、EventCard 等类型。模块之间只通过这些类型交换数据§3.3。

data

调度器把时钟作为 asof 传给 pit.query，data 负责保证读不到未来§5.5。

events

提供带 available_at 和 magnitude 的事件卡，前者决定何时进候选池，后者参与激活判断§5.2。

population

提供人设库、Tier 分档和活跃度等人设参数；调度器据此抽取例行查看的人。

agents

被叫醒后先走调用 1（信念更新与交易意向，收盘后与晚间只出明日打算），内核约束与成交之后，想发帖的人再走调用 2 写帖子§6.1。调度器只管叫醒、排顺序和收集结果。

llm

网关和响应缓存。缓存跨运行共享，不放在单次运行目录里（模块说明）；分叉点之前的调用全部命中缓存§14.3；重放只读缓存§14.4。

social

帖子按 sim_time 落盘，调度器保证它们下一阶段才可见§9.1；群聊讨论持仓是触发条件之一。

market · accounts

在所有决策返回后统一做成交判定（market 输出 Fill）与结算（accounts）§14.4§3.3；成交、拒单、费用写进本模块定义的只追加日志§8.4。

outputs

经本模块取得交付表路径；每行带 run_id 并能追到唯一清单§9.4。

validation · collect

基线与消融只是配置，由调度器照常运行§3.3。collect 做真实帖子的前向存档，文档未规定它和调度器之间的接口。

想按时间顺序看这些模块怎么配合，可读 一个交易日、一次运行 和 一条信息的旅程。不同类型散户在各阶段怎么决策见 模拟人群，发布者怎样产出帖子见 信息发布者。总览回到 首页。

08开放问题

以下是设计文档 v0.3 仍待定或标了〔需复核〕的地方。写代码前需要先拍板。

待定
  • 交易日晚间是否由事件叫醒人。§3.4 表里晚间/隔夜一行写"时政敏感者、群聊活跃者（事件触发）"，但 MVP 固定激活点只列盘前、收盘后与非交易日 20:00§3.4；§5.2 又说夜间事件进入下一激活点的候选池§5.2。本页把交易日晚间画成"不激活"，属于本页推断。
  • 未定义的具体值：个人波动阈值、νi 与 τi 的取值、"躺平"持续天数§6.3、Tier-B 低频例行查看的频率、超时与失败率的告警阈值。
  • 实际激活比例：成本估算用的是人人激活的上限；OASIS 的做法是核心用户激活概率 0.1、普通用户 0.01，本项目的实际比例在 Phase 0 探针里测§14.2。
  • 可得时点规则：各类数据 available_at 的具体取法 §5.5 还没定，它决定盘前点能看到哪些信息§5.5。
  • 非交易日出入金：出入金意向顺延到下一交易日，依据是银证转账只在交易日办理〔需复核〕§3.4。
  • 数据结构：RunManifest 字段名与类型（文档只给了 line_id）、事件日志的行格式、运行目录内的文件名、快照粒度（文档写每日收盘结算后生成账户与持仓快照§8.4，版本线分叉时记忆与信任网络也按 run_id 写时复制§9.3，它们的快照格式未定义）。
  • 分叉接口：§9.3 规定了版本线和情景分叉从日终快照出发、分叉点前走缓存，但分叉如何记录父运行、分叉时哪些状态可改、如何注入假设事件卡，没有接口定义§9.3。
