流程 · 运行生命周期

一次运行，从配置到重放

一次运行（run）先写配置和预注册，再生成人口、按仿真时钟逐日推进，把帖子、态度、决策和账户落盘，然后做 V1–V5 验收；任何一天都能凭事件日志和响应缓存重放，或者从快照分叉成新的情景§3.1§9.4。

orchestrator · 时钟与运行清单 llm · 响应缓存 outputs · 交付表 validation · 验收

01总览：一次运行的七个环节

一次运行（run）是一次完整的仿真实验，由 orchestrator（编排器）统一调度，以一个 run_id 为身份。它分三段：运行前把配置和判定标准锁定，运行中按仿真时钟逐日推进，运行后落盘、验收，并保留随时重放或分叉的能力§3.3§9.4。点击图中任一环节查看它的输入、输出和负责模块。

① 配置

这张图里有两件事要先说清。第一，"运行前"的三步全部发生在看到任何仿真结果之前：验收用哪些事件、过线标准是多少、拿哪些基线来比，都要先写进预注册并提交到 git，否则事后挑一个好看的指标就失去了检验意义§11.4。第二，⑦ 是一条回路：事件日志、每日快照和响应缓存三样东西齐全时，任何一天都可以原样重放，也可以从某天的快照分叉出去改一个条件再跑，分叉出的运行拿到新的 run_id§3.1§8.4。

03运行前：配置、预注册与人口

运行前的三步决定"跑什么、拿什么判、谁在跑"。它们的共同点是全部可以入库、可以复查：配置在 configs/，预注册在 docs/prereg/，人口有自己的版本号并写进运行清单§3.3§9.4。

配置：一套模拟，换参数就是另一个实验

configs/ 放所有可以入库的运行参数：人口的 IPF 目标边际、情景与价格路径（乐观 / 中性 / 悲观三档）、模型路由、V1–V5 的及格线。API 密钥放 .env，不进仓库configs/README。这里有一个容易忽略的设计：基线 B2–B4 和各项消融也写成这里的运行配置。B2 同质人口、B3 打乱人设、B4 去掉社交层，本质上都是"同一套模拟换一个开关"，所以由调度器照常运行，validation 模块不为它们另写代码§3.3§11.1。这样做的好处是基线和正式运行走完全相同的管线，比较时差异只来自那一个开关。

配置里还有两个开关会直接影响结论能否成立。一是意向来源（谁给出"想买想卖"的初步意向：LLM、规则先验或 Jev 评估分类器），它是可替换接口，Phase 0 先做三者的对比试验讨论 Q1§15.1。二是真实帖子注入：默认关，用于验收的运行强制关，开关状态写进运行清单，因为把真实帖喂进信息流会让 V2 的"像不像真人"失去意义§5.7讨论 Q2。

预注册：在看到结果之前把尺子定死

预注册（prereg）是把"用什么指标、及格线是多少、在哪些事件上验收、跟哪些基线比"提前登记下来。项目采用轻量做法：Phase 0 结束前登记 V1–V5 的主指标与及格线、验收事件清单和基线集合，其余指标一律算探索性结果§11.4。操作上，每轮验收运行之前在 docs/prereg/ 提交，git 提交时间就是登记时间；已提交的不改写，要改就另起新文件写明原因docs/prereg/README。

为什么要这么严：仿真可调的东西太多，跑完再挑一个好看的指标或事件，几乎总能"通过"。预注册之后，已提交的内容不改写，要改只能另起新文件并写明原因docs/prereg/README；及格线本身允许在 Phase 0 依 B5 噪声底线调整一次§12.3。止损判据同样在 Phase 0 预注册、事后不改§15.2。

样本量也在这一步定。V2 的人工盲评按二项检验估功效：要以 80% 功效、双侧 α = 0.05 检出识别率 60% 对 50%，每个验收事件约需 200 对，盲评由用户及其团队完成，功效用 statsmodels 计算§11.4讨论 9。验收事件优先选在所有用到的模型（智能体底座、事件抽取、改写、嵌入）训练截止日之后发生的事件，截止日之前的事件只用于调通管线与风格；能被记忆探针或帖子补全探针"补出原文"的时段不用于 V2；验收事件的真实帖不进校准目标和少样本池§11.3§13.1。

生成人口：550 个人从哪里来

人口以 CHFS（中国家庭金融调查）家庭为种子样本，用 IPF（迭代比例拟合，一种把样本权重反复调整到吻合各维度目标分布的方法）校准到 configs/ 里的目标边际。抽样按 5 个年龄段 × 账户规模 RT1–RT5 × 4 个 MBTI 气质组（NT / NF / SJ / SP）共 100 格，每格保底 5 人，得到 500 个 Tier-B（轻量人设）；Tier-A（深度人设，兼作大 V）50 人另行抽取，合计约 550 人§4.3§14.1。按格保底而不按账户数等比例抽，是因为 RT4–5 只占账户的 1.8%，却贡献约 32% 的成交额，等比例抽几乎没有大户样本§4.3。每个人带两种权重：w_head 表示他代表多少真实投资者，w_cap 等于 w_head 乘以他的账户资产；全市场口径用权重加总，人群口径看格内原始样本§4.3§10.1。V1 用 TVD（总变差距离：两个分布逐项之差的绝对值求和再除以 2）检查边际，及格线是主要边际 TVD ≤ 0.05§12.3。

人有了，还需要起始持仓。投资史预跑从每个人的入市年份跑到仿真起点，用规则内核在真实历史行情上调整仓位，得到起点时的持仓与成本价，以及逐年盈亏、最大回撤等经历。预跑只用起点之前的数据、不调 LLM，所以成本低，也不会引入泄漏§4.4§9.2。预跑的群体结果要对上真实散户的事实：小户整体跑输，2015 年财富从小户流向大户，多数持股家庭报告亏损（CHFS 2013 年为 70.4%）；对不上就调预跑参数，不改写经历文本§4.4。从人生骨架与预跑结果中选 3–8 个最显著的片段写成带日期的预置记忆，标记 seeded§4.4；预跑得到的起点之前的账户历史单独存放并标 seeded，不与仿真期混在一起§10.3。每格约 5 人意味着格内差异基本没有统计功效，分人群结论只在合并后的切片（气质组、年龄段、账户规模）上下§11.4。

已定（v0.3 §4.3、§14.1，来自架构讨论 A5）

种子不足：CHFS 没有 MBTI，气质组在事后抽取，种子压力落在"年龄段 × 账户规模"25 格上（每格需 20 人）。格内不同种子家庭不足 5 户时，从相邻年龄段、同账户档借种子并把年龄改到本格，人设卡标 seed_borrowed；仍不足则对现有种子做扰动复制，标"种子稀少"（seed_sparse）；完全没有种子的格留空并在报告中写明，不让 LLM 编造人口属性。人群口径结论附"不同种子数 / 借种比例"，种子稀少格只作描述、不做显著性检验；全市场口径照常按 w_head 加权进 V1。阈值 5 户在 Phase 0 看到实际分布后可调§4.3。

Tier-A 50 人：拆为大 V 20 人与深度样本 30 人。大 V 按入市 ≥ 8 年、金融素养 ≥ 2、外向性偏高、账户偏中大档条件抽样（这些条件是假设，报告中标注）；深度样本按账户档每档 6 人，落在已有 Tier-B 的格内，同格对比作为 V5 的分层效应检验。Tier-A 与 Tier-B 一起做 IPF 得 w_head；人群切片默认只用 Tier-B，Tier-A 单列§4.3§14.1。

已定（v0.3 §4.4、§5.5，来自架构讨论 A1、A8）

预跑用到的行情：日线从 2005 年起，覆盖股改与 2007 年牛市；2005 年以前的经历只写进人生骨架作文字背景，不在行情上预跑。存不复权日线和复权因子表（以除权除息日为 available_at）；智能体看到的价格按 asof 当天现算前复权，收益与战绩统一用后复权§5.5§4.4。

按比例预跑：预跑只记仓位权重、收益率、出入金占资产比例，不记绝对金额、不受整手限制；期末整体缩放，使起点资产等于抽样档位金额，整手与最低佣金从仿真起点才生效。缩放后倒推的历史入金与人生骨架收入不相符时重抽经历、记录重抽次数，不改档位；多次仍不合理标 life_asset_conflict。上面"小户跑输""2015 年财富流向"等群体检验看收益率与缩放前的相对财富变化，不受缩放影响§4.4。

数据源、各表 available_at 的取值规则与存储格式仍待定，随数据源一起定§5.5。

04运行中：时钟、激活与每一次 LLM 调用

运行阶段由 orchestrator 推时钟、决定谁被激活，llm 模块负责把调用发出去、校验、存进缓存。这一节讲三件事：一天怎么推进，一次调用怎么做到可复现，调用失败时怎么记录§3.3§9.1§14.4。

一天的固定激活点：盘前和收盘后

MVP 的仿真时钟每个交易日有两个固定激活点：盘前（08:00–09:15）和收盘后（15:00–18:00）；非交易日只有一个 20:00 晚间激活点；盘中检查点（10:00 / 11:30 / 14:00）只由量级 ≥ 3 的盘中事件触发§3.4。订单只在盘前产生，按 T 日行情判定成交；盘中事件激活也能下单，但执行方式限 chase。收盘后与非交易日的激活不出订单，第 1 次调用改为 BeliefUpdate 加"明日打算"（买 / 卖 / 持有 / 观望 + 标的），主要产出帖子、结算与测量§3.4§6.1。

在某个激活点，一个智能体被激活有三种情况：按活跃度 ν_i 被抽中（相当于例行打开软件看一眼，非交易日按 ν_i × 周末系数）；被触发，即持仓单日波动超过个人阈值、接触到量级 ≥ 3 的事件、群里有人讨论他的持仓、所持标的涨跌停；或被强制激活，即前晚"明日打算"为买或卖的人在次一交易日盘前必须激活。没被激活的人保持持仓、不发帖；被抽中但缺席的（解析失败、拒答、超时）照样记进激活表§9.1§10.3。持续运行中，盘前调用到 09:15 还没完成的智能体当日记未激活、原因"超时"，不推迟下单§9.1。

同一阶段被激活的人并发执行，阶段之间严格按时钟推进，本阶段发的帖子要到下一阶段才可见§9.1。这条规则让并发结果与执行顺序无关：如果 A 和 B 同时被激活，A 先跑完发的帖子不会被 B 看到，否则结果就取决于谁先返回，重放时无法复现。唯一的例外是群聊：同一个群在阶段内顺序进行最多 M 轮接话，只走发言调用，不影响当阶段交易§9.1§7.1。价格从哪里来取决于实验类型：历史事件推演和持续运行用真实行情（模式 A），假设情景用乐观 / 中性 / 悲观三档脚本价格§3.5§9.3。

每个激活点内部按固定顺序走四步：先并发或批量发送该激活点全部第 1 次调用（解读与意向）并校验 JSON；再由内核统一做约束与成交判定；然后只对要发帖的人发送第 2 次调用（发言，输入含当日意向与实际成交）；群聊接话放在最后，按种子决定的顺序进行§14.4 第 3 点§6.1。成交判定和费用归 market 模块，记账归 accounts 模块§3.3。

一次调用如何做到可复现

API 模型无法保证同一输入得到同一输出，所以可复现完全靠响应缓存：每次调用的结果按缓存键存档，重放时只读缓存，未命中直接报错，不静默重新调用§14.4 第 1、2 点。缓存键必须包含所有会改变输出的因素，少一个，换了条件的调用就会错误地命中旧结果。

缓存跨运行共享，不放在运行目录里§3.3。这正是分叉便宜的原因：分叉运行在分叉点之前的消息与母运行完全相同，调用全部命中缓存，只有分叉之后才产生新请求§14.3 第 5 点。厂商的模型别名可能悄悄指向新版本，所以清单里写带日期的版本号；用更新的模型重跑不算前向证据§14.4 第 2 点§13.1。

调用量的上限也在这里算。第 1 次调用（全员）约 3.0k 输入 token、200 输出；第 2 次调用（仅发帖者）约 3.6k 输入（含与第 1 次共用的 3.0k 前缀）、300 输出。550 个智能体在交易日 2 个激活点全部被激活且全部发帖时，每日约 7.26M 输入 / 0.55M 输出，按每年 242 个交易日约 17.6 亿 / 1.33 亿；123 个非交易日的 20:00 激活点另计，每年约 4.5 亿 / 0.34 亿。N 个种子 × M 个底座要乘 N·M（Phase 1 的 3 × 2 即 6 倍），假设情景的三档价格路径再乘 3。这是上限：第 2 次调用的实际量等于上限乘发帖率，按需激活后的实际比例与发帖率都在 Phase 0 探针中测；盘中检查点、群聊接话、发布者帖子、反思、V3 调查与 Jev 单独计量，不在上表内；设计文档不做费用估算§14.2。

调用失败时怎么记

核心原则是不编数据：输出坏了就如实记"没激活"，不填默认值，也不沿用上期信念，否则缺席会被伪装成"中性态度"混进统计§6.2。

已定（v0.3 §6.2、§14.4，来自架构讨论 A4）

解析失败：Pydantic 校验失败时换新种子重试，最多 2 次；种子是缓存键的一部分，所以每次重试是不同的缓存条目。仍失败则该智能体当天记"未激活"，原因"解析失败"，不填默认值§6.2。

拒答：模型拒答单独记一类，不重试，当天记缺席。拒答率按话题与人群切片，计入底座模型选型的扣分项§6.2。

超时：持续运行中盘前调用到 09:15 没完成的，当日记未激活、原因"超时"§9.1。

重放与告警：失败的尝试也写进缓存，重放时复现同一重试序列。token 用量、解析失败率、拒答率与超时率写进运行清单，超阈值告警；还要检查缺席是否集中在某些人群或某些行情日，结果写进 V1 / V3 报告§14.4 第 1、6 点§9.4。

已定（v0.3 §14.1、§14.4，来自架构讨论 A4）

底座：MVP 全走国内厂商 API，不自部署；两个底座都从有开源权重的模型中选（如 Qwen、DeepSeek 系列），闭源模型只作对比，具体型号在 Phase 0 按选型标准与记忆探针测完再定，团队若有 GPU 可加一个自部署底座对比§14.4。同一底座下 Tier-A 与 Tier-B 用同一个模型，分层只体现在记忆深度、反思频率与激活频率；跨底座比较时全体一起换；小模型留到 Phase 2 扩规模时，V2 文风指标与 V5 一致性不退化才切换§14.1。

网关：自写薄网关，用官方 openai SDK 换 base_url，不用 LiteLLM，不兼容的厂商单写适配器；缓存键、重放未命中报错、失败尝试入缓存、按 run_id 与 persona_id 计量都自己实现；Jev 走同一网关，按分类器类型单独计量。嵌入模型在本地运行开源中文模型，版本号写入运行清单与缓存键§14.4。

05运行后：落盘与验收

落盘的原则是先记事件、再派生表：所有变化追加进事件日志，快照和交付表都能从日志重算。验收对照预注册的及格线，V1–V5 各自出结论，V2 决定帖子能不能交付§8.4§12.3。

运行目录里有什么

orchestrator 规定每个运行一个目录 /runs/<run_id>/，里面是运行清单、只追加的事件日志、按 sim_date 存的快照和交付表；accounts 与 outputs 的读写路径都由 orchestrator 给出§3.3。事件日志记下每一笔下单、拒单、成交、费用和公司行为，账户状态可以由事件回放重建，并与运行清单一一对应。每日快照只是缓存，战绩随时可以从日志重算§8.4。存储用 Parquet + DuckDB + Polars，事件日志只追加§14.4。

交付物是三张主表（帖子、态度、决策）、激活表、调查表、信任网络快照和四张账户类表，全部 Parquet，以 persona_id、event_id、run_id 关联，账户类表另加 sim_date；另附人设表和运行清单§10.3。激活表每个智能体每个激活点一行，被抽中但缺席的也记，带 line_id、phase、trigger、status、absent_reason、info_cutoff、backfilled、warmup 等字段；其余各表只带 activation_id，时点、版本线、补跑、预热这类行级元数据从激活表取。可得时点按行取 info_cutoff：该行只使用 available_at ≤ info_cutoff 的信息§10.3。信任网络快照在持续运行中每 20 个交易日出一次§10.3§7.2。帖子表的 simulated 恒为 true，预跑得到的起点之前的账户历史单独存放并标 seeded；发布者的帖子进帖子表，但不进人群统计§10.3§10.1。帖子表只在团队内部及内部下游项目之间流转，不接入任何对外渠道；每条帖带 simulated 字段与正文隐式标识，对外展示样例时另加"模拟生成"显式标识§16.2。各交付表的每一行经激活表都能追溯到唯一的运行清单，这是"可审计"的具体含义§9.4。

验收：五项各自判，V2 是总闸

一个情景要跑多个种子和底座，所以态度与决策的聚合值同时记录跨种子均值和标准差，情景结果输出分布，跨种子方差大的切片在报告里标注§9.4。基线用来回答"得分来自哪里"：B1 单个 LLM 不带人设，B2 同质人口，B3 打乱人设，B4 去掉社交层，B5 真实帖对真实帖的上限（判别器的噪声底线），B6 事件错配§11.1。及格线与不过线时的处置如下，处置规则在 Phase 0 预注册、事后不改§12.3§15.2。

项检查什么及格线 §12.3不过线 §15.2

06重放与分叉：缓存决定哪些调用要重新付费

重放是用同一份清单把运行原样再跑一遍，用来证明结果可复现；分叉是从某天的快照出发、改一个条件再跑，用来做情景推演和反事实比较。两者都依赖同一个机制：调用先查响应缓存，命中就不再请求模型§3.1§14.3 第 5 点§14.4。

重放的要求最严：LLM 层只读缓存，未命中直接报错。一次重放中途报错，说明清单里某个影响输出的因素变了（例如推理引擎升级、schema 改了），或者缓存条目丢了，这时应当查原因，而不是让网关悄悄重新调用模型补上，因为补上的结果已经不是原来那次运行§14.4 第 1 点。"同一运行清单的重放一致性测试"列在工程约定的测试清单里§14.4 第 6 点。

分叉的代价取决于分叉点在哪里。分叉点之前，分支的消息与母运行完全一样，全部命中缓存；分叉点之后，改动的条件进入了消息或缓存键，调用都要新发§14.3 第 5 点。分叉出的运行拿新的 run_id，账户、记忆、信任网络按 run_id 写时复制，所以同一个人在不同分支里的状态互不干扰§8.4§9.3。预热放在分叉点之前，预热期产出在激活表里标 warmup，不进 V2–V4 验收§9.2。下面的模拟器用 12 个示例交易日演示这一点。

持续运行用同一套分叉机制管理改动。一组固定的代码、prompt、底座版本与内核参数算一条版本线，记 line_id；任一项改动就开新线，从最近的日终快照分叉，新旧线并行约 20 个交易日，差异记入运行清单后停旧线。已经落盘的历史产出不改、不重算§9.3。

漏跑的日子按 PIT 补跑，让账户与记忆保持连续；当日盘前订单仍按 T 日行情判定成交。补跑产出标 backfilled=true，只作开发与校准样本，不算 V2 前向证据，因为补跑时当天的真实帖已经存在；补跑日占比写进运行清单和 V2 报告§9.3§9.4。

08还没定的事

下面这些问题，设计文档要么只给了原则，要么明确留给后续阶段。实现前要逐条拍板，拍板结果应当写回设计文档，而不是只留在代码里。

和运行清单直接相关

  • 清单字段的类型和命名。§9.4 只列了要记录哪些内容（代码版本、版本线 line_id、数据快照、人口版本、模型与版本、嵌入模型版本、采样参数、种子、模板哈希、意向来源、真实帖子注入开关、场外配资开关、涨停成交概率档位与脚本化残差日期块、各底座的内核校准修正量、缓存命中率、token 用量、解析失败率、拒答率与超时率、补跑日占比、信息流长度分布、事后视角命中率），没有字段名、类型和文件格式。本页演示里的字段名都是示意。
  • 几项"记入运行清单"的内容不在 §9.4 的列表里。§5.2 要求 LLM 与人工量级打分的一致性记入运行清单，§3.4 要求没有分钟线的盘中检查点标"盘中无行情"，§9.3 要求新旧版本线的差异记入运行清单；§9.4 的列表没有点名这几项，字段怎么放还要定。
  • 新旧版本线的差异怎么量。§9.3 定了并行约 20 个交易日、差异记入运行清单后停旧线，但比哪些指标、差多大算可接受，没有写。
  • 预注册怎样和清单挂钩。预注册在每轮验收运行之前提交（docs/prereg/ 的说明），但清单里用什么字段指向它（文件哈希、提交号还是编号），文档没有写。
  • 运行目录里的具体文件名。§3.3 规定了目录装什么（清单、只追加的事件日志、按 sim_date 的快照、交付表），没有规定文件名和分片方式。

和调用、成本相关

  • 具体用哪两个底座、哪个版本。§14.4 只定了"国内厂商 API、有开源权重的模型、同一底座内 Tier-A 与 Tier-B 用同一个模型"，具体型号和带日期的版本要在 Phase 0 定，并写进底座模型的截止日表§15.1。
  • 真实激活比例与发帖率。§14.2 的 token 估算按"每个交易日两个固定激活点、第 1 次调用全员、第 2 次调用仅发帖者"计，表中第 2 次调用按全员发帖的上限算，实际量还要乘发帖率。激活比例和发帖率在 Phase 0 测，测之前本页的成本数字都只是上限。
  • 告警阈值。§14.4 第 6 点要求 token 用量、解析失败率、拒答率与超时率超阈值告警，阈值是多少没有写。

和数据、分叉相关

  • available_at 的规则与存储格式。设计文档只定了复权因子以除权除息日为 available_at（见 03 节的决定框），其余各表的取值规则与存储格式在 §5.5 仍待定，随数据源一起定。它决定预热和分叉时哪些信息能进 prompt，是泄漏测试的基础。
  • 分叉时种子和底座怎样分配。Phase 1 要求 3 种子 × 2 底座模型 × 3 档价格路径§15.1，但每个组合是不是都从同一个快照分出、快照按哪个种子生成，文档没有说。
  • configs/ 的文件格式。§3.3 列了它装哪几类配置，没有格式和校验规则。
  • 费率参数待核实。成交时用到的费用条目在 §8.1 标了〔需复核〕，运行前要按生效日核对后再写进配置。
本页没有写的数字设计文档没有给出的内容本页一律不写：单次运行的金额成本、告警阈值、一次运行具体从哪天预热到哪天、各步骤的实际缓存命中率。演示和模拟器里出现的天数、ID 和计数都是示例数据。
