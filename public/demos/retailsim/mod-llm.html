模块页 · llm

llm · 统一 LLM 网关

所有模型调用都从这一层出入：它决定一次请求能不能复用缓存、坏输出怎么重试、拒答怎么记账，并把每一次调用写进调用日志。

产物：调用日志 重放未命中即报错 解析失败、拒答、超时分开记 自写薄网关，不用 LiteLLM

01职责一览

一句话：llm 是全系统唯一跟模型厂商打交道的地方，负责路由、缓存、批处理、结构化输出和成本计量，产物是调用日志。§3.3

"网关"在这里指一层很薄的转发代码：上游模块把"要问模型什么"交给它，它决定这次请求要不要真的发出去、发给谁、怎样检查回来的 JSON，最后把结果交回上游，并把过程记一笔账。agents、events、social 等模块都不直接调用厂商 SDK。设计文档还规定，Jev 这类分类器 API 也经此调用。§3.3§6.6

输入

  • 输出 schema：schemas 用 Pydantic v2 导出的 JSON schema，例如 BeliefUpdate、DecisionIntent、FundingIntent§3.3§14.4
  • 调用参数：底座模型（由运行配置统一指定，全体智能体同一个）、人设卡里生成时绑定的采样温度 temperature、种子、运行模式（录制 / 重放）§4.1§6.6§14.4

02为什么需要它

模拟要能重放、要能分叉、要能算清楚花了多少，这三件事都只能在"调用模型"这一个口子上做。

可重放。设计文档的第 5 条原则是：事件溯源、LLM 响应缓存、固定种子、锁定模型版本合在一起，任何一个交易日都可以重放和分叉。§3.1同一份运行清单重放必须得到完全相同的结果。§5.5厂商 API 本身不保证确定性，同一请求今天和下个月可能回答不同；厂商的别名（例如 DeepSeek）还会悄悄指向新版本。§14.4§13.4能让某个交易日再跑一遍还一字不差的，只有把当时的回答存下来，重放时只读存档。这件事必须在所有调用共同经过的地方做，否则漏掉一个模块，整次重放就不可信。

可分叉。反事实实验从某个交易日分叉出去，比如"假如那天没有这条政策"。分叉点之前的每一次调用都应该命中缓存，不花一分钱、不改一个字。§14.3§14.4所以缓存跨运行共享，不放在单次运行目录里。§3.3

可计量、可监控。MVP 单次运行一个交易日，第 1 次调用约 3.3M 输入 token，加上第 2 次调用的全员发帖上限共约 7.26M（全员激活的上限口径），多种子、多底座时还要乘以种子数 × 底座数，Phase 1 的 3 × 2 即 6 倍§14.2。token 用量、缓存命中率、解析失败率、拒答率与超时率都要进运行清单§9.4，超阈值要告警§14.4。拒答会集中出现在政策类新闻上，不能当随机缺失处理§13.3，这要求每次拒答都被单独记下并能按话题切片。API 密钥只放环境变量或密钥服务，调用日志脱敏后落盘§16.4，这些规则也只需要在一处执行。

反例：每个模块各自调用 SDK 设想 agents 和 events 各自 import openai 直接发请求。events 那边忘了把结构化输出后端写进缓存键，后端升级以后回答变了，重放时却照样"命中"旧的存档，没有任何报错；agents 那边解析失败时悄悄填了默认值，失败率没进清单；两边的 token 各记各的，对不上总数。设计文档列出的五项测试里，"重放一致性测试"和"token 用量、解析失败率、拒答率与超时率超阈值告警"§14.4在这种结构下没有地方挂。（反例为本页构造，用来说明集中一处的必要性。）

3.1自写薄网关

"薄"的意思是：网关只做下面几件事，不做 prompt 编排、不做智能体记忆、不做重试以外的容错策略。设计文档技术栈表的网关一行写的是"自写薄网关，官方 openai SDK 换 base_url；不用 LiteLLM"。§14.4

已定（v0.3 §14.4，来自架构讨论 A4） 网关自写薄层，不用 LiteLLM。国内厂商走 OpenAI 兼容接口，用官方 openai SDK 换 base_url 调用，不兼容的厂商单写适配器。缓存键定义、重放未命中报错、失败尝试入缓存（§6.2）、按 run_id 与 persona_id 计量都自己实现。Jev 经同一网关，按分类器类型单独计量。

为什么自写，§14.4 写了两条理由。第一，网关最要紧的几件事，即缓存键怎么定义、重放未命中时报错、失败的尝试也写入缓存、按 run_id 与 persona_id 计量，用现成框架也都得自己实现。第二，国内厂商走 OpenAI 兼容接口，官方 openai SDK 换 base_url 就能调用，少一个大依赖，锁版本和复现都更容易。设计文档对整个技术栈的总体判断也是"核心自己写薄的一层"，因为现成框架没有一个同时满足日频步进、事件溯源、响应缓存与可重放。§14.4§2.4

网关的职责边界来自 §3.3 的模块表：路由、缓存、批处理、结构化输出、成本计量，Jev 等分类器 API 也经它调用，产物是调用日志。§3.3本页把这五项按一次请求的先后顺序展开，见上图与下面几小节。

谁负责：设计文档给 Phase 0 排了 2–3 周，内容之一就是搭 LLM 网关§15.1；人员配置里 1–2 名平台工程师负责调度、LLM 网关与数据层§15.3。

为什么键里记带日期的模型版本，不记厂商别名
设计文档把"模型静默更新"列为风险，应对是锁定带日期的模型版本，并把响应缓存作为可重放的存档。§13.4厂商别名（例如 DeepSeek）会切到新版本，所以运行清单写带日期的版本号，缓存键也用它。§14.4如果键里只记别名，别名切换后旧缓存仍会"命中"，回答却已经和新模型对不上。MVP 全走 API，做不到确定性重执行，重放只靠响应缓存存档。§14.4
为什么 run_id 不在缓存键里
缓存跨运行共享，分叉与重放都要复用它。§3.3§14.4分叉出来的新运行有新的 run_id，但分叉点之前的请求和原运行完全一样，应该命中原运行的存档。§14.3如果把 run_id 放进键，每个分叉都会从零开始调用。run_id 用在计量上§14.4，不用在键上。
为什么键里放完整消息，不放模板 ID
同一模板每天渲染出的文本不同：今日信息、检索到的记忆、信息流的顺序都在变，信息流还按种子为每个智能体打乱。§13.4模板内容的哈希另外写进运行清单。§9.4两处各管一件事：清单说明"用了哪版模板"，缓存键保证"这一字一句的请求对应这一份回答"。
为什么推理引擎版本与结构化输出后端也要进键
设计文档写明，官方文档提示更换结构化输出后端会改变输出，所以后端要锁定。另一条相关事实是 vLLM 自 v0.12.0 起移除了 guided_json，改用 structured outputs 接口，接口本身也会随版本变。§14.4自部署时还可以打开 vLLM 的 batch invariance 或 SGLang 的 deterministic inference，速度代价未核实。§14.4这说明"同一模型、同一消息"不足以保证同一回答，所以引擎与后端要一起进键（引擎一项的理由为本页推断）。

嵌入模型不走厂商 API：设计文档定为本地运行开源中文嵌入模型（如 BGE 系列），锁定权重版本，结果按文本哈希缓存，版本号写入运行清单与缓存键。§14.4§9.4记忆检索、背景故事多样性检查与同质化诊断共用它。§6.4嵌入调用是否也经本网关、与 LLM 响应缓存是否同一套存储，文档未定义。

3.3重放只读缓存，未命中即报错

网关有两种运行模式。录制：未命中就真的调用厂商，回答写进缓存。重放：只从缓存读，未命中就报错，不静默重调。§14.4（设计文档只写了"重放只读缓存"，"录制"是本页为正常运行起的称呼，文档未定义这个模式名。）

为什么不"未命中就补调一次"：补调得到的是今天的模型对这条请求的回答，和当时的回答可能不同。补调后整次重放看起来跑通了，其实混进了一条新回答，后续的帖子、信念和成交都可能因此偏离。报错能让人立刻发现"缓存键漏记了什么字段"或"消息构建有不确定性"，这正是设计文档要求的重放一致性测试要抓的问题。§14.4

API 模型做不到确定性，只能靠缓存；自部署可以打开确定性推理，但 MVP 不自部署§14.4，所以 MVP 的可重放性完全由缓存承担。§14.4反事实分叉时，分叉点之前的请求全部命中缓存；分叉点之后的请求是新的，需要真正调用。§9.3§14.3§14.4分叉运行在网关里对应哪种模式，文档未定义。

3.4解析失败、拒答与超时：三种缺席，分开记

厂商回来的东西先过一道判别。解析失败指回答到了，但用 Pydantic 按 schema 校验不通过，比如 stance 超出 -2..2，或者 reasons 超过 3 个。§6.2拒答指模型不肯写，例如对政策话题回一句"无法讨论"。两者的成因可能不同（本页解读，文档未写这条理由）：前者多半是随机的格式错误，换个种子再采一次就可能通过；后者是模型的内容策略，再采几次大概率还是拒。设计文档写明拒答集中在政策与政治类新闻上，不能当作随机缺失直接丢弃。§13.3

校验方式：输出由 Pydantic 校验，推理框架支持时再加 JSON schema 约束解码。§6.2MVP 全走厂商 API§14.4，约束解码是否可用取决于厂商，所以网关在回答到手后一律用同一份 Pydantic 类型再校验一次。字段约束本身来自 schemas：例如 stance 是 Literal[-2, -1, 0, 1, 2]，reasons 是 Field(max_length=3)。§6.2

已定（v0.3 §6.2、§9.1，来自架构讨论 A4）
  • 解析失败（Pydantic 校验不通过）：换新种子重试，种子进缓存键，最多 2 次；仍失败，该智能体当日记"未激活"、原因"解析失败"，不填默认值，也不沿用上期信念。
  • 拒答：单独记类，不重试，当日同样记缺席；拒答率按话题与人群切片，作为底座选型扣分（§13.3）。
  • 超时：持续运行中盘前调用到 09:15 仍未完成的智能体，当日记为未激活、原因"超时"，不推迟下单（§9.1）。
  • 失败的尝试也写入缓存，重放时复现同一重试序列。解析失败率、拒答率与超时率写入运行清单并告警（§9.4、§14.4）；检查缺席是否集中在某些人群或行情日，结果放进 V1、V3 报告。
  • 三种缺席都照样记入激活表，status 与 absent_reason（解析失败 / 拒答 / 超时）两列区分（§9.1、§10.3）。

为什么不沿用上期信念（本页解读，文档未写这条理由）：沿用等于替智能体编了一份"今天没变"的回答，下游会把它当成真实的态度，失败多的日子里人群情绪曲线会被人为压平。记"未激活"与 orchestrator 的激活机制口径一致：未激活者保持持仓，不发帖。§9.1缺席是可见的，能被统计、能被检查是否集中。

为什么拒答不重试：设计文档规定不用越狱提示，遵守厂商政策。§13.3本页的解读是，反复重试等于"试到它写为止"，还会把拒答率算低，而拒答率要计入选型扣分。§6.2设计文档引用过一个先例：用 2,000 个中国人设做民意模拟时，DeepSeek-R1 有 1,618 个无效输出（推理过长或疑似审查）。§13.3§2.3拒答集中在政策与政治类新闻上，恰好是本平台最关心的输入，所以要按话题切片；某类事件拒答率高的模型不参与该类事件的情景实验。§13.3

为什么失败的尝试也要写进缓存：设计文档的理由是重放时复现同一重试序列。§6.2§14.4具体过程是：重放时同一条请求第一次读到的仍是那份坏 JSON，网关照样判它失败、照样换同一个新种子、照样读到第二次的存档。重放与录制走的是同一条路径。如果只存成功回答，重放时第一次请求就会未命中报错。

超时这条只对持续运行规定，持续运行的各激活点按真实时间运行§3.4§9.1；历史推演是否也设截止，文档没有写。09:15 的截止由谁执行（网关取消请求，还是 orchestrator 到点不再等待），文档未定义。

拒答怎么识别（关键词、厂商返回的拒绝标记，还是分类器），文档未定义〔需复核〕。设计文档另外要求按模型、按事件类别监控拒答率、无效输出率、免责声明率与说教率。§13.3

3.5批处理与并发

每次激活最多两次调用：第 1 次（全员）解读并给出意向，只要结构化字段；第 2 次只对想发帖的智能体，写帖子正文。§6.1网关按激活点分步处理：先并发或批量发送该激活点全部第 1 次调用并校验 JSON；再由内核统一做约束与成交判定；最后对发帖者发送第 2 次调用；群聊接话在其后按种子顺序进行。§14.4§6.3§8.2§7.1第 2 次调用要等内核跑完，因为它的输入里有当日意向与实际成交（含未执行原因）。§6.1同一阶段内的激活者并发执行（异步批量调用 LLM）；阶段之间严格按时钟推进，本阶段发的帖子下一阶段才可见，所以并发结果与执行顺序无关；唯一例外是群聊，同群在阶段内顺序进行最多 M 轮接话，只走发言调用。§9.1这对网关的含义是：同一批第 1 次调用之间没有依赖，可以一起发出去、一起收回来，回答的先后不影响结果，也不影响缓存键；第 2 次调用同理。群聊接话有先后依赖，要按种子顺序逐条发。并发层 MVP 用 asyncio，规模化后用 Ray。§14.4

省钱的办法里有几条落在网关。§14.3批处理："回放模式不要求实时，可走厂商批处理接口或离线批推理"（第 4 条）。文档没有展开"回放模式"，本页理解为在历史行情上跑、不需要当日出结果的运行；它和上文"只读缓存的重放"是两件事，后者根本不发请求。响应缓存：重放或分叉时，分叉点之前的调用全部命中（第 5 条）。前缀缓存：prompt 按"规则说明 → 人设卡 → 长期信念 → 检索到的记忆 → 当日信息 → 输出 schema"排列，静态在前、动态在后，同一激活的两次调用共用静态前缀（第 3 条）。§6.1第 2 次调用的约 3.0k 前缀与第 1 次相同，可命中前缀缓存。§14.2自部署推理引擎会自动复用共享前缀，但只加速预填充；API 侧的缓存有最小长度与过期时间限制，收益取决于复用间隔。§14.3

各家厂商的组合限制不同：阿里云百炼（DashScope）的批处理不能与上下文缓存叠加；Anthropic 的缓存读取可以与批处理折扣叠加；DeepSeek 没有批处理接口（2026-10 的厂商文档），成本测算按实际组合计。§14.4schema 保持扁平：一次厂商测试（8B 模型）中，嵌套 schema 让结构化输出的开销在 vLLM 上达到 +42%、SGLang 上 +6%，扁平 schema 为 +6% 与 +2%；同一来源的吞吐测试（70B FP8、1×H100、50 并发、80% 共享前缀）为 vLLM 1,850 tok/s、开前缀缓存后 2,100，SGLang 2,550。都是单次测试，选型前要在自己的负载上重测。§14.4后两组数只在自部署时用得上。
