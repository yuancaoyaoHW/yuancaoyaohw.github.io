信息与事件层：一条新闻怎样变成事件卡

events 把新闻、政策和公告去重后抽成统一格式的事件卡，给出量级与相关资产，再写出不带立场的官媒转述和快讯两类文本，交给注意力与社交层使用。

产物 EventCard 按事件调用 LLM，与人数无关 量级防记忆污染 §5.2 L2–L4 文本归 social §5.3

01职责一览

一句话：events 把同一件事的多条新闻合成一张事件卡（EventCard），定下何时可见、多大、涉及哪些资产，再写出官媒和快讯两类中性文本。

设计文档的模块表写的是"新闻、政策、公告 → 事件卡；按渠道改写（官媒 / 财经快讯 / 传闻）"，产物是 EventCard§3.3。§5.3 把改写按事实与观点分开：events 只产出 EventCard 与 L0（官媒转述）、L1（快讯）两类不带立场的版本；L2–L4 的观点帖、情绪帖和传闻帖由 social 的发布者以 Post 产出§5.3。模块表里的"传闻"，在 §5.3 里对应 L4 另立的 origin="rumor" 事件卡，见 3.4。

和其他业务模块一样，events 只通过 schemas 里的共享类型与外界交换数据，不导入别的模块的类型，由 orchestrator 把它和上下游串起来§3.3。

02为什么需要它

散户每次激活只看几条信息，系统得先知道"今天发生了几件事、各有多大、谁该关心"。events 把杂乱的新闻流整理成这样一份清单，并且只做一次、所有人共用。

第一个原因是成本。同一条政策新闻会被官网、通讯社、快讯平台各发一遍，如果让每个智能体自己去读、自己去理解，LLM 调用量就和人数成正比。设计文档把抽取和改写定成"事件级调用"：先聚类去重，每个事件簇只调 1 次 LLM，成本随事件数增长，与智能体数无关§5.2§14.3。MVP 有 550 个智能体§14.1，这一条省下的调用是按倍数算的。

第二个原因是时间。回放历史时，智能体只能看到那个时刻已经公开的信息。事件卡的 available_at 记的是最早可公开获取的时间，不是事件发生的时间；夜间、周末发布的事件进入下一个激活点的候选池§5.2。数据层再强制 available_at ≤ clock§5.5。没有这一步，"晚上九点的新闻"可能被下午三点收盘时的智能体读到。

第三个原因是调度要用一个统一的尺度。谁被唤醒、谁先看到什么，取决于事件的量级：媒介接触到量级 ≥ 3 的事件是激活条件之一§9.1，注意力打分里也有一项 m(量级)§5.4。量级必须在事件进入仿真之前就定好，而且只看文本。

第四个原因是保住分歧。抽取模型会顺手判断利好还是利空，这个判断记在 direction_hint 里，只用于路由与监控，不给智能体看§5.2。智能体读的是改写后的文本，每类文本还有 1–3 个版本，避免所有人读到同一段话§5.3。

反例：让每个智能体直接读原始新闻
  • 同一事件的 5 条重复报道会挤占 K_i 条的注意力预算（K_i 取 3–15§5.4），有人一次激活只看到同一件事。
  • 理解新闻的调用乘以 550 人，而且每人理解的"这件事有多大"各不相同，激活规则无从下手。
  • 如果改成把抽取模型的一句"利好"直接附在新闻后面，所有人继承同一个解读，群体退化成基线 B1（单 LLM 无人设）§5.2§11.1。
  • 如果量级按事后涨跌回填，大涨日的事件量级偏高、激活人数偏多，未来收益就漏进了激活模式§5.2。

03机制详解

一条新闻要经过去重、遮蔽、抽取、打量级、映射资产、写 L0/L1 版本、一致性校验七道工序，才进入智能体的候选池。下图每个方框都可以点开看说明。紫色框是设计文档明确写了要调用 LLM 的步骤；其余方框文档没有逐一说明由规则、LLM 还是人工完成（例如量级本身是抽取字段之一，验收事件再加人工标定）。

3.1聚类去重与抽取

原始条目覆盖时政与政策、宏观数据、市场、公司、国际五类来源§5.1（第六类真实帖子默认不进入智能体信息流§5.7）。同一件事往往有多条报道，events 先按"嵌入相似度 + 时间窗"把它们聚成一个事件簇，再对每个簇调用 1 次 LLM，抽成一张 EventCard§5.2。"嵌入"是把一段文本变成一串数字向量，意思相近的文本向量也相近；时间窗保证隔了很久的相似报道不会被并到一起。相似度阈值和时间窗长度，设计文档没有给出。

抽取出来的字段里，有三个需要特别小心。available_at 取最早可公开获取的时间，夜间、周末的事件顺延到下一个激活点§5.2；MVP 的固定激活点是盘前和收盘后，交易时段内量级 ≥ 3 的事件另在其后最近的盘中检查点触发激活§3.4。这个时间从哪来，§2.5 给了两条原则：自建存档同时保存源时间戳与入库时间，以二者较晚者为可见时间；事后回补的历史数据只有源时间戳，加保守延迟（文档举例 15 分钟）后使用，并标记 backfilled，以便比较两类数据上的结果是否一致。政策文件用发布日期而不是成文日期，19:00 播出的新闻联播归入下一交易日§2.5。direction_hint（−1、0、1）只用于路由与监控，不展示给智能体§5.2。credibility 默认 1.0，传闻小于 1，证实或辟谣后更新；后续报道、证实、辟谣通过 parent_id 指回原事件§5.2§7.4。origin 取 real、rumor、counterfactual 三值，后两类只存在于沙盒§5.2§16.2。抽取模型与 prompt 版本锁定，结果缓存，同一份输入重放时得到同一张卡§5.2。

3.2量级：五档表、打分依据与防记忆污染

量级 magnitude 是 1 到 5 的整数，按下表判断§5.2。它在下游有两处用途：媒介接触到量级 ≥ 3 的事件是激活条件之一§9.1；注意力打分里的 m(量级) 也由它而来§5.4。量级打偏，被唤醒的人数和每个人看到什么都会跟着偏。

量级含义例
1例行信息日常公告、符合预期的月度数据
2个股或细分行业级业绩大幅超预期、行业标准发布
3板块级，或明显超预期的宏观信息行业重大政策、PMI 大幅偏离预期
4全市场级政策降准降息、印花税调整、重要会议定调
5历史级冲击2024-09-24 政策组合、2025-04 关税冲击

设计文档的规则是：量级只依据文本做事前判断，绝不用事后市场反应回填§5.2。但还有一种更隐蔽的泄漏。抽取模型的训练数据里装着历史，看到"降准 + 互换便利"就知道这是 2024-09-24，也知道后来涨了多少，打分可能受"已知结局"影响。所以挑选验收事件时，截止日表要覆盖所有用到的模型，包括智能体底座、事件抽取、改写和嵌入模型§13.1，聚类用的嵌入模型和写 L0/L1 的改写模型也在其中；匿名化只能减轻、消除不了这种泄漏，因为宏观事件一看便知§13.1。

已定（v0.3 §5.2，来自架构讨论 A3）
  • 遮蔽：抽取 prompt 遮去专有时间叫法（如"9·24"），只依据文本写明的三样东西打分：政策力度、发布机构级别、是否超预期。
  • 人工标定：V2 历史验收事件的量级由团队按 §5.2 量级表人工标定，LLM 打分只作参考。
  • 一致性检查：在模型截止日之后的事件上比较 LLM 与人工打分的一致性，结果记入运行清单（RunManifest，§9.4）。
  • 适用范围：开发事件与持续运行只做遮蔽与一致性检查，不做人工标定。
  • 可复现：抽取模型与 prompt 版本锁定、结果缓存；定期人工抽检量级与资产映射。

这三层的分工是：遮蔽挡住最显眼的线索，人工标定保证验收用的那几个事件量级可信，一致性检查告诉团队在没人工标定的日常运行里，LLM 打分能信几分。开发事件和验收事件的划分见§11.3：开发事件是某个底座截止日之前的事件，或被探针判为泄漏的事件，只用于调通管线、文风与校准；验收事件优先取所有底座截止日之后的事件，并须通过记忆探针与帖子补全探针；第三类是前向持续运行，逐日累积、只追加不重算。开发事件和持续运行没有人工标签，§5.2 说的"一致性检查"在这两类事件上具体比对什么，原文没有展开；一致性用什么指标衡量、多低算不合格，也没有给出。

3.3范围与资产映射

每张卡有一个 scope（market 全市场、sector 板块、stock 个股）和一个 assets 列表，列表里是映射到点时的指数、行业、题材、个股代码§5.2。"映射到点时"的意思是：用事件 available_at 那一刻的成分快照，不用今天的成分。指数与申万行业成分用历史快照，股票池包含退市股§5.5。

资产列表的下游用途是注意力打分里的 rel_i：信息与某个智能体的持仓、自选、关注行业重合越多，越容易被看到§5.4。映射错了，事件会推给不相关的人，或者漏掉真正持有的人，所以设计文档要求定期人工抽检资产映射§5.2。具体用什么方法把文本映射到代码（规则、词表还是 LLM 抽取时一并给出），设计文档没有写。

题材维度有个硬约束。题材 / 概念板块成分若拿不到历史快照，只能从某天起逐日存档，存档之前的区间不使用题材维度§5.5。

已定（v0.3 §5.2、§5.5，来自架构讨论 A2、A3）东财题材成分接口受 robots 禁止，不采§16.1；题材 / 概念板块成分改用授权来源（如 Tushare 同花顺概念成分或数据商）§5.5。资产映射里的题材维度等授权题材来源落实后再用§5.2。授权来源具体选哪家，随数据源一起定§5.5。

3.4分渠道改写：事实归 events，观点归 social

同一事件在不同渠道的面貌不同，智能体读到哪个版本取决于其媒介习惯§5.4。渠道与发布者层的级别一一对应§5.6。§5.3 把改写按事实与观点分开：events 只写不带立场的 L0、L1 两类版本，L2–L4 的文本都是观点，由 social 的发布者以 Post 产出§5.3。下表是 §5.3 的渠道表。

渠道 · 层级产出方相对延迟与文风校验
官方媒体 · L0events0；正式、政策话语，只转述与 summary 事实一致
财经快讯、券商观点摘要 · L1events0–10 分钟；简短、带数字与 summary 事实一致
大 V 解读 · L2 及 Tier-A 大 Vsocial随传播；由发布者或智能体自己生成（§7）标注依据的 event_id
中小博主、群主转述 · L3social数小时；情绪化、标题党、叙事简化可歪曲，不做事实校验，须标注依据的 event_id
小道消息、喊单号 · L4social不定；煞有介事、带"内部消息"另立 origin="rumor" 事件卡，带"传闻"标签，只在沙盒运行（§16.2）

§5.3 对 L0、L1 改写有三条规则§5.3：每个"事件 × 渠道"改写 1–3 个版本，量级越高版本越多，避免所有人读到同一段文字，改写成本随事件数增长；改写可以省略细节，但不得编造事实，也不带立场，结果与 summary 做事实一致性校验，不一致的丢弃重写；夸张度、确定性不再是改写参数，改为发布者参数，可以单独研究"标题党"对群体情绪的影响。

已定（v0.3 §5.3，来自架构讨论 A3） events 只产出 EventCard 与 L0（官媒转述）、L1（快讯）两类版本，不带立场，与 summary 做事实一致性校验，按量级每类 1–3 个版本。L2–L4 文本全部由 social 的发布者以 Post 产出：L2、L3 须标注依据的 event_id，帖子表里 L3 发布者帖须填 source_event_ids§10.3；L4 另立 origin="rumor" 的事件卡，带"传闻"标签，只在沙盒运行§16.2。L2–L4 的成本归入 social 估算§14.2。

发布者拿到什么、怎样写，由 §5.6 规定。每个发布者有五个参数：立场（多 / 空 / 摇摆）、动机（流量、带货、引流到付费群等）、准确率、夸张度与确定性；按级别加权进入推荐流§5.6。L2–L4 发布者读事件卡与 L0、L1 版本后发帖；L3 可当群主，L4 喊单号可当"付费荐股群"群主§5.6§7.1。发布者层只发帖、不交易，也不进入人群统计§5.6。所以同一张事件卡在 L3 群主手里可能被写成"明天涨停"，这类歪曲是实验要研究的对象，与 events 的事实校验无关。

为什么这样拆：事实一致性校验只对"转述"有意义。L3 的标题党本来就要渲染歪曲，用 summary 去校验它，要么全部不通过，要么校验形同虚设。把观点类文本放到 social，夸张度、确定性就和发布者的立场、动机放在同一处调，"标题党对群体情绪的影响"这类实验§5.3只改一个模块的参数。L4 另立事件卡，是因为传闻之后可能被 L0 证实或辟谣，需要一张卡来挂 parent_id 与 credibility§7.4。

传闻在设计文档里有两个来源：发布者层 L4 与低可信度事件卡。它们注入群聊或论坛，智能体按轻信度决定是否相信、转发；之后可由 L0 证实或辟谣，辟谣以关联事件卡的形式出现，用来研究"传闻—辟谣"周期§7.4。在事件卡上，这个周期体现为三件事：传闻卡 credibility 小于 1；证实或辟谣后更新 credibility；后续的证实、辟谣卡用 parent_id 指回传闻卡§5.2。模拟传闻只存在于沙盒内，每条带"传闻"标签§7.4§16.2。

成本上，抽取与改写按事件计，不按人计§14.3。§14.2 的 token 表按智能体激活估算，把"反思、事件抽取与改写"和"发布者层 L2–L4 的帖子"都列为单独计量、不在表内的项目，量级小于主循环§14.2。L2–L4 的成本归入 social 估算§5.3，events 剩下的只有抽取和 L0、L1 两类改写。

一个 L0 或 L1 版本由哪种 schema 类型承载（独立类型、Post，还是卡上的字段），设计文档没有定义；每档量级具体几个版本、一致性校验用什么方法，也没有给出。L4 的传闻卡由 events 还是 social 生成，§5.3 没有写明；§3.3 模块表把"传闻"列在 events 的改写里，可读作由 events 出卡。

3.5分发：可见时间与注意力抽取

events 写完版本之后，事情交给感知步骤。每次激活，智能体从候选池里看到 K_i 条信息；候选池包括其媒介习惯覆盖的渠道里的事件改写版本、推荐流与群聊、持仓与自选的行情异动§5.4。每条候选的打分是

score = w_i(渠道) · m(量级) · rel_i(资产) · exp(−Δt / τ_d) · sal

其中 w_i 是由人设生成的媒介习惯（例如中老年偏官媒与群聊，专业背景偏快讯与雪球），m 来自事件卡的量级，rel_i 来自事件卡的资产列表与个人持仓、自选、关注行业的重合度，Δt 是信息发布至今的时长，τ_d 是衰减时间常数，sal 是显著性（涨跌停、上热榜、大 V 转发）§5.4。可以看出，events 填的是 m 和 rel_i 的原料，以及 Δt 的起点。设计文档没有给出 τ_d、w 的取值，也没写 m(量级) 是怎样从 1–5 换成乘数的。

持仓异动必入；其余按 softmax(score / T_i) 无放回抽取，保留随机性，让同一人设的两个智能体看到的信息也不完全相同§5.4。K_i 取 3–15 条，对应约 1,500 token 的信息流预算§5.4。没被看到的信息不会消失，它可能稍后经群聊或大 V 转述到达；同一时段候选越多，每条被看到的概率越低（Hirshleifer, Lim & Teoh 2009），节后首个交易日积压的信息尤其如此§5.4。

可见时间由两道闸控制。第一道是事件卡自己的 available_at。第二道是数据层：所有读取都经 pit.query(table, asof=clock)，强制 available_at ≤ clock，智能体不直接访问数据§5.5。泄漏测试会注入未来时间戳的"金丝雀"记录并断言不可见§5.5。另外，同一阶段里发的帖子下一阶段才可见§9.1，所以 social 基于事件卡写出的 L2–L4 帖子，最早也要到下一个阶段才进入散户的候选池。

交易时段里出现的大事件另有一条路径。量级 ≥ 3 且 available_at 落在交易时段的事件卡，在其后最近的盘中检查点（10:00 / 11:30 / 14:00）激活接触到该事件的智能体§3.4§9.1。这时数据层只为事件日的指数与被激活者持仓补分钟线，智能体只看到检查点之前的分钟数据；可以下单，执行方式限 chase§3.4§5.5。拿不到分钟线的事件日，该次激活只出态度与帖子，交易意向转为"明日打算"，运行清单标"盘中无行情"§3.4。盘中激活的 token 单独计量§3.4§14.2。所以事件卡的 available_at 和 magnitude 两个字段，共同决定一件事是在盘中检查点被读到，还是顺延到下一个固定激活点。

L1 相对 L0 的 0–10 分钟延迟§5.3在以日线为主的粒度下怎样体现，文档没有说明；行情粒度以日线为主，分钟线只补盘中事件日与封板判定所需的两类§5.5。

      6.2改写归属：事实与观点分开
      

      v0.3 的 §5.3 把改写拆成两半：events 写 L0、L1，产物都能对照 summary 校验；social 写 L2–L4，产物都带立场、动机、准确率、夸张度与确定性参数§5.3§5.6。放弃的是"一个模块管所有文本"的集中度，events 的成本估算也随之变小；换来的是 L3 的歪曲不再被当成改写失败，"标题党"实验只改 social 一处的发布者参数§5.3。§3.3 模块表的 events 一行仍写"按渠道改写（官媒 / 财经快讯 / 传闻）"，与 §5.3 的分工对照，"传闻"一项落在 L4 的传闻事件卡上。
      

      


      07与其他模块的关系
      

      events 上游接数据和模型，下游喂给注意力、发布者和调度。下面按"它从谁那里拿什么、交给谁什么"逐个说明。
      

      上游。collect 负责前向存档新闻快讯，这类数据只能从今天起逐日积累§3.3；东财 7x24 快讯接口可采，从 Phase 0 起每日采集§5.5§16.1。data 是 PIT 数据湖，提供指数、行业成分的历史快照和授权来源的题材成分，资产映射要用；盘中事件日的分钟线也由它补§5.5；所有读取经 pit.query§5.5。llm 是统一网关，抽取和 L0/L1 改写都经它调用并缓存§3.3；prompts 存放抽取与改写模板，模板哈希写入运行清单§3.3。schemas 定义 EventCard 类型本身。
      

      下游。agents 的感知步骤把 L0、L1 版本放进候选池，按 §5.4 的打分抽 K_i 条。social 的发布者层由实时行情与新闻事件卡驱动§5.6，负责写全部 L2–L4 的 Post§5.3；不同发布者面对同一张事件卡怎样各写各的，可以在 发布者演示 页里动态看到。orchestrator 管时钟、激活与运行清单§3.3：媒介接触到量级 ≥ 3 的事件是激活条件之一，交易时段内的事件在最近的盘中检查点激活§9.1§3.4；LLM 与人工打分的一致性也记进运行清单§5.2。outputs 用 event_id 关联三张主表§10.3，并对每类事件输出情景条件分布§10.2。validation 的 B6 事件错配基线把 A 事件的生成帖与 B 事件的真实帖对照§11.1，依赖事件卡把帖子准确归到事件上。
      

      一条边界提醒
events 不判断"谁会看到"，也不写观点。前者是 agents 的注意力预算，后者归 social§5.3。events 交出去的只有事实层面的东西：发生了什么、什么时候能看到、多大、关系到哪些资产。
      

      


      08开放问题
      

      下面这些问题，设计文档 v0.3 要么明确写了"待定"，要么没有给出具体做法。它们不影响理解 events 的机制，但写代码之前必须定下来。
      

      历史新闻源未定数据源、各表 available_at 的取值规则与存储格式待定，历史新闻源随数据源一起定§5.5。§2.5 列出的候选各有问题：Tushare 快讯的时间戳是发布时间还是抓取时间未确认；AKShare 新闻类接口多数只返回最近 20–200 条，不能回补；GDELT 2.0 对境内 A 股新闻覆盖薄〔需复核〕§2.5。
      

      授权题材来源未落实题材成分用授权来源（如 Tushare 同花顺概念成分或数据商），具体来源随数据源一起定§5.5。落实之前，资产映射只能用指数、行业、个股三个维度；拿不到历史快照的区间不使用题材维度§5.2§5.5。
      

      L0 / L1 版本的承载类型与传闻卡的出卡方§5.3 规定 events 产出 L0、L1 两类版本，但没有定义它们用什么 schema 类型表示，也没有说是否复用 Post；版本文本是否进入帖子表，文档未写明。L4 的 origin="rumor" 传闻卡由 events 还是 social 生成，§5.3 也没有写明，§3.3 模块表把"传闻"列在 events 名下。
      

      没有给出数值的参数聚类的相似度阈值与时间窗长度§5.2；每档量级对应几个版本（只知道 1–3、量级越高越多§5.3）；事实一致性校验的方法与判定标准§5.3；m(量级) 的换算、τ_d 与 w_i 的取值§5.4；L1 的 0–10 分钟相对延迟在日线粒度下如何体现；夜间事件所在的"晚间/隔夜"阶段在 MVP 交易日里是否按事件触发运行§3.4。
      

      一致性检查的口径§5.2 要求在模型截止日之后的事件上比较 LLM 与人工打分的一致性并记入运行清单，但没有给出衡量指标与合格线；开发事件与持续运行"只做遮蔽与一致性检查"，在没有人工标定的事件上具体比对什么，也未展开。
      

      遮蔽范围§5.2 的遮蔽写在抽取 prompt 上；L0、L1 改写 prompt 以及智能体读到的文本是否同样遮去"9·24"一类叫法，文档没有说。§13.1 第 6 条的立场是主设定使用真实名称。
      

      资产映射与传闻卡的细节文本怎样映射到代码（规则、词表还是由抽取 LLM 一并给出）未定义；credibility 在证实或辟谣后是改写原卡还是新建一张以 parent_id 关联的卡，is_repeat 的判定规则，event_id 的生成规则，都未定义§5.2。
