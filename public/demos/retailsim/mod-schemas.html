基础层 · schemas

schemas：各模块共用的数据类型

把人设卡、事件卡、帖子、信念、意向、明日打算、订单、成交、出入金和运行清单定义成一套 Pydantic 类型，所有模块只靠这套类型交换数据，LLM 的第 1 次调用也按它导出的 JSON schema 输出。

Pydantic v2 · §3.3 JSON schema 约束解码 · §14.4 不依赖任何其他子包 · §3.3 解析失败记缺席 · §6.2 设计草案，尚未实现

01职责一览

一句话：schemas 定义跨模块传递的领域类型（Pydantic v2），并把它们导出成 JSON schema 供 LLM 约束解码；它不依赖任何其他子包 §3.3。

RetailSim 的一次激活要经过好几个模块：events 出事件卡，social 把它变成帖子和信息流，agents 读信息流、产出信念和意向，内核把意向改成订单，market 判定成交，accounts 记账，outputs 落表。每两个模块之间都要传一个对象，这些对象长什么样，统一写在 schemas 里。这里的"类型"指 Pydantic 的模型类：它规定每个字段叫什么、是什么类型、取值范围是什么，创建对象时自动校验。

输入

schemas 在代码上没有输入：它不 import 任何业务模块 §3.3。它的"输入"是设计文档对各个对象的定义：

  • 人设卡 §4.1
  • 事件卡 §5.2
  • 信念与观点、解析失败与拒答 §6.2
  • 意向与明日打算 §6.3
  • 激活表与其他交付表的列 §10.3
  • 运行清单 §9.4
→

schemas

  • 领域类型：PersonaCard、EventCard、Post、FeedItem、BeliefUpdate、DecisionIntent、NextDayPlan、FundingIntent、OrderIntent、Fill、CashFlow、RunManifest 等
  • 枚举与分档：ReasonTag、立场 -2..2、仓位档等 §6.2–6.3
  • JSON schema 导出 §14.4
→

输出（谁用）

  • 所有业务模块：import 这些类型来构造和读取对象 §3.3
  • llm：拿 JSON schema 做约束解码，schema 进缓存键 §14.4
  • outputs：按类型字段落成激活表、帖子表、态度表、决策表、调查表、信任网络快照与账户类表 §10.3
  • orchestrator：把各模块串起来，写 RunManifest §3.3

上游：无。下游：全部模块。schemas 只管"对象长什么样、字段合不合法"；对象由谁、在什么时候产出，由各业务模块负责。比如 T+1 能不能卖是 market 按交易规则判定的 §8.1，不写在类型里。

02为什么需要它

三个具体问题：模块之间会互相导入；LLM 的输出没法直接计数和交给内核；重放和交付表需要一套固定的字段和关联键。

问题一：模块会互相导入

类型流是绕圈的。agents 产出订单意向交给 market，market 产出成交交给 accounts，成交结果又要写回 agents 的记忆 §6.3 第 7 步。如果每个类型定义在产出它的模块里，agents 要 import market 的 Fill，market 要 import agents 的 OrderIntent，就形成循环导入。设计文档的做法是把所有共享类型放进一个不依赖任何子包的叶子包，业务模块彼此不导入对方的类型，由 orchestrator 把它们串起来 §3.3。"叶子包"指依赖图上没有向外箭头的包：别人都依赖它，它不依赖别人。

问题二：LLM 输出要能被程序直接使用

智能体每次激活最多调用 LLM 两次 §6.1。第 1 次是解读与意向，只出结构化字段：盘前与盘中激活出 BeliefUpdate + DecisionIntent[] + FundingIntent，收盘后与晚间激活出 BeliefUpdate + 明日打算 NextDayPlan，不出订单。第 2 次只在 want_to_post 为真时调用，写帖子正文，正文是自由文本，不进 JSON。态度要进态度表按人群切片统计，意向要交给内核换算成目标仓位。如果 LLM 自由作答，比如写一句"准备加点仓"，内核第 1 步"仓位档按人设映射成目标权重"就没有输入可用 §6.3。所以第 1 次调用只输出分档，例如立场 -2..2、收益区间 6 档、仓位 tiny 到 all_in、执行方式 open/dip/chase，再由内核按人设参数映射成数值和限价 §6.2–6.3。分档的取值写在类型里，导出的 JSON schema 交给推理侧做约束解码 §14.4。约束解码是指生成每个 token 时只允许符合 schema 的候选，所以输出在语法上一定合法。

问题三：重放与交付表要对得上

响应缓存的键里包含 schema §14.4 第 1 条。schema 一改，旧缓存就不再命中；重放只读缓存，未命中直接报错，不会悄悄重新调用模型。帖子、态度、决策三张主表靠 persona_id、event_id、run_id 关联，账户类表另加 sim_date；主表还带 activation_id，时点、版本线、补跑、预热等字段从激活表取，不在各表重复 §10.3。这些键在类型里统一命名，各模块才能产出可以拼在一起的行。

反例（示意）假设没有共享类型，agents 把仓位档写成中文"半仓"，内核按英文 half 查映射表，查不到就只能当成观望；同一个人的帖子行用 persona_id、决策行用另一个名字，outputs 拼表时这个人的言行就对不上，"言行不一"也没法测 §6.3 第 7 步。共享类型把这类错误挡在创建对象那一刻：字段名或取值不对，Pydantic 直接报校验错误。

03机制详解

按四件事讲：类型在模块之间怎么流动；一个类型怎么定义；从类型到 LLM 输出要经过哪些校验、校验失败怎么办；各表靠哪些键和时间字段对齐。

3.2 一个类型怎么定义

设计文档给出了 AssetView、BeliefUpdate、DecisionIntent、NextDayPlan、FundingIntent 的类定义 §6.2–6.3。下面是 AssetView，即智能体对一个标的的看法：

class AssetView(BaseModel):
    asset: str                                  # 指数 / 行业 / 个股代码
    horizon: Literal["1d", "1w", "1m"]
    stance: Literal[-2, -1, 0, 1, 2]            # 强烈看空 … 强烈看多
    ret_bucket: Literal["<-5%", "-5~-2%", "-2~0%", "0~2%", "2~5%", ">5%"]
    confidence: Literal[1, 2, 3, 4, 5]
    reasons: list[ReasonTag] = Field(max_length=3)  # 按重要性排序

这段定义里有三种约束。Literal[...] 把字段限定在几个固定取值上，立场只能是 -2 到 2 的整数，写成 "偏多" 或 1.5 都会被拒。Field(max_length=3) 限制列表长度，理由最多 3 个。ReasonTag 是一个枚举，共 16 个标签（policy、macro、national_team、herd、breakeven、lottery 等），理由只能从里面选 §6.2。理由用枚举而不用自由文本，是为了能直接聚合成"因为政策看多的人占比"这类理由分解 §10.2。

这些分档值本身不带单位，换算成数值是内核的事。例如 size="half" 由内核第 1 步按人设映射成目标权重 wint，映射斜率随过度自信参数 κ 变化 §6.3。同一个"半仓"，对不同人设会得到不同的权重；类型只保证所有人说的是同一套档位。

3.3 从类型到 LLM 输出

一个类型要依次经过三道关才变成可用对象：

1导出 JSON schemaPydantic 从类生成 JSON schema，放在 prompt 末尾的"输出 schema"段 §6.1
→
2约束解码推理侧按 schema 限制每个 token 的候选；能做到多少取决于厂商接口 §14.4
→
3Pydantic 校验收到的 JSON 再按类校验一次，通过才构造对象 §14.4 第 3 条

第 2 步依赖推理侧。MVP 全走国内厂商 API，不自部署；调用经自写的薄网关，用官方 openai SDK 换 base_url，不用 LiteLLM，不兼容 OpenAI 接口的厂商单写适配器 §14.4。厂商侧是否支持完整的 JSON schema 约束，文档未写，这也是第 3 步不能省的原因。§14.4 另列了自部署方案，MVP 不用，留给 Phase 0 的自部署对比底座或日后转自部署：vLLM 0.32.0 或 SGLang 0.5.22，结构化输出用 xgrammar 0.2.8；vLLM 自 v0.12.0 起移除了 guided_json，改用 structured outputs 接口；官方文档提示更换结构化输出后端会改变输出，所以届时后端要锁定 §14.4。

schema 的形状影响速度。§14.4 第 4 条引用一次厂商测试（8B 模型）：嵌套 schema 让结构化输出开销在 vLLM 上达到 +42%、SGLang 上 +6%，扁平 schema 为 +6% 与 +2%，所以约定 schema 保持扁平 §14.4 第 4 条。这里有一处没对齐：BeliefUpdate.views 是 list[AssetView]，本身就是一层嵌套 §6.2。文档没说这算不算"扁平"，列入第 8 节。

schema 还是缓存键的一部分：缓存键 = 哈希(模型 ID 与带日期的版本号、推理引擎版本、结构化输出后端、schema、采样参数、种子、完整消息) §14.4 第 1 条。厂商的模型别名会指向新版本，所以运行清单里写带日期的版本号 §14.4 第 2 条。解析失败的尝试也写入缓存，重试种子进缓存键 §14.4 第 1 条。给某个类加一个字段，它导出的 schema 就变了，所有用到这个类的旧缓存都不再命中。重放只读缓存、未命中报错，所以改类型等于宣布旧运行不能再按原样重放，需要在运行清单里能看出用的是哪版类型（版本号字段文档未定义，见第 8 节）。

3.4 校验失败怎么办

约束解码只保证 JSON 的形状合法。厂商 API 不一定做完整约束，模型也可能拒答或超时，所以第 3 步仍会失败。v0.3 把三种失败分开处理：

情况处理记录
解析失败Pydantic 校验不过则换种子重试，种子进缓存键，最多 2 次；仍失败则不填默认值，也不沿用上期信念 §6.2当日记"未激活"，原因"解析失败" §6.2
拒答单独记类，不重试 §6.2当日同样记缺席；拒答率按话题与人群切片，作为底座选型扣分 §13.3
超时持续运行中盘前调用到 09:15 仍未完成，不推迟下单 §9.1当日记未激活，原因"超时" §9.1

三种情况都写进激活表：被抽中但缺席的智能体照样有一行，status 与 absent_reason（解析失败 / 拒答 / 超时）记录原因 §9.1 §10.3。失败的尝试也写入缓存，重放时复现同一重试序列；解析失败率、拒答率与超时率写入运行清单并告警 §6.2 §9.4 §14.4 第 6 条。

不填默认值的好处在于缺失值的含义清楚。如果解析失败时沿用上期信念，态度表里会留下一行看起来正常的数据，读表的人分不出这一行是模型真的这样想，还是补上的。记缺席之后，态度表里就少一行，缺席原因在激活表里单独可查。代价是缺席如果集中在某类人群（比如某种文风的人设更容易拒答），人群口径的统计会偏，所以 §6.2 要求检查缺席是否集中在某些人群或行情日，结果放进 V1、V3 报告。

已定（v0.3 §6.2 §14.4，来自架构讨论 A4）解析失败与拒答分开处理。解析失败换种子重试，最多 2 次，仍失败记"未激活"、原因"解析失败"，不填默认值，也不沿用上期信念；拒答单独记类，不重试，当日记缺席。失败的尝试也写入缓存。失败率与拒答率写入运行清单并告警。

对 schemas 来说，"本次激活缺席及原因"目前只以激活表的 status、absent_reason 两列出现，设计文档没有给激活记录定义类，见第 8 节。

3.5 关联键：怎样把各表拼起来

设计原则第 4 条要求帖子与态度分别存表，以 persona_id、event_id、run_id 关联 §3.1；账户类表另加 sim_date；激活表是各表的行级元数据来源，主表带 activation_id 指回它 §10.3。每个键由一个模块负责生成，其他模块只引用不改写：

3.6 时间字段

设计原则第 2 条是"一切点时"（PIT，point-in-time）：所有数据、事件、帖子都带 available_at，仿真时钟之前不可见 §3.1。数据层的所有读取都经 pit.query(table, asof=clock)，强制 available_at ≤ clock §5.5。类型里有六个时间字段，含义不同：

字段所在类型或表含义
available_atEventCard，数据层各表最早可公开获取的时间，是 PIT 键；夜间、周末发布的事件进入下一个激活点的候选池 §5.2
occurred_atEventCard事件发生时间，可以早于 available_at §5.2
info_cutoff激活表该激活的可得时点：这一行只使用 available_at ≤ info_cutoff 的信息；其他表的行按 activation_id 取它 §10.3
sim_time激活表、帖子表、态度表、交易流水仿真时钟下的时刻 §10.3
sim_date决策表、信任网络快照、账户类表仿真交易日 §10.3
survey_date调查表V3 旁路调查的日期 §10.3 §12.1

schemas 只负责让这些字段在每个类型里叫同一个名字、用同一种类型；"未到时间不可见"由数据层的 pit.query 强制执行，不靠类型校验。

06设计取舍与已定决定

  
每个取舍写选了什么、放弃了什么、为什么。来自架构讨论 A1、A3、A4 的决定已写进设计文档 v0.3，用"已定"框标出出处。

  
类型集中在一个叶子包

  
选了：所有跨模块类型放在 schemas，schemas 不依赖任何其他子包，业务模块之间不导入对方的类型，由 orchestrator 串起来§3.3。放弃了：每个模块各自定义自己的输入输出类型。为什么：类型分散时，market 要用 accounts 的类型，accounts 又要用 market 的 Fill，很快形成循环导入；集中以后，改一个字段只需改一处，所有使用方在测试里同时暴露问题。代价是 schemas 成了所有模块的共同依赖，它的每次改动都波及全局，所以第 8 节列了版本规则这个开放问题。

  
LLM 输出分档，不输出连续数字

  
选了：stance、ret_bucket、confidence、size 都是有限枚举，分档到数值的映射由内核按人设完成§6.2。放弃了：让 LLM 直接给出"预期涨 3.7%""买 23% 仓位"。为什么：文档给的理由是数值输出校准差、容易扎堆在整数§6.2。枚举还有两个附带好处：JSON schema 能把取值限制死，约束解码更可靠；理由用 ReasonTag 枚举而非自由文本，可以直接聚合成理由分解§10.2。放弃的是精度，一个分档里的人在内核映射前没有区别。

  
schema 保持扁平

  
选了：约定 schema 扁平§14.4 第 4 条。放弃了：按领域结构自然嵌套。为什么：引用的一次厂商测试里嵌套 schema 的结构化输出开销明显更高（数字见 3.3），文档同时说明这是单次测试，选型前要在自己的负载上重测。现有定义里 BeliefUpdate.views 仍是一层列表嵌套，怎样算扁平没写清。

  
意向与订单分成两个类型

  
选了：LLM（或其他意向来源）只给 DecisionIntent，内核修正并加硬约束后才产出 OrderIntent§6.3。放弃了：LLM 直接输出 OrderIntent，这是 TwinMarket、StockAgent 等的做法，本项目只作消融，不进主线§6.6。为什么：两个类型分开，意向和实际成交就能分别进决策表，两者之差即"言行不一"，成为可测量的特征§6.3 第 7 步；行为偏差也能在内核里单独校准。代价是多一个类型、多一步映射，映射参数要靠 V4 校准。

  
解析失败记缺席，不沿用上期

  
选了：换种子重试，最多 2 次，仍失败记"未激活"、原因"解析失败"，不填默认值，也不沿用上期信念；拒答单独记类，不重试§6.2。放弃了：解析失败时沿用上期信念补一行。为什么：补出来的行和真实回答在表里分不开，记缺席后缺失值的含义清楚，原因在激活表的 absent_reason 里可查§10.3。代价是缺席可能集中在某类人群，所以要检查缺席分布（见 3.4）。schemas 这边的影响是：缺席只以激活表的列出现，没有对应的类。

  
网关：自写薄层

  
选了：自写薄网关，用官方 openai SDK 换 base_url，不用 LiteLLM§14.4。放弃了：引入 LiteLLM 这类大依赖。为什么：缓存键定义、重放未命中报错、失败尝试入缓存、按 run_id 与 persona_id 计量都要自己实现；少一个大依赖，便于锁版本与复现§14.4。这和 schemas 有关，是因为网关负责拿 schema 做约束解码和校验，schema 是缓存键的一部分。

  
已定（v0.3 §14.4 §6.6，来自架构讨论 A4）MVP 全走国内厂商 API，不自部署；两个底座都从有开源权重的模型中选，闭源模型只作对比。同一底座内所有智能体用同一模型，人设卡不带底座字段。网关自写薄层，不用 LiteLLM；国内厂商走 OpenAI 兼容接口，用官方 openai SDK 换 base_url，不兼容的单写适配器。Jev 经同一网关，按分类器类型单独计量。

  
已定（v0.3 §5.3 §10.3，来自架构讨论 A3）events 只产出 EventCard 与 L0、L1 两类不带立场的版本。L2–L4 的文本都是观点，由 social 的发布者以 Post 产出。L3 可歪曲，不做事实校验，须标注依据的 event_id，落表时填帖子表的 source_event_ids；L4 另立 origin="rumor" 事件卡，带"传闻"标签，只在沙盒运行。对 schemas 的影响：Post 要能带 event_id、source_event_ids 与发布者标识。

  
已定（v0.3 §5.5，来自架构讨论 A1）存不复权日线和复权因子表（以除权除息日为 available_at）。智能体看到的价格按 asof 当天现算前复权，与当年券商软件显示一致；收益与战绩计算统一用后复权。对 schemas 的影响：带价格的字段（如 Fill 的成交价、持仓的 market_price）是哪种口径，类型里需要写明，目前未定义，见第 8 节。





  
07与其他模块的关系

  
schemas 没有上游，其他所有模块都是它的下游。它只定义类型和校验规则，不做任何业务计算。

  
边界。schemas 负责：类型名、字段、取值范围（枚举、上下限）、Pydantic 校验和导出给 LLM 的 JSON schema§14.4。schemas 不负责：谁在什么时候生产这些对象（orchestrator 决定调度，§3.3），分档怎样映射成数值（agents 内核，§6.3），能否成交与费用（market，§8），记账与战绩（accounts，§8.4），把对象落成表（outputs，§10.3）。

  
生产者与消费者。population 产出 PersonaCard；events 产出 EventCard；social 产出 Post 并为每个智能体排出 FeedItem；agents 的 LLM 部分产出 BeliefUpdate、DecisionIntent、NextDayPlan、FundingIntent，内核产出 OrderIntent；market 产出 Fill；accounts 记 Fill 与 CashFlow，不算费用§3.3。llm 网关拿 schema 做约束解码和校验，prompts 把 schema 放进模板；orchestrator 写 RunManifest，并为每次激活（含缺席）记一行激活记录§9.1 §10.3；validation 读的是 outputs 落盘后的表。

  
改动的影响。因为所有模块都导入 schemas，一个字段改名会同时打断多个模块。§14.4 第 6 条要求有契约测试兜底；具体测什么，文档没写，见第 8 节。

  

    population生产 PersonaCard
    events生产 EventCard 与 L0/L1 版本
    social生产 Post 与 FeedItem
    agentsBeliefUpdate、DecisionIntent、NextDayPlan → OrderIntent
    marketOrderIntent → Fill，计算费用
    accounts记 Fill 与 CashFlow
